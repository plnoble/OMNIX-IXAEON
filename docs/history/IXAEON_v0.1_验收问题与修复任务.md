## 3. P1：安装版和开发版 MCP 配置不可用

### 现象与证据

- `apps/desktop/src/main/mcpSnippet.ts` 把安装版 MCP 入口指向 `resources/mcp/index.mjs`。
- `apps/desktop/electron-builder.yml` 没有把 `apps/mcp/dist/index.mjs` 复制到安装包资源目录。
- 当前 `win-unpacked/resources` 中没有 `mcp` 目录。
- MCP 启动命令写死为 `node`，全新 Windows 用户未必安装 Node.js。
- 开发模式通过 Electron 可执行文件位置向上推算仓库路径。实际会解析到类似：
  `node_modules/.pnpm/electron@44.1.1/apps/mcp/dist/index.mjs`，该文件不存在。
- 当前桌面 E2E 只断言配置文本包含 `ixaeon`，没有验证命令、入口文件和真实 MCP 握手。

### 修复要求

1. 开发版生成的 MCP 入口必须指向真实存在的 `apps/mcp/dist/index.mjs`。
2. 打包前必须构建 MCP，并把入口及所需运行文件放入安装包的固定资源目录。
3. 安装版 MCP 不得依赖用户额外安装全局 Node.js。
4. 可以验证 Electron 的 `ELECTRON_RUN_AS_NODE=1` 方案，也可以随应用携带专用运行时；不能只假定用户机器上有 `node`。
5. 桌面设置页输出的 Codex、Claude Code/通用客户端配置必须与真实打包路径一致。
6. 本地令牌仍需通过环境变量或其他受控方式传入，不能把令牌写进公开文件、日志或截图。

### 必须增加的测试

- 开发模式：生成配置后断言 `command` 可执行、MCP 入口文件存在。
- 打包模式：检查 `win-unpacked/resources/mcp/index.mjs` 或最终采用的等价入口确实存在。
- 在不依赖系统 `node` 的环境中，从安装产物启动 MCP。
- 完成一次真实 STDIO `initialize`、`tools/list`。
- 桌面服务运行时，至少真实调用一次 `prepare_task` 和 `record_work_result`。
- 桌面服务未运行或令牌错误时，返回清楚、可操作的错误信息。

### 通过条件

在一台没有配置全局 Node.js、没有源码仓库的 Windows 用户环境中，仅安装 IXAEON 后，编码 AI 可以根据设置页配置连接 MCP、读取背景并写回工作结果。

## 4. P1：问答和 MCP 原文全文搜索失效，并可能越过项目边界

### 现象与证据

以下两处使用了错误连接：

```sql
JOIN segments s ON s.id = f.rowid
```

位置：

- `packages/core/src/storage/askStore.ts`
- `packages/core/src/storage/mcpStore.ts`

`segments.id` 是 UUID 文本，FTS 的 `f.rowid` 是 SQLite 数字行号，因此无法相等。普通搜索中的正确写法是：

```sql
JOIN segments sg ON sg.rowid = f.rowid
```

最小复现结果：当前连接返回 0 条，使用 `rowid` 后返回 1 条。

此外，项目范围搜索当前允许 `src.project_id IS NULL` 的来源进入指定项目的结果。这样可能把尚未分配项目的私人对话发给某个项目的编码 Agent。

### 修复要求

1. 问答和 MCP 全文搜索统一使用正确的 FTS `rowid` 连接。
2. 指定 `project_id` 时，只能返回明确属于该项目的资料。
3. `project_id IS NULL` 的资料只能在用户明确发起全局搜索时使用，不能自动混入项目上下文。
4. 问答、`prepare_task`、`search_context` 都必须应用相同的项目隔离规则。
5. 搜索结果还必须应用有效授权检查，已撤销来源不得返回原文。
6. 修复后检查字符预算，任何结果都不得超过调用者声明的 `max_chars`。

### 必须增加的测试

- 创建只有原文片段、没有 AI 条目的来源，问答仍能通过 FTS 找到它。
- `search_context` 能找到只存在于原文中的唯一关键词。
- Project A、Project B 和未分配来源各放一个秘密标记；查询 Project A 时只能出现 A 的标记。
- 全局搜索是否包含未分配资料必须符合明确、记录在文档中的规则。
- 撤销来源授权后，问答和 MCP 不再返回该来源的原文。
- 中英文、引号、连字符等输入不会造成 FTS SQL 错误。

### 通过条件

问答和 MCP 能检索真实原文，同时不会把其他项目或未分配私人对话混入当前项目。

## 5. P1：主进程授权边界可以被渲染层自行伪造

### 现象与证据

- `apps/desktop/src/preload/index.ts` 暴露了 `pickFiles` 和独立的 `importPaths`。
- `apps/desktop/src/main/ipc.ts` 收到 `input.paths` 后，又把同一个 `input.paths` 当成 `allowedPaths`。
- 因此渲染层可以绕过原生文件对话框，自己传入任意路径，再把该路径同时声明为“已授权”。
- `registerProjectDirectory` 同样接受渲染层直接传入的根目录，并在核心层直接 `grantFolder`。
- 撤销授权后，桌面端的来源阅读、上下文和搜索没有统一检查权限。
- MCP 按 `segment_id` 读取时检查权限，但按 `item_id` 找证据时没有检查，形成旁路。

### 修复要求

1. 原生对话框选择与实际导入必须形成不可伪造的主进程授权链。
2. 推荐方案之一：
   - 原生对话框返回短期、一次性的随机授权票据；
   - 主进程保存票据与规范化真实路径的对应关系；
   - 导入 IPC 只接受票据，不接受渲染层自行声明的 `allowedPaths`；
   - 使用后立即作废，并设置很短的有效期。
3. 更简单的方案是把“弹出对话框 + 授权 + 导入”合并成一个主进程 IPC，让渲染层永远不决定实际读取路径。
4. 项目目录登记、导出目标、恢复包选择也要采用相同的可信边界思路。
5. 所有路径必须先 `realpath`/规范化，再验证授权范围；继续防御 `..`、符号链接和 junction 逃逸。
6. 撤销授权后：
   - 停止后续原文读取和提取；
   - 桌面原文阅读、全文搜索、问答、MCP 摘录都不能再暴露原文；
   - 已经生成的派生结论是否保留，仍按开发计划让用户另行决定；
   - 不能因为撤销授权自动删除已有资料。
7. MCP 无论使用 `segment_id` 还是 `item_id`，都必须经过同一权限检查。

### 必须增加的测试

- 直接从渲染层调用 `importPaths` 并传任意本地路径，主进程必须拒绝。
- 伪造、过期、重复使用授权票据必须失败。
- 对话框选中 A 文件后，不能借该授权读取同目录的 B 文件。
- 选择目录后允许读取范围内文件，但拒绝符号链接/junction 指向的范围外文件。
- 撤销授权后，分别测试桌面阅读、上下文、搜索、问答、重新提取、MCP `segment_id`、MCP `item_id`。
- 删除原文、删除派生理解、撤销授权三种操作保持独立，并有明确确认。

### 通过条件

任何文件读取都能追溯到真实原生对话框或已存在的有效持续授权，渲染层不能给自己授权；撤销后所有读取入口行为一致。

## 6. P1：ChatGPT 自动采集闭环不完整

### 现象与证据

1. `LocalServer` 预留了 `onCaptured` 回调，但 `AppRuntime` 创建它时没有传入。
2. `autoAnalyze` 目前只被保存和显示，没有进入实际业务流程，因此“自动分析”开关没有效果。
3. 扩展弹窗只显示全局采集状态，没有“暂停当前对话”的控制。
4. 新对话尚无 `/c/<id>` 时使用 `page:<hash>`；ChatGPT 随后分配正式 ID 后改为 `/c/<id>`，后端会把它们视为两个来源。
5. 同一轮回答被编辑或重新生成时，新版本被插入，但旧版本没有改为非活动分支；提取时可能同时使用旧答案和新答案。
6. `lastCaptureAt()` 使用来源最初的 `imported_at`，追加新轮次后不更新，所以“最近同步”可能显示第一次采集时间。

### 修复要求

1. 当持续采集开启、域授权有效且 `autoAnalyze=true` 时，采集成功后自动排队提取。
2. 自动分析必须防抖并按来源去重，不能每次 DOM 微小变化都生成重复提取任务。
3. `autoAnalyze=false` 时只保存原文，绝不调用云模型。
4. 扩展弹窗增加“暂停/继续当前对话”；暂停状态按稳定的对话身份保存，暂停期间扩展不得向桌面端发送该对话的新内容。
5. 新对话身份问题可以通过“等正式 ID 后提交”或“临时来源与正式来源安全合并”解决，但必须做到不重复、不丢内容。
6. 回答编辑/重新生成时保留历史版本，同时只能有当前版本处于活动状态。
7. 提取默认只使用活动版本；原始历史版本仍可查看和引用。
8. 每次成功追加内容都更新真实的最近同步时间。

### 必须增加的测试

- `autoAnalyze=false`：采集成功、原文落库、模型调用次数为 0。
- `autoAnalyze=true`：采集成功后出现提取任务，并且同一批重复提交不会重复生成任务。
- 暂停当前对话 A 后，A 不上传；同时打开的对话 B 仍可上传。
- 新建聊天从无 ID 变为正式 ID 后，数据库中只有一个来源。
- 重新生成同一轮回答后，旧版保留但 `is_active_branch=false`，新版为 true。
- 提取上下文中只出现活动版本。
- 最近同步时间随新批次更新。
- 在真实 ChatGPT 页面做一次人工测试并保存状态截图；自动化模拟不能代替这项人工证据。

### 通过条件

用户只需配对一次，之后新对话可以自动增量保存；自动分析开关、全局暂停和当前对话暂停都真实有效。

## 7. P1：导出不够可读，恢复流程存在覆盖与路径风险

### 现象与证据

- 当前 ZIP 只有 `manifest.json`、`readme.txt`、`db.sqlite` 和 `vault/`。
- `manifest.json` 只有版本和计数，项目、来源、结论、纠正、证据、工作记录仍只能通过 SQLite 阅读，不符合“人类可读 JSON”要求。
- 恢复时，旧数据库或 Vault 的 `rename` 失败会被 `.catch(() => {})` 静默忽略，然后程序继续写入新数据，有覆盖旧数据且没有可靠备份的可能。
- 一旦关闭数据库后恢复失败，当前进程的数据库和本地服务可能保持失效状态，缺少完整回滚。
- `Vault.absolutePath()` 只检查 `sha256/` 前缀，没有严格拒绝 `../` 和格式异常。
- 恢复包中的 SQLite 数据可以带恶意 `raw_path`；后续导出可能据此读取 Vault 目录外文件。

### 修复要求

1. 导出 ZIP 至少增加以下人类可读文件，字段命名稳定并带格式版本：
   - `data/projects.json`
   - `data/sources.json`
   - `data/segments.json` 或按来源拆分的对话/文档 JSON
   - `data/items.json`
   - `data/item-evidence.json`
   - `data/corrections.json`
   - `data/work-runs.json`
   - 必要的权限元数据和清单说明
2. 原始文件继续完整保存在 `vault/`，SQLite 可作为快速完整恢复副本继续保留，但不能是唯一的数据表达。
3. 备份失败必须立即中止恢复，不能吞掉异常后继续覆盖。
4. 使用临时目录完成解压、格式检查、数据库完整性检查、迁移兼容检查和 Vault 校验；全部成功后再原子替换当前数据。
5. 替换过程中任一步失败，必须能恢复原数据；不能留下半个新数据库配半个旧 Vault。
6. 恢复失败后应用应继续可用，或者明确、安全地恢复旧运行时；不能静默进入数据库已关闭状态。
7. `raw_path` 使用严格格式，例如：

   ```text
   sha256/[0-9a-f]{2}/[0-9a-f]{64}
   ```

8. 解析路径后还要用 `resolve`/`relative` 或等价方法确认最终绝对路径位于 Vault 根目录内。
9. 恢复必须保持“先预览、再明确确认”的交互；主进程也要防止绕过预览直接恢复。

### 必须增加的测试

- 打开导出 ZIP，不依赖 IXAEON 程序即可阅读项目、结论、纠正和工作记录 JSON。
- 导出再恢复后，项目、来源、片段、证据、当前理解、改口历史、工作记录和原文完全一致。
- 模拟数据库备份失败、Vault 备份失败、新数据库写入失败、Vault 中途写入失败，旧数据都必须保持可用。
- 恢复包包含 `../`、绝对路径、盘符路径、错误哈希长度、哈希与目录不一致时全部拒绝。
- 构造 SQLite 中带恶意 `raw_path` 的恢复包，必须在替换现有数据前拒绝。
- 未执行预览或确认时，直接调用恢复 IPC 必须失败。

### 通过条件

普通用户可以直接阅读导出内容；任意恢复失败都不会破坏当前数据；恢复包不能诱导程序读取或写入数据目录之外。

## 8. P1：首次设置中的自定义数据目录会丢失设置状态

### 现象与证据

`AppRuntime.completeSetup()` 在用户选择新数据目录后，只更新 `bootstrap.json`，本进程仍继续使用旧目录，并把以下内容写入旧目录：

- `setupComplete=true`
- 模型配置和 API Key 密文
- 第一个项目
- 审计记录

下次启动会根据 `bootstrap.json` 打开新的空目录，于是用户可能再次看到首次设置，刚创建的项目和设置也不在新目录中。

现有 E2E 使用 `IXAEON_DATA_DIR` 环境变量固定目录，绕过了真实的自定义目录切换，因此没有发现这个问题。

### 修复要求

1. 用户选择新目录后，首次设置产生的全部数据必须写入新目录。
2. 可以在完成设置前重新初始化运行时到新目录，也可以安全迁移当前临时数据；不能让配置和数据库分散在两个目录。
3. 如果设计上要求重启才能切换，重启后必须保持“设置已完成”、模型设置和首个项目完整，且用户需要得到明确提示。
4. 切换失败时保留旧目录，不得留下指向空目录的启动指针。
5. API Key 仍使用 `safeStorage`，不得为了迁移方便退化为明文。

### 必须增加的测试

- 使用临时 `LOCALAPPDATA`，不要设置 `IXAEON_DATA_DIR`，完整执行一次选择自定义目录的首次设置。
- 关闭并重新创建运行时，验证数据目录、`setupComplete`、项目和模型配置保持一致。
- 模拟目标目录不可写，验证不会修改有效的旧启动指针。
- 默认目录、用户自定义目录、环境变量覆盖三种优先级分别测试。

### 通过条件

选择自定义目录后重启应用，用户仍直接进入主界面，项目和配置都存在于新目录且旧目录没有残留一套分叉数据。

## 9. P1：日志仍会保存对话正文前 2,000 字符

### 现象与证据

`packages/core/src/logging/logger.ts` 对普通字符串只做长度截断。一个 27,000 字符的对话正文会把前 2,000 字符原样写入日志。

现有测试仅断言“完整的 27,000 字符没有全部出现”，因此即使泄漏前 2,000 字符也会通过。

### 修复要求

1. 日志采用字段白名单或明确的敏感字段策略，而不是把任意对象递归后直接写入。
2. `text`、`content`、`body`、`prompt`、`response`、`excerpt`、原始请求等字段不得保存正文，可以记录字符数、哈希、来源 ID、任务 ID和错误码。
3. API Key、Bearer Token、扩展令牌、本地 MCP 令牌继续完全遮盖。
4. 错误对象和第三方 API 错误正文也要清洗，避免正文或密钥藏在 `message`、`cause`、响应体中。
5. 生产日志不能因 debug 级别而恢复保存原文。

### 必须增加的测试

- 日志输入包含独一无二的对话短语，日志中不得出现该短语的任何连续正文。
- 长正文测试不能只断言“完整字符串不存在”，要断言开头、中间、结尾标记都不存在。
- 嵌套对象、数组、Error、`cause`、模型响应和 HTTP 错误分别测试。
- 各类密钥和令牌继续测试。

### 通过条件

日志只能说明“发生了什么”，不能复原用户说过什么，也不能找到任何密钥或令牌。

## 10. P1：重新提取会先删除旧理解，长文切块也没有真正限长

### 现象与证据

- `Extractor.extractSource()` 在任何模型调用之前执行 `deleteOldAiItems()`。
- 如果中间某个模型调用失败，旧的 current AI 条目已经删除，新的结果又没有完整写入。
- Markdown/TXT 普通文档当前被解析为一个完整 segment。
- `buildBlocks()` 只有在当前块已经有内容时才会检查上限；单个 30,000 字符 segment 会完整进入一个标称上限 8,000 的块。
- 这会直接影响两份真实思想文档的提取质量和引用精度。

### 修复要求

1. 所有模型块先成功完成并通过结构、引用和长度校验，再在一个短数据库事务中替换旧 AI 理解。
2. 任意模型调用、解析或写库失败，旧的 current 理解必须保持不变。
3. 不要在跨网络模型调用期间持有长事务锁；可以先把候选结果放在内存或 staging 表中。
4. Markdown/TXT 按标题、段落、列表或安全字符边界拆成可引用 segment，同时 Vault 中的原始文件保持逐字不变。
5. 每个发送给模型的块，包括编号、角色和提示包装后的实际字符数，都不得超过规定上限。
6. 超长单段仍要继续安全拆分，不能因为只有一个 segment 就突破上限。
7. 拆分后每条 AI 结论仍必须能追溯到真实 segment；无效引用不得进入当前理解。

### 必须增加的测试

- 已存在旧 current 理解时，让第一个和中间模型块分别失败，旧理解都保持不变。
- 所有块成功后，旧 AI 理解才被原子替换；用户纠正和 superseded 历史不丢失。
- 导入 30,000 字符单段、多个标题和超长无换行文本，断言任何模型请求都不超过上限。
- 直接导入：
  - `JARVIS/_CONSTITUTION/_v0.1.md`
  - `grok-20260903-IXAEON-思想碰撞.md`
- 验证拆分后的 segment 数量、顺序、引用和原文打开功能。

### 通过条件

模型失败不会让现有理解倒退或消失；长文始终按限制分块；每条理解都能打开准确原文依据。
