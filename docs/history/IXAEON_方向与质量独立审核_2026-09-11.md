# IXAEON 方向与开发质量独立审核

日期：2026-09-11。审核代码：`a9e6eb7`，当前包版本 `0.2.6`。

本轮依据用户要求，独立评估最终目标、实际实现与验证质量。用户与开发 Agent 期间作出的选择作为设计背景，不作为不可质疑的结论。本报告也不把此前由审核者编写的开发计划视为天然正确。

## 1. 结论先说

**方向已经从单项目交接往个人 Agent 拉回，但关键能力没有真正接通；当前不只是差真人验收，还存在可以复现的实现缺陷。**

已有价值：个人范围、关系记录、公开来源检查、编码任务状态与界面开始建立；没有推倒可靠性底座，研究页面也明确说明不是全网搜索。

主要问题：

- 个人理解仍有丢失人工选择、遗漏已确认目标的问题。
- 统筹运行器虽然存在，却未接入桌面实际使用路径；用户用到的关系建议主要是词语重叠规则。
- 研究目前主要是网页／订阅更新检查，没有形成结合用户目标的研究判断。
- 编码任务没有取得真实项目快照和必要背景，验证成功不代表任务完成，结果也没有进入原有工作记忆闭环。
- 隐私、执行隔离、取消、网络防护存在实测或代码可确认的缺口。

**不建议现阶段让它承担重要真实项目的自主修改，也不建议将尚未允许外发的敏感资料放入后直接使用模型问答。** 这是基于合成测试发现的风险，不代表已发现真实隐私泄露、真实项目破坏或外部攻击。

## 3. 必须优先修复的实现问题

优先级含义：P1 应在扩大真实使用前处理；P2 应在认定相应功能已完成前处理。多个失败测试可能属于同一根本问题。

### F01 · P1：所谓“独立验证”会把没有完成的任务放行

位置：[任务页默认验证](D:/Agent/Project/OMNIX-IXAEON析衍/apps/desktop/src/renderer/src/pages/Tasks.tsx:107)、[执行与验证](D:/Agent/Project/OMNIX-IXAEON析衍/packages/core/src/execution/executor.ts:305)。

已复现：RQ07、RQ08、RQ16。

- 任务页创建任务固定配置 `node -e process.exit(0)`，没有检验目标产物或行为；从研究发现创建任务也使用同样命令。
- 执行器报告 `claimedSuccess=false`，随后返回零退出码的验证仍使任务进入 `pending_accept`。
- 配置了两个检查时，只运行第一个；第二个本应失败的检查被忽略。

影响：用户看到“独立验证 passed”，可能理解为结果通过，但系统只证明一个无条件成功的命令运行了。不能通过继续添加“执行器自报不等于验收”的文案弥补。

修复要求：批准前展示真正的成功判据；没有有效检查就显示未验证；保留执行器失败状态，执行全部必要检查，实际产物不存在或范围不符时拒绝通过。不要把缺少运行环境的失败改成成功。

### F02 · P1：可修改范围与隔离执行没有落实到验证阶段

位置：[范围检查](D:/Agent/Project/OMNIX-IXAEON析衍/packages/core/src/execution/taskStore.ts:443)、[验证子进程](D:/Agent/Project/OMNIX-IXAEON析衍/packages/core/src/execution/executor.ts:364)、[进程环境](D:/Agent/Project/OMNIX-IXAEON析衍/packages/core/src/execution/executor.ts:145)。

- 真实 Codex 适配器固定返回空的 `changedPaths` 和 `testsModified=false`，没有通过真实差异独立核对改动。
- 验证命令由父进程直接运行，并非放在所宣称的任务沙箱内。RQ17 的合成 `test.cjs` 成功写入工作区外、但仍属于本轮临时目录的测试文件。
- 静态检查还发现：继承几乎全部父进程环境，只移除两个 IXAEON 环境变量；超时与取消调用 `child.kill()`，未实现计划承诺的子进程树回收。

## 4. 开发方向：哪些选择我会质疑

### D01：统筹器存在于代码，不等于用户已经可以使用它

[桌面实际入口](D:/Agent/Project/OMNIX-IXAEON析衍/apps/desktop/src/main/appRuntime.ts:593) 调用 `proposeObviousRelations()`；`new Orchestrator(...)` 只在测试中出现。

目前关系生成依靠中文相邻字、英文词重叠，冲突依靠少量固定词对。它可以是候选召回方法，但不足以理解“额度监控能够服务模型调度”这类需要看目的、输入输出和能力互补的联系。

“有一张个人总览 + 有一张关系表”是结构进展，不能等于用户要求的整体理解。下一轮应让真实桌面流程调用按需检索与判断，提出有证据、代价和替代方案的建议，并让用户纠正后能记住。

### D02：不买搜索服务可以，不能因此把订阅检查叫作研究完成

现在研究路径没有模型分析或其他实质研究判断；`action_worthy` 默认 false，由用户手动标记，局限说明基本固定为发布方声明。保存的“研究问题”没有用于判断页面内容与目标的相关性。新发现还会直接生成 open_loop，缺少相关性过滤时容易把待讨论变成资讯收件箱。

先检查已批准来源是合理的范围选择；**联网获取信息和研究信息的意义是两项不同能力**。不是非要付费搜索，而是需要利用获准的现有推理能力，对少量资料形成可核对的分析、适用条件与下一步实验。额外模型费用必须明确，不把零搜索费用说成零研究成本。

研究语义补齐前，应称“来源更新检查／研究资料入口”，不能仅凭 T03 打开了一个网页，认定主动研究闭环已完成。

### D03：归档一份旧聊天，不应默认撤销其中所有长期约束

[归档实现](D:/Agent/Project/OMNIX-IXAEON析衍/packages/core/src/storage/sourceStore.ts:629) 会将该来源 origin=ai 的理解整体搁置并清空待处理原因，包含已经由用户确认的理解；恢复来源不恢复这些条目的原状态。自动“经验摘要”取标题与开头几段，不是从成功失败结果中总结经验。

用户确实可能需要让旧工作退出当前待办，但一份旧聊天同时可能包含长期有效的个人原则。例如“这个安装任务结束了”与“我不允许上传私人文档”不应一起失效。

建议重新确认三个动作的区别：停止跟进这个来源、完成／搁置具体任务、撤销某条长期理解。可以提供便捷批量操作，但应有预览和可恢复语义，不能为了页面清爽削弱个人记忆。

### D04：把未完成的新核心放进 0.2.x，不会降低它的实际发布风险

提交链显示 S1—S5 与迁移 11—17 已包含在后续 0.2.x 的源码中，新模块进入运行时，并已有真实安装与更新记录。报告诚实地写“不是 0.3.0”，值得保留；但版本标签不是隔离开关。

建议将实验研究／编码能力显式标为预览并以功能开关控制，把稳定性修复与未完整验收的新核心分开说明。不能因为包号仍为 0.2.x，就绕过真实数据迁移、执行安全和升级证据。

### D05：原计划也需要改进验收组织方式

原计划同时列了很多模型、状态和验收项，容易让实现变成“每一节都有类和页面”，但重要函数只在测试中被调用。只补更多函数级测试，仍然可能继续发生这种偏差。

保留长期目标和安全要求，但下一轮按一个真实用户任务从头到尾交付，再扩展覆盖。不能用“完成 S1/S2/S3”替代“用户现在能靠它解决什么”。

## 5. 对质量的综合判断

值得保留：

- 模块职责开始分开，数据库迁移、共享契约、测试和记录体系已有基础。
- 既有 unit / integration 通过，类型和生产源码规范检查通过。
- 文档保留真实验收未完成标记，研究不冒充全网搜索，当前 UI 也区分 Fake/Codex。

不足集中在：

- 生产调用路径和辅助函数测试不一致，典型是 Orchestrator、taskBackground、助手建议创建与分享控制。
- 测试偏向“函数存在、某字段正确、单条 happy path”，未充分覆盖默认 UI 行为、取消窗口、第二个验证命令、不同读取入口。
- A08/A11/A13/A20 等标为通过的条目，覆盖范围比实际测试宽；“result path”多处仅写 vitest 和日期，不能直接追溯机器结果。
- 新状态机与既有生命周期衔接不足，不能认为旧 V0.2 的可靠性自动覆盖新研究和执行功能。
- 问答覆盖列表直接把全部项目列为 included、omitted 为空，未根据实际进入上下文的证据统计；“已覆盖”的文字仍需收紧。

**综合定位：有可继承基础的早期集成原型，不是只差最后一次点按钮的成熟个人 Agent。** 这不是要求全部重写，而是先修复关键边界并接通已写出的模块。

## 6. 建议下一轮怎么做

### 第一优先：先让现有能力可信

先处理 F01—F06、F08 的执行／隐私／个人语义部分，再扩大真实使用。没有沙箱保障的真实执行保持不可用；没有有效判据的任务只能显示未验证。修复必须保留本轮失败证据，另存通过结果。

不要为了让 RQ 测试转绿而将所有条目改成人工 origin、完全禁用功能、吞掉错误，或把真实工作替换成固定模拟结果。

### 第二优先：做一个对用户有价值的完整演示

选择用户批准的三个真实项目、一组代表性聊天、一个关注主题和一个安全的小编码任务：

1. IXAEON 从聊天中提出目标和约束，用户确认／纠正后稳定保留。
2. 它根据项目能力和目的提出一条真实有用的关联，也能说明哪些不该关联。
3. 对批准来源的新资料给出与目标相关的研究判断，而不只是显示标题。
4. 用户批准任务，执行器获得正确项目快照、必要背景和真实限制。
5. 实际产物经过与任务相关的检查，用户能看见差异并接受或拒绝。
6. 下次打开或换编码客户端时，IXAEON 能说明做了什么、验证了什么、还有什么没完成。

第一条完整演示可以先用已具备真实样本的 ChatGPT；这不是删除 Gemini/Grok/Claude 的既定交付，三者继续在缺项清单中，拿到最小脱敏样本后完成，而不是悄悄另起阶段遗忘。

### 第三优先：再补覆盖与长期成长

接着完成其他平台、真实恢复升级与完整 UI 回归，完善研究质量和低打扰通知，再推进模型池、Door 和正式候选自我升级。当前不需要靠新增设备页面或更多模型选项解决内核未连通的问题。

## 7. 值得与用户讨论的两个决定

1. **归档的含义**：建议默认“停止跟进来源和旧任务”，而不是“忘掉其中已确认的长期原则”。涉及当前实现与此前选择的变化，应由用户确认。
2. **下一次验收看什么**：建议从“新增了多少功能／通过了多少测试”，转成“它能否依据三个真实项目提出有价值的建议，并完成一个可验证的小任务”。测试仍需要，但服务于这个结果。

用户可以决定便利性和自主程度；开发者和审核者仍需说明这些选择的实际代价。用户曾经同意某项方案，不能替代实现证据，也不能使一个尚未落实的隔离承诺成立。
