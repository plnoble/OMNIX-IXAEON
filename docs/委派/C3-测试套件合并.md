# 规格 C3：门禁里按审核编号命名的回归套件——补漏、去重、整理

档位：**A**（测试组织与门禁接线，不改产品代码行为）。大小：以测试文件为主（按 AGENTS.md，300 行只算 `src`，本任务不应改 `src`）。依赖：无。来源：[C3 测试套件分类](交付/C3-测试套件分类.md)（调研 agent 2026-09-29 逐套盘点，整合方定稿）。
v2 规格：验收条件以「门禁照绿 + 逐条对照表」为准，对照表写进交付说明；Codex 审查时核对有没有丢检查点。

## 要什么

门禁（`scripts/verify.mjs`）里有 21 个按审核编号命名的 vitest 套件和 3 组真实 Electron 界面测试。调研逐套盘点后，最要紧的不是减少套件数，而是三个漏洞：

- 两套回归测试（`direction-quality-20260911` 23 项、`direction-recheck-20260914` 14 项）有配置却**没接进门禁**，37 项检查从 9 月中旬起没人跑；
- 两组真实用户反馈的界面回归（`sources` 文件夹导入与重新分析、`wizard` 向导）**没接进门禁**，只能手动跑；
- 一个界面测试配置（`playwright.project-audit.config.ts`）和门禁里的 `recheck-ui` 重复。

另外 `review-f71da15` 与 `review-p0-boundaries` 同一批行为写了两轮，可以合并。

## 整合方定的（2026-09-29）

1. **没接进门禁的两套：先接回来跑，再去重，不许不看就弃用。** 接回来后若有失败：
   - 断言对应的行为后来被锁定规格明确改掉了 → 在交付说明里写清是哪条规格、哪一行断言，删掉那条断言；
   - 看起来是真回归（现行为不对） → **停下**，不改测试、不改代码，列进交付说明，队列状态改「待复审（整合方）」。
2. **`results-*.json`（57 个）不搬。** 它们是历史证据，被 8 份以上历史报告按路径引用，搬家就要改历史文档。在 `apps/desktop/test/review/` 加一份说明：这些是历史证据、没有测试读取、新的证据写进交付说明、不要再往这里放。
3. `review-p2-evolution-upgrade` 只改门禁里的**显示名**（去掉「自演进、升级」字样，免得误读为暂停的能力已实现），不改文件名——历史报告按文件路径引用它。

## 步骤

1. 把 `direction-quality`、`direction-recheck` 两套原样接进 `verify.mjs`，跑通（按上面第 1 条处理失败）。
2. direction 系列三套（quality、recheck、round2）逐条对照去重，合并成一套；每套独有的断言（尤其负向断言）都保留。

5. 删掉重复的 `playwright.project-audit.config.ts`（它的 spec 由 `recheck-ui` 配置接住，不丢用例）。
6. 加第 2 条的说明文件；改第 3 条的显示名。

## 验收条件

1. 合并后 `node scripts/verify.mjs` 全绿，锁定验收（`acceptance-lock`、`acceptance`）不受影响。
2. **独有检查点一条不丢**：被合并、被删的每个 `it()` 在交付说明的对照表里有去处——合并后哪条测试的哪条断言接住它，或第 1 条里「被规格改掉」的依据。没有去处的不许删。
3. 两套原来没进门禁的测试，每条的结局（通过 / 按规格删掉 / 疑似回归待整合方）都列在交付说明里。
4. 门禁里审核回归这一段的总耗时，合并前后各实测一次并写进交付说明（调研实测基线：vitest 套件约 50 秒、界面约 19 秒）。
5. 界面测试步骤在默认端口被占时，给出「先关掉正在运行的 IXAEON」这类明确提示，而不是含糊失败（现有的端口检查若已满足就不用改）。
