# 规格 K2：驾驶舱快照（核心）

档位：**B**（新的数据汇总接口）。大小：中（≤300 行源码；超了就拆成 K2a relay 部分、K2b 队列和项目部分）。依赖：无。
v2 规格：先只推测试（`packages/core/test/acceptance/k2-*.test.ts`），等整合方看过并锁定，再写实现。

## 要什么

一个函数加一个 IPC 通道，把"开发现在跑成什么样"汇总成一份快照，给 K3 的页面和 K5 的手机页用。

每个数据来源都要带**读取时间**和**健康状态**。用户第一眼要能看出数据新不新、是不是卡住了。

## 契约

- 类型（zod，放 `packages/contracts`）：

  ```ts
  SourceHealth   = { status: 'ok' | 'stale' | 'missing' | 'error', readAt: string, lastEventAt: string | null, note: string | null }
  AttentionItem  = { kind: 'relay_down' | 'turn_unfinished' | 'relay_stale' | 'relay_stopped' | 'queue_user',
                     project: string | null, text: string, since: string | null }
  RunningItem    = { kind: 'relay' | 'turn' | 'paused_role', role: string | null, taskId: string | null,
                     startedAt: string | null, until: string | null, text: string }
  RecentEvent    = { at: string, role: string, taskId: string | null,
                     outcome: 'done' | 'failed' | 'timeout' | 'quota' | 'other', text: string }
  ProjectCard    = { id, name, status, description, currentState, updatedAt }
  CockpitSnapshot = { generatedAt: string,
                      sources: { relay: SourceHealth, queue: SourceHealth, projects: SourceHealth },
                      attention: AttentionItem[], running: RunningItem[],
                      projects: { active: ProjectCard[], paused: ProjectCard[], archived: ProjectCard[] },
                      recent: RecentEvent[],          // 最新在前，最多 20 条
                      today: { finishedTurns: number } }
  ```

- 实现放 `packages/core/src/cockpit/snapshot.ts`：

  ```ts
  buildCockpitSnapshot(db, opts: { relayDir: string; ixaeonRepo: string; now?: Date }): CockpitSnapshot
  ```

  - `relayDir` 默认 `join(os.homedir(), '.ixaeon', 'relay')`（和 relay 的数据目录一致），可用环境变量 `IXAEON_RELAY_DIR` 覆盖。
  - `ixaeonRepo` 取设置项 `cockpit.ixaeon_repo`（`packages/core/src/settings.ts` 的 `getSetting`；设置页的输入框在 K3），没设就不读队列，`queue` 记为 `missing`。
  - `packages/core` **不 import `packages/relay`**（依赖方向：core 不反向依赖 relay，和用户 10-29 对 H1 定的一样）：队列主表自己解析，行为照 relay 的 `parseMainTable`（「可以领的」下面第一张表）。
- IPC：`getCockpitSnapshot(): Promise<CockpitSnapshot>`（`packages/contracts/src/ipc.ts` 加类型，`apps/desktop/src/main/ipc.ts` 接 `buildCockpitSnapshot`，preload 暴露）。K3 的页面用它。
- **不加 HTTP 接口**：本机服务（`localServer.ts`）除 health 外都要 Bearer 令牌，现在也没有调用方；以后 K8（MCP）要用时再加。

## 各来源怎么读（只读，只读列出的字段）

**relay**
- `lock.json`：`{ pid, startedAt }`。
  - pid 存活 → `running` 加一条 `relay`（"调度器在转，从 HH:MM 起"）；
  - 文件在但 pid 不在 → `attention` 加一条 `relay_down`（"调度器进程不在了，锁文件残留"）。
- `ledger.jsonl`：读最后 200 行，只用 `turn, role, kind, taskId, startedAt, endedAt, exitCode, timedOut, quotaHit, statusBefore, statusAfter`，生成 `recent` 和 `today.finishedTurns`。`kind` 是 `integrator-inbox`（飞书回复棒）的那几棒**不用 `statusBefore` / `statusAfter`**：那是整合方对用户在飞书里原话的概括，`recent` 里只写「处理了你在飞书里的回复」。
- `turns/`：**只看目录名和文件的修改时间，不读文件内容**。编号大于 ledger 最后一棒的目录，算"没跑完的一棒"：
  - 调度器在转 → `running` 加一条 `turn`；
  - 调度器不在 → `attention` 加一条 `turn_unfinished`（"第 N 棒没有跑完，只有交代文件 / 最后输出于 HH:MM"）。
- `state.json`：只用 `stoppedReason`、`pausedUntil`。
  - `stoppedReason` 非空 → `relay_stopped`；
  - `pausedUntil` 在未来的角色 → `running` 加一条 `paused_role`（"额度暂停到 HH:MM"，不算要用户处理）。
  - **不读 `notify.sent`**：它是飞书通知的去重记录，事情办完了键也一直留着（本机现在还留着 10-23 的 `needs-user 70`），拿它当「等你处理」会永远挂着旧事。等用户的事从队列里读（下面的 `queue_user`）。
- **"可能停了"（`relay_stale`）**：同时满足以下三条时，`sources.relay.status = 'stale'`，并在 `attention` 里加一条：
  1. 最后一棒结束已超过 2 小时；
  2. 没有角色处于额度暂停中；
  3. 队列里至少一行状态以「待领」或「进行中（」开头（不判断依赖，所以文案写「可能停了」）。

**队列**
- `git -C <ixaeonRepo> show origin/main:docs/委派/队列.md`（10 秒超时，照 `runtime/projectBrief.ts` 的 git 调用）：只认 origin/main，和 relay 一致；不 fetch（relay 转的时候它自己会 fetch，共用检出和 relay-run 共用一份 refs）。
- 解析"可以领的"那张主表的序号、任务、档位、状态；状态**以「等用户」开头**的行 → `queue_user`（relay 的约定，见 `packages/relay/src/engine.ts`）。很多行的说明里提到「用户 X 月 X 日定」，不能按「含用户」认。

**项目**
- projects 表，按 `status` 分三组。

## 约束

- 只读；不新增网络访问；不新增 HTTP 接口。
- **不读** relay 的 `config.json`、`feishu.json`；`inbox.jsonl` 不读。
- `turns/` 下的任何文件都不读内容。
- 任何文件不存在或解析失败 → 对应来源记 `missing` 或 `error`，并写 note，其他部分照常；不抛错。
- 时间一律 ISO 8601；界面再换成本地时间。

## 验收条件

1. 合成 relay 目录（`lock.json` 用测试进程自己的 pid，`ledger.jsonl` 3 棒，`turns/` 下 1 到 4，其中 4 没进 ledger）→ `running` 有 `relay` 和第 4 棒，`recent` 3 条且最新在前。
2. 同上，但 `lock.json` 的 pid 不存在 → `attention` 有 `relay_down` 和 `turn_unfinished`（第 4 棒）。
3. 最后一棒结束于 3 小时前、没有额度暂停、队列有"待领" → `relay` 为 `stale`，`attention` 有 `relay_stale`；把其中一个角色的 `pausedUntil` 设在未来 → 不再 stale，`running` 出现 `paused_role`。
4. `stoppedReason` 非空 → `relay_stopped`。
5. 合成 git 仓库：origin/main 上的队列有一行状态是"待用户定"，工作区再改出一行（不推）→ 只出现 origin/main 那一行。
6. relay 目录不存在 → `relay` 为 `missing`，`queue`、`projects` 照常。
7. 合成目录里放 `config.json`、`feishu.json`（含假密钥 `SECRET-XYZ`），`turns/4/prompt.md` 写入 `PROMPT-XYZ`，`inbox.jsonl` 写入 `INBOX-XYZ` → 快照 JSON 里找不到这三个字符串。
8. projects 分组正确；IPC `getCockpitSnapshot` 返回和 `buildCockpitSnapshot` 同样的内容（`generatedAt` 除外）。
9. 队列里一行状态是「待领（用户 10-25 定的…）」、一行是「等用户：要不要做 X」→ 只有后一行进 `queue_user`。
10. `state.json` 的 `notify.sent` 里有 `needs-user 70` 键、队列里第 70 行已完成 → `attention` 里没有它。
11. ledger 里一棒 `kind` 是 `integrator-inbox`、`statusAfter` 是 `INBOX-SUMMARY-XYZ` → 快照 JSON 里找不到这个字符串，`recent` 里那一条写「处理了你在飞书里的回复」。

## 真机检查

在 `scripts/real/` 加 `cockpit-snapshot.ts`（经 `run-batch.mjs` 跑）：对本机真实的 relay 目录和 IXAEON 仓库构建快照。**只输出统计数字**：各来源的 status、running / attention / recent 的条数、projects 三组的数量，不输出任何文本内容。

## 整合方审定（2026-10-30）

对照 main（`b56516b`）和本机 relay 数据目录的实际字段（只看字段名）改准，档位 B 不变（新的本机读取：relay 数据目录、仓库里的队列）。

- **去掉 `GET /api/cockpit`，改成 IPC `getCockpitSnapshot`**：`localServer.ts` 除 `/api/health` 外一律要 Bearer 令牌，K3 用 IPC 就够，HTTP 接口现在没有调用方——零调用方的接口正是 9-17 方向纠正说的空壳。K8（MCP）真要用时再加，到时走同样的令牌。K5 的手机页在主进程里直接调 `buildCockpitSnapshot`。
- **去掉 `needs_user`（不读 `notify.sent`）**：那是通知去重记录，办完了键还在，会永远挂着旧事。
- **`queue_user` 改成状态以「等用户」开头**：照 relay 的约定；草稿的「含用户」会把一大半带说明的行都算进去。
- **飞书回复棒的 `statusBefore` / `statusAfter` 不进快照**：L16 并入后有这种棒，`statusAfter` 是整合方对用户原话的概括。补了验收第 11 条。
- **core 不 import relay**：队列主表自己解析；git 调用 10 秒超时。
- `lock.json` 确实是 `{ pid, startedAt }`，ledger 字段名都对得上；pid 判活照 relay 的 `pidAlive`（Windows 上进程号可能被别的进程复用，文案写「调度器在转（进程 N）」即可，不另做核实）。
- `relay_stale` 的第 3 条放宽成「待领」或「进行中（」开头、不看依赖，文案写「可能停了」。
- 超过 300 行就照草稿拆 K2a（relay 部分）/ K2b（队列和项目部分 + IPC）。

**用户 10-30 的决定，审定时一条没改**：驾驶舱是 IXAEON 的一个项目、走快车道；IXAEON 是唯一的项目 / 目标 / 决定记录处；手机只读、默认关闭、只开一个独立端口、经 Tailscale（不用 funnel）；这不等于解冻「多设备」；额度来源用 QuotaHub、Claude 先手动登记；不读凭据、聊天内容、会话正文；验收按「真机通过 / 用户接受」分开报。
