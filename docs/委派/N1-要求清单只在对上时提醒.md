# 规格 N1：关注方向的要求清单——只有对上了才提醒

档位：**B**（新的外发：把发现与要求交给模型判定；改变什么会主动出现在用户面前）。大小：中（≤300 行源码，超了把界面拆成 N1b）。依赖：W1b（概览页新发现）并入后再动概览页那块；迁移 34 已由整合方加好。
v2 规格：先把验收条件写成测试（`packages/core/test/acceptance/n1-*.test.ts`，界面部分放 `apps/desktop/test/acceptance/`），**先只推测试**等整合方看过并锁定，再实现。

## 要什么

用户 2026-09-20 的原话：「研究这块，发现了新的更新，然后呢？等着我去看？」他要的不是一堆发现堆在页面上，而是——**他写下几条硬要求，出了对上的才告诉他**（「内存 24GB 以上、能跑本地大模型、五千以内的手机，出了就提醒我」）。

用户在这三种方式里只选了「符合要求清单才提醒」：不要每日简报，也不要系统弹窗。

## 契约

迁移 34 已经建好两张表（**不要再加迁移**）：`research_requirements`（id / topic_id / text / sort_order / created_at）、`research_finding_matches`（finding_id / requirement_id / verdict `meets|fails|unknown` / reason / judged_at，主键是前两列）。

1. 存取放 `packages/core/src/research/requirements.ts`，从 `packages/core/src/index.ts` 导出：
   - `listRequirements(db, topicId)`、`addRequirement(db, { topicId, text })`（≤200 字，尾部追加 sort_order）、`removeRequirement(db, id)`；
   - `judgeFindings(db, provider, topicId)`：这个方向下**还没判过**的发现 × 每条要求，逐条让模型判 `meets` / `fails` / `unknown` 并给一句 ≤60 字的理由，写进 `research_finding_matches`；判过的（表里已有这对 id）跳过；没有要求时什么都不做。
     - 发给模型的只有：这条发现的标题、摘录、URL，以及要求的原话。**不发个人记忆、不发别的发现。**
     - 模型不通（没配置或调用失败）：不写库、不报错给上层流程，返回 `{ judged: 0, failed: N }`，发现照常留着。
   - `listMatchedFindings(db, { since, seenAt })`：返回「对上了」的发现（含所属方向、对上的要求与理由）；**对上了 = 这个方向至少有一条要求，且它的每条要求都判成 `meets`**；按 `fetched_at` 倒序，最多 20 条；`isNew` = `fetched_at` 晚于 `seenAt`。
2. 定时轮次与「立即检查」产生新发现之后，调用 `judgeFindings`（同一次调用里，判定失败不影响发现入库，也不让这次检查算失败）。
3. IPC：`listResearchRequirements(topicId)`、`addResearchRequirement({ topicId, text })`、`removeResearchRequirement(id)`、`listMatchedFindings()`、`markMatchedFindingsSeen()`（写 `app_settings` 的 `overview.matched_seen_at`）。
4. 界面：
   - 研究页每个方向下面一块「你的要求」：一行一条，可删；输入框 + 「加一条」；没有要求时提示「没有要求就不会提醒你，只会在页面上列发现」。
   - 概览页顶部加块 `overview-matched-findings`「符合你要求的新发现」：每条显示标题（点开走系统浏览器）、所属方向、**对上的每条要求与模型给的理由**、时间；新的带「新」标记；「都看过了」调 `markMatchedFindingsSeen` 后刷新。一条都没有时整块不显示。W1b 的「最近的新发现」留在它下面。
   - 侧栏「研究」右边显示未看的对上条数（`nav-research-badge`），0 不显示。

## 约束

- 不加迁移；不改抓取、打分、定时那几块；判定只发标题 / 摘录 / URL / 要求原话。
- 判过不重判（模型额度有限）；要求改了之后，新加的要求会对老发现重新判一次（表里没有这对 id）。
- 「对上了」的判定不许放宽成「至少一条 meets」——用户要的是全部对上。

## 验收条件

1. 一个方向两条要求、三条发现：假模型把发现 A 判成两条都 `meets`、B 判成一 `meets` 一 `fails`、C 判成一 `meets` 一 `unknown` → `listMatchedFindings` 只返回 A。
2. 没有要求的方向：`judgeFindings` 不调用模型、不写库；它的发现不会出现在「符合你要求的」里。
3. 判过不重判：再调一次 `judgeFindings`，模型调用次数为 0；新加一条要求后再调，只对这条新要求判（调用次数 = 发现数）。
4. 发给模型的内容只含标题、摘录、URL、要求原话（用假模型截请求核对），不含个人记忆里的任何一条。
5. 模型不通：`judgeFindings` 返回 `failed > 0`、不抛错；这次检查照常算成功，发现照常入库。
6. `isNew`：从没看过时全是新；`markMatchedFindingsSeen` 之后旧的不是新；之后新来的对上发现又是新。
7. 界面：概览页有对上的发现时显示这一块，每条列出对上的要求与理由；没有时整块不出现；点「都看过了」调 IPC 并刷新；侧栏角标显示未看条数，0 不显示。
8. 研究页能加、能删要求；加超过 200 字的报错不写库。
