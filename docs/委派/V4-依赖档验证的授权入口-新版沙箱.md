## 要什么

编码任务做完要独立验证。带 npm 依赖的项目（验证命令写成 `ixaeon:vitest run …`）走依赖档：在 Codex 的沙箱里跑，连不了外网、只能写任务副本。核心层 D2 时写好了检查和发起授权，**桌面应用里一处都没接**，用户没地方授权；没跑成的原因原样写着英文代码（「依赖档沙箱检查未过：unauthorized，不派生，不算验证。」）。

这一单：

1. 依赖档换成新版 Codex（0.163 起）沙箱的用法——D2c、L0b 在本机验出来的配方；
2. 设置页加一块「依赖档验证」：显示授权了没有，没授权时给一个「授权」按钮；
3. 验证没跑成时把原因说成人话、告诉用户去哪儿授权；
4. 找 Codex 并成一套，取本机最新版（用户 2026-10-19 定的，执行器也跟着换）。

### D2c、L0b 验出来的（这份规格的依据）

- **要提权装一次**：`codex sandbox setup --elevated --current-user --codex-home <专用 CODEX_HOME>`，Windows 弹一次管理员确认。装的是机器级的东西（两个沙箱专用的本机账户、几条防火墙规则和过滤器；装过的不重装）。
- **装一次之后长期可用**：同一个 CODEX_HOME 不带任何提权动作连跑 10/10 成功，不弹窗，每次约 1.1 秒。
- **提权是每个 CODEX_HOME 一次**：换一个新的 CODEX_HOME 又要装。所以 IXAEON 用数据目录里**固定的**那个（`<数据目录>/codex-sandbox-home`，D2 定的，不变），不能每个任务换一个。
- **每次调用都要带 `-c windows.sandbox="elevated"`**，配置里也要有 `[windows] sandbox = "elevated"`；不带就报「Restricted read-only access requires the elevated Windows sandbox backend」。
- **提权沙箱要求能读整个盘**（配置里 `":root" = "read"`，不写就报「elevated Windows sandbox requires effective `:root` read access」）。
- 沙箱里**外网挡得住，本机端口挡不住**（连 `127.0.0.1` 上别的进程连得上）；往副本外写、经目录链接往真实依赖写都挡得住；vitest 要把 `TEMP`/`TMP` 指到副本里才跑得起来（D2 已经这么做了）。
- **没装过的 CODEX_HOME 带着提权设置去跑，Codex 会自己去拉起提权安装**：L0b 从后台会话发起时弹不出来，等了 120 秒以 `ShellExecuteExW … 1223` 失败；在用户桌面上的应用里发起，**就会真弹窗**。所以「没装过就不许派生」要靠 IXAEON 自己的检查守住（契约 3.6）。
- 旧的检查口径（`cap_sid` 三类、版本配对的 helper、setup 标记、服务 RUNNING）对新版不准：本机这几样都在，新版照样要提权（D2c）。
- `codex sandbox --help` 里**不列** `setup` 这个子命令，但它认（L0b 实测）；不带 `--elevated` 时只报「`codex sandbox setup` currently requires --elevated」、不动机器。

### 找 Codex 的两套办法（旧版查到的，仍然成立）

`%LOCALAPPDATA%\OpenAI\Codex\bin\` 顶层的 `codex.exe` 是 5 月的 0.130；Codex 桌面应用自己更新的 0.163 在带哈希的子目录里。执行器（`resolveCodexLocator`）先看 `IXAEON_CODEX_EXE`、再看顶层；沙箱检查（`locateCodexExecutable`）不看环境变量，按目录名顺序取第一个（不一定最新）。授权和版本配对，两套找到的不是同一个，授权了也会判成没授权。

## 契约（接口写死，不改名、不加字段）

1. **类型**（`packages/contracts/src/entities.ts`）：

   ```ts
   /** V4：依赖档验证用的 Codex 沙箱，这台机器授权了没有。 */
   export interface VerifySandboxView {
     /** ok = 授权了，依赖档验证跑得了；其余三种跑不了。 */
     status: 'ok' | 'unauthorized' | 'codex_missing' | 'unsupported_platform';
     /** 用的是哪个版本的 Codex 命令行（`codex --version` 里的版本号，比如 0.163.0-alpha.10.2）；没找到 Codex 是 null。 */
     codexVersion: string | null;
   }
   ```

2. **两个新接口**（`packages/contracts/src/ipc.ts`、`apps/desktop/src/main/ipc.ts`、`apps/desktop/src/preload/index.ts` 三处；业务逻辑放在 `AppRuntime` 上的同名方法，IPC 只转一下）：

   ```ts
   /** 只查：不弹窗、不写任何文件、不记审计。 */
   getVerifySandbox(): Promise<VerifySandboxView>;
   /** 发起一次授权（Windows 会弹一次管理员确认），等它结束再查一遍，返回查到的。 */
   authorizeVerifySandbox(): Promise<VerifySandboxView>;
   ```

   - 两个都用应用的数据目录（`AppRuntime.dataDir`）。
   - `authorizeVerifySandbox`：调一次 `requestSandboxAuth(dataDir)`，不管它说成没成，接着 `checkSandboxAuth(dataDir)`，返回后者的结果。记一条审计 `verify_sandbox.authorize`，内容 `{ status }`（查到的那个状态，四选一）。
   - **只有设置页那个按钮会调 `authorizeVerifySandbox`。** 应用启动、打开设置页、派任务、跑验证，都不许调 `requestSandboxAuth`（无人值守时绝不弹窗，D2 定的）。

3. **核心层**（`packages/core/src/execution/verifySandbox.ts`、`executor.ts`、`index.ts`）：

   1. **找 Codex 只有一套办法，取最新版**：
      - `IXAEON_CODEX_EXE` 设了：就用它，不问别的候选；设成 `none`：当没有 Codex（沙箱这边是 `codex_missing`，执行器用替身）。
      - 没设：`<LOCALAPPDATA>\OpenAI\Codex\bin\codex.exe` 和 `bin` 下每个子目录里的 `codex.exe` 都是候选；每个问一遍 `--version`，取版本号最大的（`主.次.补` 逐段按数字比，照 `scripts/codex-review.mjs` 的 `findCodex`）；问不出版本号的不算。一个都没有：当没有 Codex。
      - 导出 `findLatestCodex(): Promise<{ exe: string; version: string | null } | null>`（在 `verifySandbox.ts`，经 `packages/core/src/index.ts` 导出，连同 `checkSandboxAuth`、`requestSandboxAuth`）。`version` 只有在「用 `IXAEON_CODEX_EXE` 指定了、又问不出版本号」时是 null；这时沙箱这边是 `unauthorized`（它在，只是配不上授权）。
      - 执行器（`resolveCodexLocator`）、`checkSandboxAuth`、`requestSandboxAuth`、依赖档派生用的 `codex.exe`，都用这个办法找到的。
      - 时机：执行器**只在应用启动时找一次**（`createCodingExecutor`），记下结果，`AppRuntime.codexLocator` 返回同一个结果，`codingDispatch` 判断有没有 Codex 时用记下的，不重新问。沙箱这边（检查、发起授权、依赖档派生）**每次重新找**——Codex 升级了要看得出来。
      - 这样一来编码任务改由本机最新版执行（这台机器上从 0.130 换到 0.163）。执行器传给 `codex exec` 的参数新版还认不认，由真机检查第 4 步核对。
      - `checkSandboxAuth(dataDir, { codexExe })` 这个测试接缝留着：传了 `codexExe` 就用它、不去找（D2 锁定的测试在用）；`{ platform }` 也留着。
   2. **不卡住窗口**：`verifySandbox.ts` 里不许用 `spawnSync`（这几个函数跑在 Electron 主进程里，发起授权要等用户点完确认框）。一律异步子进程。超时：问版本 20 秒，`setup` 120 秒，授权后试跑 60 秒。函数名、参数、返回类型不变。
   3. **专用 CODEX_HOME 的配置**（`ensureSandboxProfileConfig`，名字、参数不变；每次派生前重写，副本换了跟着换）写成这样（`<副本>`、`<依赖>` 用正斜杠；依赖每个一行）：

      ```toml
      [permissions.ixaeon]
      [permissions.ixaeon.workspace_roots]
      "<副本>" = true
      [permissions.ixaeon.filesystem]
      ":root" = "read"
      "<副本>/**" = "write"
      "<依赖>/**" = "read"
      [permissions.ixaeon.network]
      enabled = false
      [shell_environment_policy]
      inherit = "all"

      [windows]
      sandbox = "elevated"
      ```

      和旧版比：加了 `":root" = "read"` 和 `[windows]` 那一段；去掉了 `[permissions.default_permissions]`（调用时 `--permission-profile` 已经点名，L0b 的配方里也没有）。

   4. **依赖档派生**（`executor.ts` 的 `checkDependencyTier`）的参数，逐个照写：

      ```
      <codex.exe> -c windows.sandbox="elevated" sandbox --permission-profile ixaeon -C <副本> -- <node> <副本>/node_modules/vitest/vitest.mjs run --config-loader runner --no-cache <命令参数…>
      ```

      即 argv 是 `['-c', 'windows.sandbox="elevated"', 'sandbox', '--permission-profile', 'ixaeon', '-C', 副本, '--', node, vitest.mjs, 'run', '--config-loader', 'runner', '--no-cache', ...命令参数]`。环境照旧（白名单、`CODEX_HOME` = 专用目录、`TEMP`/`TMP` = 副本里的临时目录）。`<codex.exe>` 是 3.1 找到的那个；派生之前找不到了（授权检查之后 Codex 被卸了）：不派生，照 `codex_missing` 那句话回（3.7），`ran` 是 false。

   5. **发起授权**（`requestSandboxAuth(dataDir)`，只该由设置页的按钮调）：
      1. 找 Codex（3.1）：没有 → `{ ok: false, reason: 'codex_missing' }`；不是 Windows → `unsupported_platform`；问不出版本号 → `unauthorized`。三种都不起任何子进程去装。
      2. 建 `<专用 HOME>/auth-probe`（空目录；`-C` 绝不用系统临时目录，D2 复审定的），按 3.3 写配置（副本 = `auth-probe`，没有依赖）。
      3. 装：`<codex.exe> sandbox setup --elevated --current-user --codex-home <专用 HOME>`，环境白名单加 `CODEX_HOME=<专用 HOME>`。退出码不是 0 → `unauthorized`，到此为止。
      4. 试跑：`<codex.exe> -c windows.sandbox="elevated" sandbox --permission-profile ixaeon -C <auth-probe> -- cmd /c echo ixaeon-sandbox-auth-ok`，同样的环境。退出码不是 0，或者输出里没有 `ixaeon-sandbox-auth-ok` → `unauthorized`，到此为止。
      5. 两步都成了：写授权记录 `<专用 HOME>/ixaeon-sandbox-auth.json`，内容 `{"codexVersion":"<版本>"}`（第 1 步问到的版本），返回 `{ ok: true }`。
   6. **检查口径**（`checkSandboxAuth`，换掉旧的四样）：
      - 不是 Windows → `unsupported_platform`；找不到 Codex → `codex_missing`；问不出版本号 → `unauthorized`。
      - 授权记录在、能解析、里面的 `codexVersion` 和现在找到的 Codex 版本**完全一样**，并且 `<专用 HOME>/.sandbox/setup_marker.json` 在 → `ok`；缺任何一样、版本不一样、记录坏了 → `unauthorized`。
      - 只读文件、只起 `codex --version` 这一个子进程：**不跑 `codex sandbox`**（没装过时它会自己拉起提权安装，见上）、不跑 `sc query`、不往数据目录写任何东西。
      - 为什么版本不一样就算没授权：Codex 升级之后新版还认不认原来那次安装，没验过；宁可让用户再点一次，也不能在后台派生时弹窗。所以 Codex 桌面应用每更新一次，要再授权一次（设置页那句话里写了）。
   7. **没跑成的原因说人话**：`checkDependencyTier` 授权检查没过时，验证输出（`verify_output`）现在是「依赖档沙箱检查未过：<英文代码>，不派生，不算验证。」，换成下面三句之一（逐字）：

      | 原因                   | 验证输出                                                                                                               |
      | ---------------------- | ---------------------------------------------------------------------------------------------------------------------- |
      | `unauthorized`         | 这台机器还没给 Codex 沙箱授权，依赖档验证跑不了：到设置页「依赖档验证」点「授权」。授权之后新派的任务才会跑这一档验证。 |
      | `codex_missing`        | 没找到 Codex 命令行，依赖档验证跑不了（这一档要用 Codex 的沙箱）。                                                     |
      | `unsupported_platform` | 依赖档验证只在 Windows 上跑得了。                                                                                      |

      回报里那一行照旧是「验证没跑：<验证输出>」（`taskReport.ts` 的 `verifyLine` 不改），任务卡片照旧显示验证输出。这几句会随回报进对话、再随对话历史发给模型。

   D2 定下的别的都不动：`-C` 用副本、派生环境走白名单、零依赖档整个不碰。`locateCodexExecutable` 没人用了就删掉。

4. **界面**（`apps/desktop/src/renderer/src/pages/Settings.tsx`）：

   - 「编码任务交给谁」那一块后面加一块「依赖档验证（Codex 沙箱）」（`testId="settings-verify-sandbox"`）。
   - 打开设置页时调一次 `getVerifySandbox`（不定时刷新）。没拿到结果之前这一块显示「正在查……」。
   - 状态那句话（`data-testid="settings-verify-sandbox-status"`），按 `status` 四选一（逐字；`<版本>` 是 `codexVersion`）：

     | status                 | 显示                                                                                                                           |
     | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
     | `ok`                   | 已授权（Codex <版本>）。带 npm 依赖的项目，验收测试在 Codex 的沙箱里跑：连不了外网，只能写任务副本。                           |
     | `unauthorized`         | 还没授权（Codex <版本>）。带 npm 依赖的项目，验收测试现在跑不了。授权一次就行；Codex 更新之后要再授权一次。                     |
     | `codex_missing`        | 没找到 Codex 命令行，依赖档验证跑不了。                                                                                        |
     | `unsupported_platform` | 依赖档验证只在 Windows 上跑得了。                                                                                              |

     `unauthorized` 而 `codexVersion` 是 null（指定的 Codex 问不出版本号）：「还没授权（Codex 版本不明）。」接后面同一句。

   - 只有 `unauthorized` 时显示按钮「授权」（`testId="settings-verify-sandbox-authorize"`）。
   - 点了先用 `window.confirm` 问（逐字）：

     ```
     给 Codex 沙箱授权？

     Windows 会弹一次管理员确认。同意之后，Codex 会在这台机器上装好它的沙箱：两个专用的本机账户和几条防火墙规则（已经装过的不重装）。之后跑依赖档验证不用再问。

     只有点这个按钮才会弹；任务在后台跑的时候绝不弹。Codex 更新之后要再点一次。
     ```

   - 取消：什么都不发生。
   - 确认：按钮变成不可点、文字是「授权中……（等 Windows 的确认）」；调 `authorizeVerifySandbox`；拿到结果后，状态那句话按新结果换掉，并显示一句（`data-testid="settings-verify-sandbox-message"`）：结果是 `ok` →「授权好了。」；其余 →「没授权成：可能是 Windows 的确认被取消了，也可能是 Codex 的沙箱没装好。可以再点一次。」
   - 出错（两个接口抛错）：显示在这一页现有的报错条里。

## 约束

- 不加迁移。不删数据。不跑 `codex sandbox uninstall`。
- 测试里**绝不真的调 `requestSandboxAuth` 去装**（会在跑测试的机器上弹窗），子进程一律用替身。真的发起授权只有用户自己点。
- 真机检查**不许点「授权」、不许跑 `codex sandbox setup --elevated`**。
- 执行器只换「用哪个 codex.exe」（3.1），别的不改；不改零依赖档。
- 测试、交付说明里的路径用合成的；版本号用合成的（比如 `9.9.9`）。
- **已经锁定的测试，这一单会撞红的**（D2 的 `d2-sandbox-tier.test.ts` 钉着旧 argv；V4 旧版锁的 `packages/core/test/acceptance/v4-*.test.ts`、`apps/desktop/test/acceptance/v4-*.test.ts` 钉着旧的四样检查和旧文案）：**你不改它们**。新条件写进新的测试文件（`v4-new-*.test.ts`、`v4b-*.test.ts`），在交付说明里列出旧的哪几条红了、为什么；整合方审测试时一起改旧的、重锁。

## 已知的风险（写进交付说明，不用这一单解决）

- 沙箱里能读整个盘（提权沙箱的要求），能连本机端口。依赖档跑的是编码任务在用户自己项目里写的测试；「连不了外网、写不出副本」成立，「读不到别处」「碰不到本机服务」不成立。设置页只说前两样。
- 授权后试跑那一步要是撞上「装了一半」，Codex 可能再弹一次确认——这时用户就在电脑前，可以接受。

## 验收条件

核心层（`packages/core/test/acceptance/`，`V4` 那一支）：

1. **找 Codex 只有一套，取最新版**：合成的 `LOCALAPPDATA` 下，顶层一个 `codex.exe`、两个子目录各一个，问版本时（子进程替身）分别说 `0.10.0`、`0.9.0`、`0.11.0`：找到的是 `0.11.0` 那个（按数字比，`0.11` 比 `0.9` 大）；再加一个问不出版本号的，不算它；顶层没有、只有子目录里有，照样找得到；一个都没有是 null。`IXAEON_CODEX_EXE` 指向一个文件：用它，别的候选一个都不问；指定的问不出版本号：返回 `{ exe, version: null }`，`checkSandboxAuth` 是 `unauthorized`；设成 `none`：null。执行器 `resolveCodexLocator`、`checkSandboxAuth`、`requestSandboxAuth`、依赖档派生找到的是同一个文件。执行器在应用启动时找一次，之后判断有没有 Codex 不再问版本。
2. **不卡住窗口**：`checkSandboxAuth`、`requestSandboxAuth` 跑的时候 `node:child_process` 的 `spawnSync` 一次都没被调（换成一调就抛错的替身；异步子进程换成按脚本回话的替身，`spawn`、`execFile`、`exec` 及其 `promisify` 写法都要接上——旧版锁定时踩过）。
3. **检查口径**：授权记录在、版本一样、setup 标记在 → `ok`；缺记录、记录坏了、版本不一样（记录 `9.9.8`、现在 `9.9.9`）、缺 setup 标记，各是 `unauthorized`；问不出版本号是 `unauthorized`；不是 Windows 是 `unsupported_platform`。整个检查只起过 `--version` 一种子进程（没有带 `sandbox` 的、没有 `sc` 的），数据目录里的文件前后一样（`ok` 和 `unauthorized` 两种都核对，检查要一路走到底）。旧的那四样（`cap_sid`、helper、setup 标记、服务）都摆好、但没有授权记录：`unauthorized`。
4. **发起授权**（子进程全是替身）：先起 `setup`，参数正好是 `['sandbox', 'setup', '--elevated', '--current-user', '--codex-home', <专用 HOME>]`；再起试跑，参数正好是契约 3.5 第 4 步那一串，`-C` 是 `<专用 HOME>/auth-probe`；两次的环境里 `CODEX_HOME` 是专用 HOME。两步都成 → `{ ok: true }`，授权记录写了、版本对；`setup` 退出非 0 → `unauthorized`、没起试跑、没写记录；试跑退出非 0、或输出里没有那串标记 → `unauthorized`、没写记录；没有 Codex / 不是 Windows / 问不出版本 → 一个装的子进程都没起。之后 `checkSandboxAuth` 是 `ok`（把 setup 标记也摆上，模拟 Codex 装好时会写它）。
5. **依赖档派生**：授权过了，派生的 argv 正好是契约 3.4 那一串（`-C` 和 `cwd` 是副本、命令参数原样在最后），`codex.exe` 是最新版那个；派生时专用 HOME 里的 `config.toml` 有契约 3.3 的每一条（`":root" = "read"`、副本写、依赖读、`enabled = false`、`[windows]` 里 `sandbox = "elevated"`），写权限只有副本一条，没有 `default_permissions`。
6. **没跑成的原因**：三种授权没过的情况，验证输出是契约 3.7 表里那一句（逐字），`ran` 是 false，没派生任何子进程去跑测试；回报里那一行是「验证没跑：」接这一句。

桌面（`apps/desktop/test/acceptance/`，`V4b` 那一支）：

7. **只查不弹**：`AppRuntime.getVerifySandbox()` 返回 `{ status, codexVersion }`，四种状态各一条；没调 `requestSandboxAuth`，没记审计，数据目录里没多出文件。
8. **发起授权**：`AppRuntime.authorizeVerifySandbox()` 调了一次 `requestSandboxAuth`（参数是数据目录），之后调了 `checkSandboxAuth`，返回后者的结果；`requestSandboxAuth` 说成了、再查却是 `unauthorized` 时，返回 `unauthorized`。审计 `verify_sandbox.authorize` 一条，内容 `{ status }`。
9. **别处不弹**：应用里除了 `authorizeVerifySandbox`，没有别的路径调 `requestSandboxAuth`：起应用、打开设置页、派一个依赖档的任务、跑完验证，`requestSandboxAuth` 一次都没被调，也没有任何子进程的参数里带 `setup`。
10. **IPC**：`registerIpc` 注册了 `getVerifySandbox`、`authorizeVerifySandbox`，调它们得到的和 `AppRuntime` 上的方法一样（给两个方法各顶一个独有的返回值核对，不数调用次数）。
11. **设置页**：打开时调了一次 `getVerifySandbox`；没拿到结果之前显示「正在查……」；那一块排在「编码任务交给谁」后面；四种状态各显示契约 4 的那句话（逐字，带版本号），外加「版本不明」那一句；只有 `unauthorized` 有「授权」按钮。
12. **设置页，点「授权」**：确认框文字逐字；取消不调 `authorizeVerifySandbox`；确认之后调了一次，等结果的时候按钮不可点、文字是「授权中……（等 Windows 的确认）」；结果是 `ok` → 状态换成「已授权」那句、显示「授权好了。」、按钮没了；结果是 `unauthorized` → 显示「没授权成」那句、按钮还在；出错显示在报错条里。
