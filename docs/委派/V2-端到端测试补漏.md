2. **端口守卫**：端到端测试启动前照 C3 的 `apps/desktop/test/review/ui-port-guard.ts` 做同样的检查，端口被占就明确提示「先关掉正在运行的 IXAEON」，而不是跑出一堆含糊的失败。
3. **剩下的逐项定位**，每项归到下面一类，写进交付说明：

## 整合方判定（2026-09-30）：没有真回归，接着做完

执行方停下来交整合方是对的（拿不准就停）。它记下的证据本身已经指明了原因：两个应用实例的父进程是**两个不同的** Playwright 进程（ppid 35496 与 22084）。

- **smoke 设置页 / MCP 握手 / MCP 端点三项（原表第 4–6 项）是连锁失败，属于「测试本身的问题」**：
  - 总览那条过时断言一挂，Playwright 就丢掉这个 worker、另开一个（`playwright.config.ts` 里 `workers: 1`、`retries: 0`，失败后照常换 worker）；
  - 旧 worker 退出前跑 `afterAll`，里面的 `app.close()` 把应用正常关掉、数据目录删掉——这就是「进程树整体消失、没有崩溃日志」；
  - 新 worker 重跑 `beforeAll`，建新的临时数据目录再启动，于是停在首次设置向导；
  - 后面的测试都默认第一条已经走完向导，于是跟着挂。
  - 修法：这类前后依赖的套件加 `test.describe.configure({ mode: 'serial' })`（前面一条挂了，后面的直接跳过，不在新实例上乱跑），再修掉触发它的过时断言。
- **m2-ui S1、S2（原表第 7、8 项）是断言过时**：E6（83af882，2026-09-18，用户说「不想导入一份资料就逐句审核」）把待讨论页改成只放冲突、你要求继续待处理的、编码代理报回的结果，普通提取的条目只显示条数。S1（不采纳）、S2（确认）的条目不是冲突，按 E6 本来就不该出现在待讨论页。确认 / 不采纳的入口在理解页（`Understanding.tsx`：AI 说的显示「采纳」，其余显示「确认正确」，都有「不采纳」）。改成在理解页操作，其余断言（落库状态、简报前后变化）不动。冲突类场景（S4）照旧在待讨论页，已经通过。
- 原表第 1–3 项的归类（W1b / E1 重写总览、D3 第 1 条自动开工）照执行方写的。

接下来照规格步骤做完：改三类过时断言、给前后依赖的套件加 serial、步骤 2 端口守卫、步骤 4 接进 CI。四个诊断脚本（`scripts/real/v2-*.mjs`）不用合并，原因已经查明。
