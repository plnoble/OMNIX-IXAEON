# 规格 D2：编码任务的独立验证按档位进沙箱，真实项目的测试也能跑

档位：**B**（验证的安全边界；验证第一次用上外部工具 Codex CLI 的沙箱；涉及一次系统授权）。大小：中（≤300 行源码，超了把「依赖档」拆出去）。依赖：V1（验证命令不再拉起新窗口，须先并入）。来源：[D2 沙箱实验](交付/D2-沙箱实验.md)、[D2b 沙箱实验](交付/D2b-沙箱实验.md)（调研 agent 2026-09-29、09-30），整合方定稿。
v2 规格：先把验收条件写成测试（`packages/core/test/acceptance/d2-*.test.ts`），**先只推测试**等整合方看过并锁定，再实现。

## 要什么

场景一的「独立验收」要能跑真实项目的测试。现在验证（`CodingOrchestrator.verify` → `defaultCheck`）只能在 Node 权限模型里跑纯 Node 测试，项目副本里又没有依赖目录，TypeScript + vitest 这类项目（IXAEON 自己就是）跑不起来。

两轮实验的结论（整合方已定）：

- **否决**「Node 权限模型 + 把依赖目录链接进副本」：跑 vitest 要允许起子进程（子进程完全不受限）、网络不受管、真实依赖能被写穿——等于裸跑，违反「验证不裸跑」。
- **零依赖档**：`node:test` + 可剥离的 TS 写法 + 显式 `.ts` 导入 + 不用 npm 依赖，在现有 Node 权限模型里直跑就行（D2 实验 E4）。
- **依赖档**：用 Codex CLI 自带的 Windows 提权沙箱。专用 CODEX_HOME 授权一次之后连续 10/10 无人值守；依赖目录链接进副本后读得到、写不穿（操作系统权限直接拒）；联网与往副本外写都被挡；vitest 能跑通（D2b）。

## 契约

1. **三档**，档位由 IXAEON 按命令形状判断，命令自带的权限参数一律剥离（验证器不能自己扩权）：
   - **零依赖档**：`[node, <测试文件>.ts]` → 照现在的 `defaultCheck` 在 Node 权限模型里直跑（读写都限在副本内）。
   - **依赖档**：`['ixaeon:vitest', 'run', …<测试文件>]`（IXAEON 认的固定写法，不是可执行程序）→ 走下面第 2–4 条。
   - **拒绝档**：其他一律不跑（`ran=false`，现状不变）。
2. **依赖档的副本**：`copyProjectWorkspace` 跳过的每个 `node_modules`，在副本里同一相对位置建目录链接（Windows junction）指回项目里真实的那个；副本根放一个空的 `pnpm-workspace.yaml`，挡住 vite 往上级目录探测。
3. **依赖档的沙箱**：
   - 专用 CODEX_HOME 放在 IXAEON 数据目录下（`<数据目录>/codex-sandbox-home`，不放系统临时目录），里面的 `config.toml` 由 IXAEON 生成：一个权限档案，副本子树可写、真实依赖目录只读、`network.enabled = false`，并设为默认档案（写法照 D2b §3 的配方）。换任务时改档案里的路径，不需要重新授权。
   - 跑法：`codex sandbox windows --permissions-profile <档案> -c windows.sandbox="elevated" -C <副本> -- <node> <副本>/node_modules/vitest/vitest.mjs run --config-loader runner …`，vitest 的缓存目录与 `TMP` / `TEMP` 都指到副本内（D2b §4.5 的三个必要条件）。
   - 超时照现在的验证超时；取消照现在的做法杀掉进程树。
4. **跑之前先查，绝不弹窗**：依赖档每次跑之前做被动检查（照 `scripts/real/d2b-e3-auth-check.mjs` 的做法：只读文件与服务状态）。缺什么就不跑，验证结果记成「没跑成」而不是「没通过」，原因分开：
   - `unauthorized`：这台机器的专用沙箱还没授权（需要用户点一次系统授权）；
   - `codex_missing`：找不到 Codex CLI；
   - `unsupported_platform`：不是 Windows。
     无人值守的验证**不得**触发授权弹窗；授权只由用户主动点的入口触发（入口与界面文案是 D6，本单只提供核心层的「检查」与「发起授权」两个函数，不接界面）。
5. 验证结果：「没跑成」（上面三种原因，`verify_status = 'not_run'`，原因写进验证输出）与「跑了没通过」（`failed`）分开记录；D3 的回报照这个区分写（没跑成写原因，不写「验证失败」）。

## 约束

- 零依赖档、拒绝档的现有行为与测试不变；V1 的 `ELECTRON_RUN_AS_NODE` 处理对两档都适用。
- 不加迁移（`verify_status`、`verify_output` 已有；原因写在输出里）。
- 不改 D5（验收测试先行）的范围：本单只让验证「能在沙箱里跑真实项目的测试」，谁来写测试、什么时候锁定不在这里。

## 验收条件

1. 零依赖档：合成的 TS 项目（node:test，可剥离写法）在副本里经 `defaultCheck` 跑：通过例退出 0、`verify_status = passed`；故意失败的例子退出非 0、`failed`。
2. 依赖档的副本：合成项目（根目录与一个子包各有 `node_modules`）准备副本后，两处都是指回真实目录的链接，副本根有空的 `pnpm-workspace.yaml`。
3. 依赖档的命令：已授权（检查函数替身返回已授权）时，实际派生的命令与参数正好是第 3 条的形状（档案名、提权、`-C` 副本、`--config-loader runner`），环境里的 `TMP` / `TEMP` 指到副本内；沙箱替身返回 0 / 非 0 分别记成 `passed` / `failed`。
4. 没授权：不派生任何 codex 进程（替身调用 0 次），`verify_status = not_run`、原因 `unauthorized`。
5. 找不到 Codex、不是 Windows：同第 4 条，原因分别是 `codex_missing`、`unsupported_platform`。
6. 命令自带的权限参数、`ixaeon:vitest` 以外的程序：照旧剥离或拒绝（现有相关测试照过）。
7. 专用 CODEX_HOME 在数据目录下，生成的 `config.toml` 里网络关闭、真实依赖目录只读、副本可写。

## 真机检查

用户的机器上，合成的 TS + vitest 小项目（临时目录）：

1. 第一次跑依赖档：检查报「没授权」，验证记成没跑成、没有弹窗；
2. 调用核心层的「发起授权」（会弹一次系统授权，**事先告诉用户、请用户点「是」**）；
3. 再跑：通过例 `passed`、失败例 `failed`；再试一次经链接往真实 `node_modules` 写，被拦、真实目录不变。
   原样输出贴进交付说明，脚本放 `scripts/real/d2-*.ts`。

## 整合方审测试时的改正与补充（2026-09-30，锁定前）

执行方先推的测试把契约 2 读成了「每份副本一复制好就带链接」。那样真实依赖目录会暴露给执行器阶段和零依赖档：零依赖档靠 Node 权限模型，它判写权限看的是链接所在的路径，会顺着链接写穿真实依赖（D2 实验 E1 已实测），这正是本单否决的那条路。改正与补充如下（原来的验收条件一条没删）：

1. **链接只在依赖档跑的那段时间存在**（改正契约 2 与条件 2）：
   - `copyProjectWorkspace` 本身不建链接，也不放 `pnpm-workspace.yaml`；
   - 依赖档派生之前，在副本里为项目中每个 `node_modules`（复制时跳过的那些，按项目当前的样子找）建目录链接指回真实目录；副本根没有 `pnpm-workspace.yaml` 就放一个空的，有就原样保留；
   - 跑完（通过、没通过、派生出错、取消都算）拆掉本次加进副本的一切：链接、空文件、临时目录、缓存目录。副本和跑之前一模一样，真实依赖目录里的东西一个不少。不拆干净的话，验证后的范围核对（A05）会把这些当成「验证程序改了批准范围外的文件」。
2. **零依赖档：副本里有任何链接就不跑**（新增条件 8），目录链接、符号链接都算，藏在子目录里也算；`ran=false`，原因写明。执行器自己建的链接、项目里本来就有的链接都在内，理由同上。
3. **依赖档的上下文**（新增条件 11）：编排层验证时把项目根目录与数据目录交给验证——`runCheck` 的第 4 个参数，再到 `defaultCheck` 的第 6 个参数 `{ projectRoot, dataDir, checkAuth?, spawnCommand? }`。`checkAuth`、`spawnCommand` 只给测试替换，生产用默认值。`defaultCheck` 已有的第 4、5 个参数（V1 锁定）不动。
4. **核心层两个函数**放 `packages/core/src/execution/verifySandbox.ts`：
   - `checkSandboxAuth(dataDir, env?)`：被动检查，只读，不写文件、不弹窗；`env` 可替换平台与 Codex 路径，供测试用；
   - `requestSandboxAuth(dataDir)`：发起授权，会弹一次 UAC；测试里不调用。
5. **派生的环境**（新增条件 9）：
   - 照现有白名单，白名单外的环境变量带不进去；
   - 另加 `CODEX_HOME=<数据目录>/codex-sandbox-home`，`TMP`/`TEMP` 指到副本内已建好的目录；
   - 在应用（Electron）里跑时加 `ELECTRON_RUN_AS_NODE=1`（和 V1 同一判定，套在沙箱里真正跑的那个 node 上）；
   - 生成的 `config.toml` 写 `[shell_environment_policy] inherit = "all"`，让沙箱把这些原样传进去（D2b §4.5）；
   - `write` 条目只许有副本，换任务时档案里的路径跟着换成新副本。
6. **第四种「没跑成」，以及子命令限制**（新增条件 10）：
   - 真实项目根目录没有 `node_modules/vitest/vitest.mjs` → 原因 `vitest_missing`，不当成「跑了没通过」；
   - `ixaeon:vitest` 第二段不是 `run`（`watch` 之类）一律拒绝。
7. **取消与超时**（新增条件 12）：外面的取消信号要传到派生，`spawnCommand` 收到的 `signal` 跟着取消；超时 60 秒，和现有验证相同。
8. vitest 的缓存目录怎么指到副本内（命令行参数、环境变量……）由实现方试出来。验收看结果：真机检查里用 `vitest.config.ts`（TS 写法）、不设 `cacheDir` 的项目，跑完真实依赖目录里不许多出任何东西。
9. **已知限制**（不在本单解决，交付说明和真机检查里如实写）：pnpm 等工作区的内部包经链接解析到真实项目，不是副本里改过的那份；依赖档验证的是「副本里的文件 + 真实依赖」。

### 新增验收条件

8. 零依赖档：副本里有目录链接（放在子目录里也算）就不跑，`ran=false`，输出写明「链接」；链接那头的目录里没多出任何东西。
9. 依赖档派生的环境：
   - `CODEX_HOME` 是 `<数据目录>/codex-sandbox-home`；
   - `TMP`/`TEMP` 在副本内，且目录已建好；
   - 白名单外的环境变量带不进去；
   - Electron 下有 `ELECTRON_RUN_AS_NODE=1`，普通 node 下没有；
   - 生成的 `config.toml` 有 `inherit = "all"`，`write` 条目只有副本，换副本后跟着换。
10. 项目根目录没装 vitest → `vitest_missing`、不派生；`ixaeon:vitest watch` 拒绝、不派生。
11. 生产路径：
    - 编排层把项目根目录与数据目录交给验证；
    - 什么都不替换，在从没授权过的新数据目录上跑依赖档任务：`verify_status = not_run`，原因是 `unauthorized`（装了 Codex）或 `codex_missing`（没装）；任务停在待接受，没有派生沙箱；
    - `checkSandboxAuth` 对非 Windows、找不到 Codex、没授权分别给出三种原因，且不往数据目录写任何东西。
12. 取消：外面一取消，派生收到的信号跟着取消；超时 60 秒。

### 真机检查补充（原来三条之外）

4. 合成项目用 `vitest.config.ts`、不设 `cacheDir`，根目录和一个子包各有 `node_modules`：通过例 `passed`；跑完真实 `node_modules` 的目录项与内容不变（没有 `.vite`、`.vite-temp`），副本里没有链接、没有多出的文件。
5. 用 Electron 可执行文件当 node（`ELECTRON_RUN_AS_NODE=1`，模拟应用里）两档各跑一次通过例。
6. 取消：跑一个一直等待的测试，中途取消，确认没有残留进程。
7. 记下真实 `node_modules` 的权限（`icacls`）在跑之前和跑之后有没有变化，原样贴出。
8. 跑依赖档测试时如果弹出 UAC，说明检查函数错放行了：请用户点「否」，按失败处理。

## 整合方复审第一轮（2026-10-01）：退回修改

整合方逐行看过 `executor.ts` 与 `verifySandbox.ts` 的改动。结构是对的：检查不过就不派生，链接在 `finally` 里拆，零依赖档的链接守卫也对。合并前要改下面几处：

1. **CI 会红**：依赖档在授权检查之后又调了一次 `locateCodexExecutable()`，找不到就返回 `codex_missing`，不会走到替身派生。
   - 执行方本机装了 Codex，所以 31/31；CI 机器上没有 Codex，D2 一标完成，`d2-copy-junction`、`d2-sandbox-tier` 里靠替身派生的测试就会挂。整合方把 `LOCALAPPDATA` 指到空目录复现：13 失败、18 通过。
   - 改法：授权检查通过后不再判断 Codex 在不在，生产的检查函数已经保证了它在；拿不到路径时用默认安装位置的路径（真派生时起不来，就按「派生出错」记）。
   - 改完用「`LOCALAPPDATA` 指到空目录」再跑一次四份测试，贴输出。
2. **发起授权不许碰系统临时目录**：`requestSandboxAuth` 拿 `tmpdir()`（用户的 `%TEMP%`）当 `-C` 和 `write` 条目。提权沙箱的 setup 会按配置给写入根加访问权限，而且留着（D2b 日志里的「granting write ACE … for sandbox group and capability SID」），等于给沙箱开了往用户临时目录写的口子。
   - 改成数据目录里专用的空目录，比如 `<数据目录>/codex-sandbox-home/auth-probe`；
   - 派生环境也走白名单，现在传的是整份 `process.env`。
3. **照 D2b 配方补 `workspace_roots`**：D2b 实测能用的配方里有 `[permissions.<档案>.workspace_roots] "<副本>" = true`，现在生成的配置里没有。先补上；phase2 若证明不需要，交付说明写清楚再去掉。
4. **缓存目录：加 `--no-cache`**。整合方用 vitest 4.1.11 实测：
   - `--cache.dir` 已经废弃，一用就报错退出；
   - 默认会往 `node_modules/.vite/vitest/<hash>/results.json` 写结果缓存，经链接就是写真实依赖，会被拒；
   - `--config-loader runner --no-cache` 一起用，测试照过，`node_modules` 下一个文件都不写。
   - 把 `--no-cache` 加在 `runner` 与命令参数之间（锁定测试允许产品在这里加不带路径的参数）。
5. **准备副本要稳**（`prepareDependencyCopy`）：
   - 副本里那个位置已经有东西（比如执行器自己建了 `node_modules`）时，`symlinkSync` 会抛 EEXIST，异常直接冒出去，前面建好的链接也不拆。改成发现已有就整单不跑（`ran=false`，写明「副本里已有 node_modules」），不覆盖执行器的东西；准备到一半出错，先把已经建的拆掉再返回；
   - 找 `node_modules` 时跳过和 `copyProjectWorkspace` 一样的目录（`.git`、`dist`、`build` 等，把那个集合导出来复用），不在副本里本来没有的目录下建链接；
   - `mkdirSync(recursive)` 可能一次建好几层，现在只记了最深一层，拆的时候上面几层会留下。要么每一层都记，要么上级目录不在副本里就不链；
   - `.ixaeon-tmp` 如果副本里本来就有，现在跑完会被整个删掉。先查，有就换名字或者不跑。
6. **会弹 UAC 的步骤，要等用户明确说可以**：phase2 那次是「报备了、没人应答」就跑了 `requestSandboxAuth`。以后弹窗前，等用户在对话里明确同意再跑。这次先按第 2 条改完，由整合方转告用户，用户同意后再补跑 phase2。
7. **300 行**：整合方逐行审过，这次不拆。把依赖档拆出去，要把已锁定的四份测试重新分成两单、再锁一次，比一起审的成本高。第 5 条会再加几十行，也照样不拆。
