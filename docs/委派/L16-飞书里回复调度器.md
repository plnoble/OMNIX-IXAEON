# 规格 L16：用户在飞书里回复，调度器收得到、交给整合方办

档位：**B**（新的外部连接：飞书长连接；用户在飞书里说的话发给模型；新加依赖包）。大小：中（约 220 行源码；超过 300 行就拆，L16b 放契约第 4、5、6 条）。依赖：L15。来源：用户 2026-10-24 问「我飞书的回复你可以收到么」，整合方答「现在收不到：群里的自定义机器人只能发」，用户定了「我来做自建应用」。

v2 规格：先把验收条件写成测试（`packages/relay/test/acceptance/l16-*.test.ts`），**先只推测试**，整合方锁定后再写实现。

## 要什么

1. 用户在飞书开放平台建一个**企业自建应用**（开机器人、开「接收群聊中 @ 机器人的消息」权限、事件用**长连接**收），把应用的 ID 和密钥写进 `<数据目录>/feishu-app.json`，再把机器人拉进现在收通知的那个群。
2. 调度器起一个**收听**进程（`relay listen`），用飞书官方的 Node SDK 连长连接，不需要公网地址。用户在那个群里 **@ 机器人**说的话，只要是**用户本人**说的，就记进 `<数据目录>/inbox.jsonl`，并在群里回一句「收到」。
3. 下一棒优先派给整合方：**飞书回复棒**。整合方读用户的原话，多半是在回答「等用户」的那几行，把决定写进队列（改状态、要的话写规格、加行），然后在群里回一句它做了什么。
4. 第一次用时绑定：跑 `relay listen --bind`，用户在群里 @ 机器人说一句话，调度器记下是哪个群、哪个人（`chatId`、`ownerOpenId`），以后只听这个群里这个人的。

## 契约（接口写死，不改名、不加字段）

1. **凭据文件** `<数据目录>/feishu-app.json`：`{ "appId": string, "appSecret": string, "chatId"?: string, "ownerOpenId"?: string }`。`appSecret` 不打印、不写进日志和报错（报错里出现就换成 `<已隐藏>`）。文件不在、不是 JSON、缺 `appId` / `appSecret` → 当没配，不起收听。
2. **依赖**：`packages/relay/package.json` 加飞书官方 SDK `@larksuiteoapi/node-sdk`，版本写死（不写 `^`、`~`），`pnpm-lock.yaml` 跟着更新。只用它的长连接客户端（`WSClient`）和事件分发（`EventDispatcher`），收 `im.message.receive_v1` 一种事件。不调别的接口；往群里回话照旧走 L3 的自定义机器人。
3. **认不认这条消息**：`src/notify/inbox.ts` 导出纯函数 `acceptMessage(event: unknown, app: { chatId?: string; ownerOpenId?: string }): { ok: true; id: string; text: string } | { ok: false; why: string }`。只有下面都成立才 `ok`：
   - 群聊（`chat_type` 是 `group`），`chat_id` 等于 `app.chatId`；
   - 发消息的人 `open_id` 等于 `app.ownerOpenId`；
   - 消息里 @ 了机器人（`mentions` 不空）；
   - 消息类型是 `text`。`text` 去掉 @ 的占位（`@_user_1` 这种）和首尾空白之后不空。

   `id` 是 `message_id`。不认的，`why` 写一句（不带消息内容）。
4. **`relay listen`**：
   - 连上之后打一行 `收听中`。每条事件交给 `acceptMessage`：认 → 记进 `inbox.jsonl` 一行 `{ "id", "at": <ISO>, "text" }`（同一个 `id` 已经有了就不记）→ 往群里发 `收到：<text 前 50 个字>。下一棒交给整合方。`；不认 → 打一行 `没理：<why>`，不发。
   - 带 `--bind`：`chatId` 和 `ownerOpenId` 不看，第一条群里 @ 了机器人的文字消息到了，就把它的 `chat_id` 和发消息人的 `open_id` 写进 `feishu-app.json`（别的字段原样保留），打一行 `绑好了`，往群里发 `绑好了：以后只听你在这个群里 @ 我说的话。`，退出码 0。
   - 没带 `--bind`、`chatId` 或 `ownerOpenId` 没有 → 打一行 `还没绑定：先跑 relay listen --bind`，退出码 2。
5. **看门人**：`feishu-app.json` 四个字段都有 → 看门人起一个子进程 `relay listen --under <看门人的进程号>`（从代码根起，和棒的子进程同一份代码），它退出了就隔 `idleSeconds` 再起；打一行 `收听 <进程号> 退出 <退出码>`。没配全 → 不起。`--exit-when-idle` 退出前先停掉收听。
6. **飞书回复棒**：
   - `inbox.jsonl` 里有 `id` 不在 `state.inboxDone`（`RelayState` 加可选 `inboxDone?: string[]`，只留最近 200 个）里的 → `decideNextTurn` **先于**复审派一棒：`{ role: 'integrator', kind: 'integrator-inbox', taskId: 'inbox', task: '用户在飞书里说的话', status: '<条数> 条' }`。`opts` 加 `inboxPending?: number`，由 `runOnce` 读文件算出来。整合方在歇 → 不派（等它歇完）。不算规划次数。
   - 交代（逐字一段，后面按时间先后列原话，再接普通棒的 `ASK`、停点、最后一行）：

     > 你是整合方（统筹）。这一棒是飞书回复棒：用户在飞书里给调度器发了下面这些话，照 AGENTS.md 和 docs/委派/整合方手册.md 处理。多半是在回答队列里「等用户」的那几行：把用户的决定写进去（改那一行的状态、要的话写规格、加行），决定记进三周任务单（原话里有名字、地址、密钥这类个人信息的不要抄进仓库，只记决定）。看不懂的，或者用户要的事得动 docs/ 以外的东西，加一行「等用户：<你的问题>」问回去。只改 docs/ 下面的文件。做完照手册推到 main。

     原话一条一行：`- <北京时间 月日 时:分>：<text>`。停点：`停点：处理完这几条、推上 main 就停。` 最后一行：`做完在最后一行输出：RELAY-DONE inbox <一句话说你做了什么>`。
   - 核对：起点到现在之间改了 `docs/` 以外的文件 → `inbox-touched-code`（`Violation` 加它），照原来停下。
   - 这一棒有 `RELAY-DONE`、没越界 → 交代里列的那几条 `id` 记进 `inboxDone`，往群里发 `{ kind: 'inbox-done'; summary: string }`：`整合方处理了你的回复：<summary>`（`summary` 是 `RELAY-DONE inbox` 后面那句）。没有 `RELAY-DONE`（崩了、撞额度、超时）→ 不记，下一棒再派。
   - 记账：`kind: 'integrator-inbox'`、`taskId: 'inbox'`、`statusBefore` 是条数、`statusAfter` 是 `summary`。
7. 收听进程只往 `inbox.jsonl` 追加、只发「收到」「绑好了」两种话；不碰仓库、不碰 `state.json`、不起任何角色。

## 约束

- 只改 `packages/relay/`（含 `README.md`：写清用户在飞书开放平台要点哪几处、`--bind` 怎么用、`feishu-app.json` 长什么样，配图不用）。`pnpm-lock.yaml` 跟着依赖变。
- 不让飞书里的话直接执行任何命令：只通过「整合方的一棒、只改 docs/」生效。
- `appSecret` 和用户的原话不进仓库、不进日志（原话只在 `inbox.jsonl` 和那一棒的交代里）。测试、交付说明里用合成的原话。
- 已锁定的验收测试不改；撞上了停下写进交付说明。

## 验收条件

1. `acceptMessage`：合成的 `im.message.receive_v1` 事件——本人在绑定的群里 @ 机器人说「76 要」→ `ok`，`text` 是 `76 要`；换一个群、换一个人、没有 @、图片消息、只 @ 不说话 → 各自不 `ok`，`why` 里不带消息内容。
2. 收听（把 SDK 那一层换成一个假的事件源，照 `l2b-notify` 的假飞书收「收到」）：一条认的 → `inbox.jsonl` 多一行、假飞书收到 `收到：76 要。下一棒交给整合方。`；同一个 `id` 再来一次 → 不多记、不再回；不认的 → 不记、不回。`--bind`：`feishu-app.json` 里只有 `appId`、`appSecret`，来一条 @ 机器人的消息 → 文件里多了 `chatId`、`ownerOpenId`，原来两项不变，退出码 0。没绑定又没带 `--bind` → 退出码 2、打那一行。
3. 派活：`inbox.jsonl` 有没办的 → 先派飞书回复棒，哪怕同时有「待复审（整合方）」的行；都办过了 → 照原来；整合方在歇 → 不派。
4. 交代：逐字含契约第 6 条那段、原话那几行的写法（北京时间）、停点、最后一行。
5. 核对与记账：合成仓库里替身当整合方——只改 `docs/` 并输出 `RELAY-DONE inbox 第 76 行改成了待领` → 不停，`inboxDone` 记上那几条，假飞书收到 `整合方处理了你的回复：第 76 行改成了待领`，记账照契约；替身改了 `packages/` 下的文件 → `inbox-touched-code`、停下；替身没输出 `RELAY-DONE` → `inboxDone` 不记，下一次 `once` 又派飞书回复棒。
6. 看门人：`IXAEON_RELAY_CODE` 指向一个假代码目录（它的 `relay.mjs listen` 打一行就退出）、`feishu-app.json` 四项齐 → 看门人起了收听、退出后又起；文件不全 → 不起。
7. 隐私：上面所有测试的输出、报错里都找不到合成的 `appSecret`。

## 真机检查

- **甲（开发做，用户的应用建好、`feishu-app.json` 写了 `appId`、`appSecret` 才做；没建好就写没跑）**：临时数据目录里放一份 `feishu-app.json` 的**副本**、`feishu.json` 的副本，跑 `relay listen --bind`，在交付说明里写清「请用户在群里 @ 机器人说一句话」——这一步要用户，开发不等：只验到「连上了、打出 `收听中`」为止，贴出那一行（别的输出遮掉）。
- **乙（整合方合并后和用户一起做）**：用户在群里 @ 机器人绑定一次，再 @ 它回答一行「等用户」，看到「收到」、下一棒整合方处理完回「整合方处理了你的回复：…」，队列里那一行照用户的话改了。结论追加到这份规格末尾。

## 整合方审测试时的改正与补充（2026-10-24，接力第 25 棒）

测试是 dev2 在 `dev2/L16`（88608ee）交的，6 份、24 条。整合方写了一份一次性实现（没提交）跑通，再逐处改坏 61 处做变异检查：60 处有测试变红，剩下 1 处是等价的（`acceptMessage` 里「`app.chatId` 没有」那个判断去掉也一样——`chat_id` 本来就不会等于 `undefined`）。带着那份实现跑 `packages/relay` 全部 45 份验收测试（288 条）都过，没有撞红已锁定的。去掉实现后新测试 27 条红、4 条过（过的是「不该派」「不全就不起」这类，没有实现也该成立）。锁定后 6 份、31 条。上面的依赖写的是 L15，队列里用户已经去掉了这个依赖（4d8906d），以队列为准。

**改正**（原来实现写对了也过不了，或者等于没测）：

1. `l16-listen`：原来等 stdout 里出现「收到：…」——契约只要求把它发到群里，没要求打到 stdout；而且一看到就杀进程，后面那条重复的、那条不认的还没喂到，「不多记、不再回」等于没测。改成假事件源喂完 2 秒后自己退，测试等进程退了再查；群里**一共**只收到一句。顺带：`relay.mjs` 外面包了一层，杀外层杀不到里面那层，原来每跑一次留一个挂着的孤儿进程。
2. `l16-listen`：坏文件原来写的就是「不是 JSON」四个字，再查输出里没有「不是 JSON」——实现说「feishu-app.json 不是 JSON」反而过不了，也查不出有没有把文件内容打出来。换成一份带着合成密钥的坏 JSON，查密钥没漏出来。
3. `l16-inbox-turn`：「改了 `packages/`」的替身往合成仓库里不存在的 `packages/` 目录写文件，ENOENT 崩掉、什么都没推，越界从来没发生过。先建目录，再查确实推上去了、记账里有 `inbox-touched-code`。
4. `l16-watchdog`：假代码的 `once` 马上退，看门人 `--exit-when-idle` 第一轮空转就退了，收听来不及「退出后隔 `idleSeconds` 再起」。假 `once` 改成 5 秒后退。

**补充**（只加、只改严）：

- `acceptMessage`：飞书 SDK 摊平的形状也认（见下面「定下的」第 5 条）；还没绑定、传进来的不是对象 → 不 `ok`、不抛错；@ 了两个人，两个占位都去掉。
- 收听：「收到」只带原话的前 50 个字（`inbox.jsonl` 里记全文）；`--bind` 跳过前面别的群、别的人、没 @ 的消息；每条收听测试都查输出里没有 `appSecret`；连接那一层报错、报错原文带着 `appSecret` → 打出来的换成 `<已隐藏>`；文件不在、不是 JSON、缺 `appId`、缺 `appSecret` 四种都是退出码 2、那一行提到 `feishu-app.json`、不打「收听中」。
- 交代：原话故意倒着传，要交代自己按时间排；北京时间跨日（UTC 16:30 → 北京次日 00:30）；先后是「那段 → 原话 → ASK → 停点 → 最后一行」。
- 飞书回复棒：越界、没 `RELAY-DONE` 都不发「整合方处理了你的回复」；没 `RELAY-DONE` 不停下；用户又回了一条 → 再派一棒、交代里只列新的、两次回话都发（不限频）；`inboxDone` 200 个上限（下面第 1 条）。
- 看门人：子进程是 `listen --under <看门人的进程号>`；`--exit-when-idle` 退出前停掉还挂着的收听（不停的话看门人退不出来）。

**规格里没写到、这次定下的**：

1. **「没办的」只看 `inbox.jsonl` 最后 200 行。** 契约第 6 条让 `inboxDone` 只留最近 200 个，可 `inbox.jsonl` 一直变长：过了 200 条，最早办过的会被挤出 `inboxDone`，又被当成没办的，每一棒都派。只看最后 200 行就对上了。
2. 「没配」（文件不在、不是 JSON、缺 `appId` / `appSecret`）时 `relay listen` 打一行提到 `feishu-app.json` 的话（不带文件内容），退出码 2，和「还没绑定」一样。
3. 契约里「打一行」都打在 stdout（`console.log`），照调度器别的输出。
4. 原话的时间照 `notify/feishu.ts` 的 `beijing` 写：`10月24日 14:03`。
5. 测试换掉 SDK 那一层的接缝：环境变量 `IXAEON_RELAY_EVENT_SRC` 指向一个模块，导出 `startEventSource(onEvent, app)`（测试里的只用第一个参数），没设就用真 SDK 那份。`acceptMessage` 两种形状都认：HTTP 推送的原始形状（`{ header, event: { message, sender } }`，测试用的）和 SDK `EventDispatcher` 交给回调的摊平形状（`message`、`sender` 在顶层）。
6. 「收到」「绑好了」「整合方处理了你的回复」都走 L3 的发送，前面带「【IXAEON 接力】」那一行没关系（测试查的是包含）。`inbox-done` 和 `planned`、`daily` 一样不限频。

**给实现的提醒**：

1. 停掉收听要停掉**整棵进程树**：`relay.mjs` 外面包了一层 `spawnSync`，只杀外层，里面那层的长连接还挂着（Windows 上照 `run-turn.ts` 的 `killTree` 用 `taskkill /T /F`）；或者 `listen --under <pid>` 定时看那个进程还在不在，不在就自己退。测试里的假代码没有这层包装，测不出来；真机检查乙时看一眼任务管理器里有没有剩下的 node。
2. `relay listen` 不读 `config.json`、不拿锁（会和看门人的锁冲突）、不碰 `state.json`：在 `relay-main.ts` 的 `main()` 里 `loadConfig` 之前分出去。
3. `--bind` 绑好要退出，真 SDK 的长连接会把进程挂住；注意 `relay-main.ts` 末尾那条：这台机器上发过 HTTPS 再 `process.exit` 会崩（0xC0000409）。先关掉 `WSClient` 再让进程自己退。
4. 飞书回复棒的 `statusAfter` 是 `summary`；没 `RELAY-DONE` 时是 `null`。
5. 体量：整合方那份一次性实现（不含真 SDK 那份和 README）约 250 行源码；加上真 SDK 和 README 可能过 300，过了照上面拆 L16b（契约第 4、5、6 条）。
