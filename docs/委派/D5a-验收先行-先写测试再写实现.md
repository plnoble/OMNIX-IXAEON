# 规格 D5a：验收先行——先写测试并锁定，再写实现，做完自动跑

档位：**B**（新写的提示词；在用户机器上跑模型写的代码）。大小：中（≤300 行源码）。依赖：V3（零依赖档断网）✅、D7 ✅。来源：用户 2026-09-27 定的「验收把关」，2026-10-05 试场景一走通之后同意现在做。

v2 规格：先把验收条件写成测试（`packages/core/test/acceptance/d5a-*.test.ts`），**先只推测试**，整合方看过并锁定后再实现。

## 要什么

现在聊天里提出来的编码任务有验收条件、没有验证命令，做完只能写「没有有效验证命令，保留未运行」，接受全凭用户自己看。用户定的做法（与开发 IXAEON 自己的流水线同一个思路）：

> 先写测试，核心模型对照验收条件核一遍有没有漏或放宽，锁定后再实现；实现时改了测试就算失败。

这一单做其中的骨架：**写测试 → 实现前先跑一遍 → 锁定 → 写实现 → 再跑**。「核心模型核一遍」是下一单（D5b）。

## 什么任务走这条路

有验收条件（`acceptance_json` 至少一条）而且没有验证命令（`allowed_commands_json` 是空的）的任务——也就是聊天里提出来的任务。别的任务（任务页手建、带验证命令的）照旧，一点不变。

## 契约（接口写死，不改名、不加字段）

1. **执行器多一个只读范围**（`packages/core/src/execution/executor.ts`）：

   ```ts
   export interface ExecutorRunOptions {
     /** 这些文件的内容给执行器看，但不许改。能改什么仍由任务的 scope 定。 */
     readScope?: string[];
   }
   // CodingExecutor.run(task, workspace, signal, options?: ExecutorRunOptions)
   ```

   - `ModelCodingExecutor`：内容照 D7 的规则发，只是「批准范围内的」换成「scope 加 readScope 之内的」；能写的仍只有 scope。
   - `ConfiguredCodingExecutor`（桌面端）把 `options` 原样传下去。Codex、替身执行器不用管它。

2. **测试放哪**：副本里的 `ixaeon-acceptance/<任务号前 8 位>/`，文件名以 `.test.mjs` 结尾，每个文件能用「node 文件名」直接跑（`node:test` 加 `node:assert`，不用 npm 包）。导出常量 `ACCEPTANCE_DIR = 'ixaeon-acceptance'`。这些文件算这次任务的改动，接受后随分支一起落地。

3. **流程**（`CodingOrchestrator.dispatch`，同一次派发里走完；每一步之间照旧查取消）：

   1. **写测试**：调一次执行器。任务目标换成下面的「写测试的交代」，`scope` 换成只有测试目录，`readScope` 是原来的批准范围。
      - 这一步改了测试目录以外的文件 → 任务失败，原因「写验收测试时改了别的文件：<路径>」，不再往下走。
      - 没写出测试文件（执行器报错、自己说做不到、什么都没写）→ 不锁定，原因记执行器说的话，直接去第 4 步。
   2. **实现前先跑一遍**：每个测试文件按零依赖档跑（`runCheck([process.execPath, <相对路径>], 副本, …)`）。
      - 全都通过 → 这些测试测不出这次改动 → 不锁定，原因「验收测试在实现之前就全部通过，测不出这次改动」。
      - 沙箱不肯跑（`ran === false`）→ 不锁定，原因用沙箱给的说明。
      - 跑完之后副本里测试目录以外的文件有变化 → 任务失败，原因「验收测试改了项目里的文件：<路径>」，不再往下走（副本已经不干净，不能接着写实现）。
      - 其余情况（至少一个文件不通过）→ 进下一步。
   3. **锁定**：记下测试目录里每个文件的指纹。
   4. **写实现**：再调一次执行器。任务目标是现在派发时的那一份（目标、可修改范围、获准背景、获准 Skill），锁定了的话后面接上「写实现的交代」；`scope` 是原来的批准范围；`readScope` 是测试目录。
      - 做完后测试目录里任何文件的指纹变了、多了或少了文件 → 任务失败，原因「实现时改了验收测试：<路径>」。
      - 其余核对（改动不出批准范围、执行器自己说没做成）照旧。
   5. **再跑**：
      - 锁定了：每个测试文件再跑一遍。全过 → `verify_status = 'passed'`，等用户接受；有不过的 → 任务失败，`verify_status = 'failed'`，输出进 `verify_output`（与现在验证失败的写法一样）；沙箱不肯跑 → 等用户接受，`not_run`，原因进 `verify_output`。跑完之后测试目录以外的文件有变化 → 任务失败，原因「验收测试改了项目里的文件：<路径>」。
      - 没锁定：等用户接受，`verify_status = 'not_run'`，`verify_output` 写第 1、2 步记下的原因。

4. **执行报告**（`executor_report_json`）多一项 `acceptanceTests: { files: string[]; locked: boolean; reason: string | null }`。`changedPaths` 包含测试文件。`testsModified` 不把本任务新写的验收测试算进去（不然每个任务都显示「测试代码被修改」）。

5. **两段交代**（写死在核心层，原文如下；`<…>` 是填进去的）：

   写测试的交代：

   ```
   这一步只写验收测试，不要写实现。

   要做的事：
   <任务目标>

   验收条件：
   1. <条件一>
   2. <条件二>

   怎么写：
   - 测试文件放在 <测试目录>/ 下，文件名以 .test.mjs 结尾。别的文件一个都不要动。
   - 用 node:test 和 node:assert/strict，不用任何 npm 包。每个文件要能用「node 文件名」直接跑；有测试不通过时退出码不是 0。
   - 每条验收条件至少有一个测试，测试的名字以「条件 N：」开头。
   - 测试跑的时候不能联网、不能起别的进程，只能读项目目录里的文件；不要改项目里的文件。
   - 实现现在还没有写：这些测试现在应该不通过，实现写对之后才通过。
   - 有的条件没法这样自动测（比如要人看界面、要联网）：不要硬凑，在 summary 里写明是哪几条、为什么。一条都测不了就不要写文件，把 claimedSuccess 设为 false，在 summary 里说明。
   ```

   写实现的交代（接在原来的任务目标后面）：

   ```
   验收测试已经写好并锁定：<测试文件，逗号分开>。
   - 不许改这些文件，也不许在 <测试目录>/ 下增删文件；改了这次任务就算失败。
   - 做完的标准是它们全部通过（每个文件用「node 文件名」跑）。
   ```

## 约束

- 不加迁移。不动 D2 的三档规则和 V3 的断网。
- 测试只在零依赖档跑。依赖档（Codex 沙箱）不在这一单：带 npm 依赖的项目，模型写的测试多半引不到依赖、实现前实现后都不通过——照上面的流程就是「任务失败，独立验证失败」，如实。这是已知的局限，写进交付说明，不要绕。
- 用户点「要做」批准的就是整件事，包括在隔离副本里写验收测试、在零依赖档里跑它们。不另加确认。
- 回报的文字这一单不改：锁定并通过时现有的回报写「验证通过」，没锁定时写「验证没跑：<原因>」，都是现有逻辑按 `verify_status`、`verify_output` 出的。

## 验收条件

1. 有验收条件、没有验证命令的任务：执行器被调两次。第一次的目标是「写测试的交代」（含任务目标、编了号的每条验收条件、测试目录），`scope` 只有测试目录，`readScope` 是原批准范围；第二次的目标含原任务目标和「写实现的交代」（含每个测试文件的路径），`scope` 是原批准范围，`readScope` 是测试目录。
2. 测试实现前不通过、实现后通过：任务等用户接受，`verify_status = 'passed'`；`acceptanceTests.locked = true`，`files` 正是那些测试文件；`changedPaths` 含测试文件和实现改的文件；接受后合成 git 项目的分支里两样都有。
3. 实现后测试仍不通过：任务失败，`verify_status = 'failed'`，`verify_output` 里有测试的输出。
4. 实现时改了、删了或在测试目录里新加了文件：任务失败，原因里有那个路径。
5. 测试在实现之前就全部通过：不锁定，照样写实现，任务等用户接受，`not_run`，原因写明测不出这次改动。
6. 第一步没写出测试（执行器自己说做不到）：照样写实现，任务等用户接受，`not_run`，原因里有执行器说的话。
7. 第一步改了测试目录以外的文件：任务失败，原因里有那个路径；执行器没有被调第二次。
8. 测试跑的时候改了测试目录以外的文件：任务失败，原因里有那个路径。实现前那一遍出的事，执行器没有被调第二次。
9. 带验证命令的任务、没有验收条件的任务：与现在一模一样（执行器只调一次，D3、D4、D7b 的锁定测试照过）。
10. `ModelCodingExecutor`：`readScope` 里的文件发内容；要改它们（不在 scope 里）照样被拒。不传 `readScope` 时与现在一样（D7 的锁定测试照过）。
11. 派发途中取消：不再往下走，状态是已取消。
12. `testsModified`：只写了本任务的验收测试时是 false；实现改了别的测试文件时是 true。

## 端到端测试（随实现一起交，不锁定）

`apps/desktop/e2e/d5a-acceptance-first.spec.ts`，假模型加响应脚本、`IXAEON_CODEX_EXE=none`、合成的小 git 项目（一个不带依赖的 `.mjs` 模块）：聊天里提一个带验收条件的任务 → 点「要做」→ 对话里的回报写「验证通过」→ 任务页显示「独立验证 passed」→ 接受后分支里有测试文件和实现。

## 真机检查

`scripts/real/d5a-acceptance-first.mjs`，照 `scripts/real/d7b-model-task.mjs` 的做法（临时数据目录只取五项配置、临时用户目录只放 `Local State`、任务经 IPC 走、输出里换掉模型名和网关），在用户自己的模型网关上跑两个任务，合成项目里放一个不带依赖的 `calc.mjs`（只有 `add`）：

1. 目标「给 calc.mjs 加一个 multiply(a, b)」，验收条件「multiply(2, 3) 等于 6」「原来的 add 不变」→ 打印：写了哪些测试文件、实现前那一遍的退出码、最后的 `verify_status`、接受后分支相对 main 改了哪些文件。
2. 目标「把 README 写得更通顺」，验收条件「读起来通顺」→ 打印模型在第一步说了什么、最后的 `verify_status` 和原因。

结果要从任务的实际状态读，不对就以非零码退出。原样贴进交付说明。

## 留给下一单（D5b）

锁定之前让核心模型对照验收条件把测试核一遍：有没有哪条没测到、有没有放宽。没过核对的不锁定，回报里写明是哪条。这一单的 `acceptanceTests` 以后会加核对结果，别的不变。
