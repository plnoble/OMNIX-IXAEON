# 规格 D5a：验收先行——先写测试并锁定，再写实现，做完自动跑

档位：**B**（新写的提示词；在用户机器上跑模型写的代码）。大小：中（≤300 行源码）。依赖：V3（零依赖档断网）✅、D7 ✅。来源：用户 2026-09-27 定的「验收把关」，2026-10-05 试场景一走通之后同意现在做。

v2 规格：先把验收条件写成测试（`packages/core/test/acceptance/d5a-*.test.ts`），**先只推测试**，整合方看过并锁定后再实现。

## 要什么

现在聊天里提出来的编码任务有验收条件、没有验证命令，做完只能写「没有有效验证命令，保留未运行」，接受全凭用户自己看。用户定的做法（与开发 IXAEON 自己的流水线同一个思路）：

> 先写测试，核心模型对照验收条件核一遍有没有漏或放宽，锁定后再实现；实现时改了测试就算失败。

这一单做其中的骨架：**写测试 → 实现前先跑一遍 → 锁定 → 写实现 → 再跑**。「核心模型核一遍」是下一单（D5b）。

## 什么任务走这条路

有验收条件（`acceptance_json` 至少一条）而且没有验证命令（`allowed_commands_json` 是空的）的任务——也就是聊天里提出来的任务。别的任务（任务页手建、带验证命令的）照旧，一点不变。

## 契约（接口写死，不改名、不加字段）

1. **执行器多一个只读范围**（`packages/core/src/execution/executor.ts`）：

   ```ts
   export interface ExecutorRunOptions {
     /** 这些文件的内容给执行器看，但不许改。能改什么仍由任务的 scope 定。 */
     readScope?: string[];
   }
   // CodingExecutor.run(task, workspace, signal, options?: ExecutorRunOptions)
   ```

   - `ModelCodingExecutor`：内容照 D7 的规则发，只是「批准范围内的」换成「scope 加 readScope 之内的」；能写的仍只有 scope。给模型的话里，「可修改范围」下面多一行「只读范围（内容发给你看，但不要改）：<readScope>」，没有只读范围就没有这一行（执行方实现时加的，整合方复审时认了，条件 33）。
   - `ConfiguredCodingExecutor`（桌面端）把 `options` 原样传下去。Codex、替身执行器用不着它，但 `run` 的签名要收下这个参数（见末尾「实现时会撞上的」）。`ExecutorRunOptions`、`ACCEPTANCE_DIR` 从核心包的出口（`@ixaeon/core`）导出。

2. **测试放哪**：副本里的 `ixaeon-acceptance/<任务号前 8 位>/`，文件名以 `.test.mjs` 结尾，每个文件能用「node 文件名」直接跑（`node:test` 加 `node:assert`，不用 npm 包）。导出常量 `ACCEPTANCE_DIR = 'ixaeon-acceptance'`。这些文件算这次任务的改动，接受后随分支一起落地。

3. **流程**（`CodingOrchestrator.dispatch`，同一次派发里走完；每一步之间照旧查取消）：

   1. **写测试**：调一次执行器。任务目标换成下面的「写测试的交代」，`scope` 换成只有测试目录，`readScope` 是原来的批准范围。
      - 这一步改了测试目录以外的文件 → 任务失败，原因「写验收测试时改了别的文件：<路径>」，不再往下走。
      - 没写出测试文件（执行器报错、自己说做不到、什么都没写）→ 不锁定，原因记执行器说的话，直接去第 4 步。
   2. **实现前先跑一遍**：每个测试文件按零依赖档跑（`runCheck([process.execPath, <相对路径>], 副本, …)`）。
      - 全都通过 → 这些测试测不出这次改动 → 不锁定，原因「验收测试在实现之前就全部通过，测不出这次改动」。
      - 沙箱不肯跑（`ran === false`）→ 不锁定，原因用沙箱给的说明。
      - 跑完之后副本里有文件变了（测试自己目录里的也算，见条件 31）→ 任务失败，原因「验收测试改了项目里的文件：<路径>」，不再往下走（副本已经不干净，不能接着写实现）。
      - 其余情况（至少一个文件不通过）→ 进下一步。
   3. **锁定**：记下测试目录里每个文件的指纹。
   4. **写实现**：再调一次执行器。任务目标是现在派发时的那一份（目标、可修改范围、获准背景、获准 Skill），后面接上「写实现的交代」（验收条件每次都给，其余看锁没锁定，见契约 5）；`scope` 是原来的批准范围；`readScope` 是测试目录。
      - 做完后测试目录里任何文件的指纹变了、多了或少了文件 → 任务失败，原因「实现时改了验收测试：<路径>」。
      - 其余核对（改动不出批准范围、执行器自己说没做成）照旧。
   5. **再跑**：
      - 锁定了：每个测试文件再跑一遍。全过 → `verify_status = 'passed'`，等用户接受；有不过的 → 任务失败，`verify_status = 'failed'`，输出进 `verify_output`（与现在验证失败的写法一样）；沙箱不肯跑 → 等用户接受，`not_run`，原因进 `verify_output`。跑完之后副本里有文件变了（测试自己目录里的也算）→ 任务失败，原因「验收测试改了项目里的文件：<路径>」。
      - 没锁定：等用户接受，`verify_status = 'not_run'`，`verify_output` 写第 1、2 步记下的原因。

4. **执行报告**（`executor_report_json`）多一项 `acceptanceTests: { files: string[]; locked: boolean; reason: string | null }`。`changedPaths` 包含测试文件。`testsModified` 不把本任务新写的验收测试算进去（不然每个任务都显示「测试代码被修改」）。

5. **给执行器的交代**（写死在核心层，原文如下；`<…>` 是填进去的）：

   写测试的交代：

   ```
   这一步只写验收测试，不要写实现。

   要做的事：
   <任务目标>

   验收条件：
   1. <条件一>
   2. <条件二>

   怎么写：
   - 测试文件放在 <测试目录>/ 下，文件名以 .test.mjs 结尾。别的文件一个都不要动。
   - 用 node:test 和 node:assert/strict，不用任何 npm 包。每个文件要能用「node 文件名」直接跑；有测试不通过时退出码不是 0。
   - 跑的时候当前目录是项目根目录；引入项目里的模块，要从测试文件所在的目录往上两级（../../）。
   - 每条验收条件至少有一个测试，测试的名字以「条件 N：」开头。
   - 测试跑的时候不能联网、不能起别的进程，只能读项目目录里的文件；不要改项目里的文件。
   - 实现现在还没有写：这些测试现在应该不通过，实现写对之后才通过。
   - 有的条件没法这样自动测（比如要人看界面、要联网）：不要硬凑，在 summary 里写明是哪几条、为什么。一条都测不了就不要写文件，把 claimedSuccess 设为 false，在 summary 里说明。
   ```

   写实现的交代（接在原来的任务目标后面，各段之间空一行）。验收条件每次都给：

   ```
   验收条件：
   1. <条件一>
   2. <条件二>
   ```

   锁定了，再接：

   ```
   验收测试已经写好并锁定：<测试文件，逗号分开>。
   - 不许改这些文件，也不许在 <测试目录>/ 下增删文件；改了这次任务就算失败。
   - 做完的标准是它们全部通过（每个文件用「node 文件名」跑）。
   ```

   没锁定、但测试目录里有第 1 步写的文件（测不出这次改动，或者实现前沙箱不肯跑），再接：

   ```
   <测试目录>/ 下是这次任务写的验收测试，没有锁定，不拿它们当验证。
   - 不要改、不要删这些文件，也不要往 <测试目录>/ 下加文件；动了这次任务就算失败。
   ```

   第 1 步什么都没写：只有验收条件那一段，不提验收测试。

   2026-10-05 审测试时改的三处：写测试的交代里加了「当前目录是项目根目录」那一句（模型看不到副本，不说的话它不知道路径从哪算起）；写实现的交代里每次都给验收条件（验收条件原来只有回报里用到，执行器从没见过——测试没写出来的时候，写实现的人就完全不知道做完的标准）；加了没锁定时的那一段（没锁定时动测试目录照样算失败，见条件 13，那就得先告诉执行器）。

6. **替身执行器**（`FakeCodingExecutor`，2026-10-05 审测试时补）：被叫去写验收测试（任务的 scope 只有测试目录）时不动副本，返回 `claimedSuccess: false`、summary「替身执行器不写验收测试」。它原来不管被叫去做什么都写自己那几个文件，不改的话第 1 步就会被判「写验收测试时改了别的文件」，用替身跑的聊天任务全部失败。

## 约束

- 不加迁移。不动 D2 的三档规则和 V3 的断网。
- 测试只在零依赖档跑。依赖档（Codex 沙箱）不在这一单：带 npm 依赖的项目，模型写的测试多半引不到依赖、实现前实现后都不通过——照上面的流程就是「任务失败，独立验证失败」，如实。这是已知的局限，写进交付说明，不要绕。
- 用户点「要做」批准的就是整件事，包括在隔离副本里写验收测试、在零依赖档里跑它们。不另加确认。
- 回报的文字这一单不改：锁定并通过时现有的回报写「验证通过」，没锁定时写「验证没跑：<原因>」，都是现有逻辑按 `verify_status`、`verify_output` 出的。

## 验收条件

1. 有验收条件、没有验证命令的任务：执行器被调两次。第一次的目标是「写测试的交代」（含任务目标、编了号的每条验收条件、测试目录），`scope` 只有测试目录，`readScope` 是原批准范围；第二次的目标含原任务目标和「写实现的交代」（含每个测试文件的路径），`scope` 是原批准范围，`readScope` 是测试目录。
2. 测试实现前不通过、实现后通过：任务等用户接受，`verify_status = 'passed'`；`acceptanceTests.locked = true`，`files` 正是那些测试文件；`changedPaths` 含测试文件和实现改的文件；接受后合成 git 项目的分支里两样都有。
3. 实现后测试仍不通过：任务失败，`verify_status = 'failed'`，`verify_output` 里有测试的输出。
4. 实现时改了、删了或在测试目录里新加了文件：任务失败，原因里有那个路径。
5. 测试在实现之前就全部通过：不锁定，照样写实现，任务等用户接受，`not_run`，原因写明测不出这次改动。
6. 第一步没写出测试（执行器自己说做不到）：照样写实现，任务等用户接受，`not_run`，原因里有执行器说的话。
7. 第一步改了测试目录以外的文件：任务失败，原因里有那个路径；执行器没有被调第二次。
8. 测试跑的时候改了测试目录以外的文件：任务失败，原因里有那个路径。实现前那一遍出的事，执行器没有被调第二次。
9. 带验证命令的任务、没有验收条件的任务：与现在一模一样（执行器只调一次，D3、D4、D7b 的锁定测试照过）。
10. `ModelCodingExecutor`：`readScope` 里的文件发内容；要改它们（不在 scope 里）照样被拒。不传 `readScope` 时与现在一样（D7 的锁定测试照过）。
11. 派发途中取消：不再往下走，状态是已取消。
12. `testsModified`：只写了本任务的验收测试时是 false；实现改了别的测试文件时是 true。

整合方审测试时补的（2026-10-05，为什么补见末尾一节）：

13. 写实现那一步动了测试目录（改、删、加，不是测试的文件也算），不管锁没锁定都失败：测试没锁（测不出改动）时实现改了它、第一步没写出测试而实现往测试目录里写了文件，一样任务失败，原因里有那个路径。
14. 没锁定时，写出来的测试照样记进 `acceptanceTests.files`、算进 `changedPaths`；写实现之后不再跑它们。
15. 验证通过时 `verify_output` 里也有测试的输出（与现在验证通过的写法一样）。
16. 跑测试的时候取消：取消信号接进验证进程（照 A04），进程跟着停，不等它自己跑完；状态是已取消，不再往下走。
17. 执行器自己的报告通道文件（`EXECUTOR_CHANNEL_FILE`，Codex 每一步都写）不算「改了别的文件」，也不进 `changedPaths`。
18. 写实现那一步其余的核对照旧，而且在跑测试之前：改动超出批准范围、执行器自己说没做成 → 任务失败，不跑测试。
19. 沙箱不肯跑（契约 3 里有，原来没列成条件）：实现前不肯跑 → 不锁定，原因用沙箱的话，照样写实现，`not_run`；实现后不肯跑 → 等用户接受，`not_run`，原因用沙箱的话，`acceptanceTests.locked` 仍是 true。
20. 「没写出测试」的三种情况都算（条件 6 只写了第一种）：自己说做不到、说成了但一个文件都没写、报错（不是取消）。原因里有执行器说的话，报错时是报错的话。
21. 「测试目录以外」指这个任务自己的目录以外：测试文件写在 `ixaeon-acceptance/` 下别的地方，也算改了别的文件。
22. 测试怎么跑：`runCheck([process.execPath, <相对路径>], 副本根目录, 取消信号, …)`，命令只有这两段；每个测试文件实现前、实现后各跑一遍，实现前的都跑完才调第二次执行器；两步在同一个副本里做。
23. 替身执行器（契约 6）：用它跑带验收条件、没有验证命令的任务——执行器被调两次，第一次不动副本；任务照常做完等用户接受，`not_run`，原因里有「替身执行器不写验收测试」，不是「没有有效验证命令」。
24. `ConfiguredCodingExecutor` 把 `options` 原样传给实际干活的执行器（交给模型、交给 Codex 都传）；`ACCEPTANCE_DIR`、`ExecutorRunOptions` 能从 `@ixaeon/core` 引到。测试在 `apps/desktop/test/acceptance/d5a-executor-options.test.ts`。
25. 写测试的交代里写明：跑的时候当前目录是项目根目录，引入项目里的模块要从测试文件所在的目录往上两级。
26. 写实现的那一次，目标里有编了号的每条验收条件，锁没锁定都有。
27. 没锁定、但测试目录里有第 1 步写的文件时，写实现的目标后面接上「没锁定」的那一段（含测试目录）；第 1 步什么都没写时不接，目标里不提验收测试；锁定了的不说「没有锁定」。

整合方复审实现时补的（2026-10-06，为什么补见末尾「整合方复审实现时改的」）：

28. 替身执行器只在「scope 只有这个任务的测试目录」时不写。批准范围是整个项目（`.`）的任务，写实现那一步照常写；带验证命令、不走验收先行的任务也照常写。
29. 验证输出里不带本机的绝对路径：副本的路径（反斜杠的、正斜杠的、`file://` 的写法都算）换成「<副本>」；每个文件那一段的开头写「node <相对路径> → <退出码>」，不写可执行程序的完整路径。
30. 执行器说的话只留开头 500 字（多的截掉，后面加「…」）：没写出测试时记的原因、写进 `verify_output` 的都是截过的。
31. 测试跑的时候往自己的测试目录里写文件，也算「验收测试改了项目里的文件」：任务失败，原因里有那个路径，不往下走。
32. 沙箱不肯跑、又没给说明：原因写「验证的沙箱不肯跑，也没给说明」，不写成「没有有效验证命令，保留未运行」。实现前、实现后那一遍都一样。
33. 给模型的话里写明只读范围（契约 1）；没有只读范围时不提这一句。

## 端到端测试（随实现一起交，不锁定）

`apps/desktop/e2e/d5a-acceptance-first.spec.ts`，假模型加响应脚本、`IXAEON_CODEX_EXE=none`、设置里选「我的模型」、合成的小 git 项目（一个不带依赖的 `.mjs` 模块）：一个带验收条件的聊天任务 → 点「要做」→ 对话里的回报写「验证通过」→ 任务页显示「独立验证 passed」→ 接受后分支里有测试文件和实现。

带验收条件的任务怎么造（2026-10-05 改）：假模型那条路的 `propose_task` 提出来的任务带验证命令、不带验收条件，走不到这里；带验收条件的只有 Hermes 经记忆桥调的 `propose_coding_task`，端到端测试里没有 Hermes。照 `scripts/real/d3-auto-dispatch.ts` 的现成做法：在临时库里直接造出项目对话、这一轮提问、任务草案（`acceptance_json` 有条件，`allowed_commands_json` 是 `[]`）和它的待办卡，再在界面上点「要做」。假模型的响应脚本要给两次：先是写测试的，再是写实现的。

## 留给下一单（D5b）

## 整合方审测试时的改正与补充（2026-10-05）

执行方先推的那版测试（`prep/D5a`，15 条）由整合方重写后锁定。锁的是两个文件：

另外改了 D1 的 `apps/desktop/test/acceptance/d1-coding-task-draft.test.ts` 并重锁（见下面「规格的漏洞」）。

### 原版里错的

1. 条件 2、12 的「实现前不通过、实现后通过」，用的是一个永远不通过的测试（断言 1 + 1 等于 3），却指望最后验证通过。照规格实现的话，实现后那一遍照样不通过、任务失败——这两条永远过不了，只有「做完不重跑测试」的实现才能让它们变绿，等于把实现往错的方向逼。现在用真的会跟着实现变的测试：引入 `calc.mjs`，断言 `multiply(2, 3)` 等于 6。
2. 条件 1 把测试文件写在了任务的测试目录外面，却指望执行器被调第二次，和条件 7 矛盾。
3. 条件 10 指望改只读范围里的文件时「返回没做成」；D7 锁定的行为是抛错、一处都不写。
4. 条件 8「实现后那一遍」写着测不了（现在测了：测试在断言通过之后才往项目里写文件）；条件 11 的断言两头都算过。

测试要在「照规格写对的实现」上通过、在「写错的实现」上不通过，两头都得真的跑过，光看「现在是红的」不够（原版交上来时写的是「11 红 4 绿」）。整合方这次的做法：先搭一个一次性的实现（不提交），测试全过之后把它逐个改坏（75 种改法），每种改法都有测试变红；再把实现丢掉，确认测试变红（37 条里红 30 条，绿的 7 条是「别的任务照旧」这类现在就该成立的）。

### 规格的漏洞：替身执行器

`FakeCodingExecutor` 不管被叫去做什么都写它那几个文件。照原规格，它在「写测试」那一步就会被判「写验收测试时改了别的文件」，用替身跑的聊天任务全部失败——D1 锁定的测试有两条因此会红，而执行方不能改锁定的测试。所以补了契约 6 和条件 23：替身被叫去写验收测试时不动副本，照实说写不了。

跟着变的：用替身跑的聊天任务，回报从「还没有独立验收」变成「验证没跑：…替身执行器不写验收测试」。

D1 的两条测试整合方已经改好重锁，D5a 做完之前、之后都成立，执行方不用动：

- 「整合方补：没写 scope 的草案……」里自带的替身执行器，在只许写测试的那一步不写、照实说；另加一句断言：项目里的文件只写了一遍。
- 「契约 4」不再只认「还没有独立验收」这一句，改成：回报不许说「验证通过」，要写「还没有独立验收」或「验证没跑：……」，`verify_status` 是 `not_run`。D5a 之后的确切写法由条件 23 钉住。

### 规格原来没想到的两处：写实现的人知道什么

1. **验收条件从没给过执行器。** 查的时候才发现，`acceptance_json` 只有对话里的回报在用，派发给执行器的目标里没有它。锁定了的话执行器还能从测试里看出来；测试没写出来（比如「读起来通顺」这种测不了的条件）的时候，写实现的人完全不知道做完的标准。补了条件 26：写实现的那一次，目标里每次都带验收条件。带验证命令的任务不走这条路，照旧不带（条件 9 说的「与现在一模一样」）——那是另一件事，这一单不动。
2. **没锁定时执行器不知道不能动测试目录。** 条件 13 定了没锁定时动测试目录照样算失败（不然批准范围以外的改动就有了一条不受核对的路）。可原规格只在锁定时才告诉执行器别动。测不出改动的那种情况下，测试文件就在副本里，执行器顺手把它「改好」，任务就失败了，而且没人告诉过它。补了条件 27：测试目录里有文件就说一声。

这两处都是整合方的建议，不是用户逐条定的；真模型上好不好用，等实现回来在用户的模型网关上跑了再看。

## 整合方复审实现时改的（2026-10-06）

执行方的实现让 37 条锁定测试全过、门禁和端到端测试都绿。整合方逐行读过，另用几条探针试了锁定测试没照到的地方，改了下面这些再并入。锁定的测试补了 7 条（条件 28–33），现在是 40 + 4 条。

### 实现里的问题

1. **替身执行器把「批准范围是整个项目」也当成「叫它写测试」。** 判断写的是「scope 里每一项要么是 `.`、要么以 `ixaeon-acceptance` 开头」。没写范围的草案存的就是 `['.']`，于是写实现那一步替身也不写了，任务以「执行器未声称成功」失败；带验证命令、不走验收先行的任务也一样。锁定的测试没照到（用的都是具体的文件名），是整合方的测试漏了。改成只认「scope 只有这个任务的测试目录」，补条件 28。
2. **验证输出里带着本机的绝对路径。** 每个文件那一段的开头写的是可执行程序的完整路径；测试不通过时，node:test 的报错里到处是副本的绝对路径。路径里有本机的用户名，而失败时回报会带上验证输出的开头几行，回报进对话，对话历史又会发给模型。改成开头写「node <相对路径>」，输出里副本的路径换成「<副本>」，补条件 29。原有的验证命令那条路（`verify`）没动——那是另一件事，这一单只管新加的。
3. **执行器说的话原样进回报。** 第一步没写出测试时，原因记的是执行器说的话，不限长度。Codex 的最后一条消息能有两千字，整段会出现在回报的「验证没跑：」后面。改成只留开头 500 字，补条件 30。
4. **沙箱不肯跑又没给说明时，写成了「没有有效验证命令，保留未运行」。** 那句话是给「压根没有验证命令」的任务用的，回报会因此写成「还没有独立验收」。改成照实写不肯跑，补条件 32。
5. **类型上硬转。** 执行报告的类型里没加 `acceptanceTests`，写进去时用 `as never` 硬转；跑测试时传的上下文也硬转了一次。类型补上，硬转去掉。
6. **整份副本的指纹算了十三遍。** 取测试文件清单、取测试目录的指纹各自把整份副本重新算一遍。项目大的时候每遍都要把所有文件读一次。改成一步只算一次、各处共用，现在是八遍（原来没有验收先行时是五遍）。

### 比规格严的一处，认了

规格写的是「测试跑完之后，副本里**测试目录以外**的文件有变化 → 任务失败」。实现是副本里任何文件变了都算，测试往自己的目录里写个临时文件也失败。整合方认这个更严的：测试目录是要锁定的，跑一遍就变样的目录锁不住。规格正文改了，补条件 31。
