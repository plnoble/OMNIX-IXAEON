# 规格 G03：从你聊天里提炼出来的目标，点「关注」不再被拒

档位：**B**（改变记忆含义在研究端的执行）。大小：小（≤80 行源码）。依赖：无。来源：[全局审核 2026-09-20](交付/全局审核-2026-09-20.md) G03。
v2 规格：先把验收条件写成测试（`packages/core/test/acceptance/g03-*.test.ts`），**先只推测试**等整合方看过并锁定，再实现。

## 要什么

提炼器把你在聊天里说的目标记成 `origin = 'ai'`、`said_by = 'user'`——前者是「记录由提炼器生成」，后者才是「谁说的」。W1a 提关注方向时接受这种目标，但建研究主题（`researchStore.ts` 校验 `relatedGoalId`）仍要求 `origin = 'user'`。结果：越是正常的「从聊天里自动理解你」这条路，越会卡在最后一步点「关注」；先确认那条目标也没用，因为确认不改 `origin`。

## 契约

`relatedGoalId` 指向的目标，按现有的记忆含义判断：

- 接受：人工建的（`origin = 'user'`）、提炼出来的你说的话（`said_by = 'user'`）、你采纳过的 AI 建议（`confirmation = 'confirmed'`）；
- 拒绝：没采纳的 AI 建议（`isUnadoptedAiAdvice` 为真的），报错不建主题。

研究端和记忆端用同一个判断，不各写一套。

**整合方复审测试时定（2026-09-24）**：「同一个判断」就是 W1a 挑依据的那个判断（`collectWatchMemories` 的条件：当前、没标「不对」、没结束、不是没采纳的 AI 建议），写成一处，两边共用；`relatedGoalId` 另外照旧要求 `type = 'goal'`。W1a 会拿来当依据的目标，点「关注」一定成功；它不会拿的，一定被拒。上面的接受清单漏了从资料里提炼的目标（`said_by` 为空：不是「你说的」，也不是 AI 建议）——W1a 会拿它提方向，只按清单实现的话点「关注」照样被拒。测试里用一组目标形状逐个核对两边一致。

## 约束

- 不改提炼器怎么记 `origin` / `said_by`；不加迁移。

## 验收条件

1. 四种目标各一条，分别作为 `relatedGoalId` 建主题：人工建的 ✓、提炼出的你说的 ✓、采纳过的 AI 建议 ✓、没采纳的 AI 建议 ✗（报错，不建）。
2. W1a 端到端：库里只有一条「提炼出的你说的」目标 → 提方向 → 点「关注」成功，主题关联到这条目标。

## 真机检查

不需要：纯本地校验，自动化覆盖。交付里写「规格不要求真机检查」。
