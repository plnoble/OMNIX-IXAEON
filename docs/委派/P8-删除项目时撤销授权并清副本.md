# 规格 P8：删除项目时撤销它绑的文件夹的授权，清掉任务副本

档位：**B**（权限与隐私；删除数据）。大小：中（≤150 行源码）。依赖：P5（解除绑定的那套办法直接拿来用）。来源：P5 写规格时查到、当时没放进去的缺口；用户 2026-10-09 同意加。

v2 规格：先把验收条件写成测试（`apps/desktop/test/acceptance/p8-*.test.ts`），**先只推测试**，整合方看过并锁定后再实现。

## 要什么

项目页点「删除」，现在只做一件事：把项目这一行删掉（它的理解、关系、编码任务跟着删，来源变成未归属）。留下三样没人管的东西：

1. **文件夹的读取授权还有效。** 项目绑过的文件夹，那条授权删除之后照样在。没有哪个界面看得到它，也撤不掉。
2. **正在排队或执行的编码任务没人叫停。** 任务那一行跟着项目删掉了，执行器却还在跑。
3. **任务的隔离副本还在硬盘上。** 每个批准过的任务在数据目录的 `workspaces/<任务号>/` 下有一份项目文件夹的副本。任务删了，副本留着，里面是当时的项目文件；任务页上已经没有这些任务，也就没有地方删它们。

这一单：删除项目时，先照 P5 的办法解除绑定（取消在途任务、撤销这个文件夹自己的那条授权），再删项目，然后把这个项目的任务副本清掉。确认框里把这些说清楚。

**第 3 样是整合方加的，用户点头的是第 1 样**（「删除项目时一并撤销它绑的文件夹的授权」）。理由：副本里是项目文件，删了项目之后它们成了界面上够不着的垃圾。用户要是不要这一条，整合方从规格里拿掉——执行方写测试时把第 3 样的条件（7、8、9）单独放一个 `describe`，好拿。

## 契约（接口写死，不改名、不加字段）

1. **类型**（`packages/contracts/src/entities.ts`）：

   ```ts
   /** 删除项目的结果。前两项是原来就有的。 */
   export interface DeleteProjectResult {
     /** 变成未归属的来源数。 */
     sourcesUnassigned: number;
     /** 跟着删掉的理解条数。 */
     itemsRemoved: number;
     /** 撤销了哪条授权；没撤销是 null（没绑文件夹、别的项目也绑着同一个文件夹、或者没有单独的授权）。 */
     revokedPermissionId: string | null;
     /** 删除之前取消了几个在途的编码任务。 */
     cancelledTasks: number;
     /** 删掉了几个任务副本目录。 */
     copiesRemoved: number;
     /** 有几个任务副本目录没删掉（文件正被占用等）。它们还在数据目录的 workspaces 下。 */
     copiesLeft: number;
   }
   ```

2. **接口**：`deleteProject(id: string): Promise<DeleteProjectResult>`（`packages/contracts/src/ipc.ts` 里原来的返回类型换成这个；多了四个字段，原来的两个不变）。业务逻辑放在 `AppRuntime.deleteProject(projectId)`，IPC 只转一下，测试直接测这个方法。

3. **`AppRuntime.deleteProject` 做什么**，按这个次序：

   1. 项目不存在：拒绝（原来的报错），什么都不变。
   2. **绑着文件夹的**：先照 P5 解除绑定——直接调 `unbindProjectFolder(projectId)`。它会取消排队、执行、验证中的任务并在各自的对话里回报「取消了」，清掉路径，撤销这个文件夹自己的那条授权（别的项目也绑着同一个文件夹、或者没有这样一条授权时不撤销；上级文件夹的授权不动），记审计 `project.folder_unbound`。`revokedPermissionId`、`cancelledTasks` 就取它返回的。
   3. **没绑文件夹的**：`revokedPermissionId` 是 null。这个项目要是还有排队、执行、验证中的任务（老数据里才有），照样取消并回报（`coding.cancel` 再 `codingDispatch.onTaskSettled`），算进 `cancelledTasks`。
   4. 记下这个项目所有任务的 `workspace_path`。
   5. 删项目：`projects.delete(projectId)`（原来的做法，不改；`sourcesUnassigned`、`itemsRemoved` 取它返回的）。审计 `project.deleted` 照旧，内容还是 `{ projectId, sourcesUnassigned, itemsRemoved }`。
   6. 清副本：第 4 步记下的每个目录，**只有在数据目录的 `workspaces/` 之内的才删**（判断办法照 `CodingOrchestrator.remove` 里现有的那一段）；不在里面的碰都不碰，也不计数。删掉的算进 `copiesRemoved`；删不掉的（抛错）不拦住整件事，算进 `copiesLeft`。目录本来就不在的不计数。
   7. 有副本要清时（`copiesRemoved + copiesLeft > 0`）记一条审计 `project.task_copies_removed`，内容 `{ projectId, removed, left }`。
   8. 让正在用的对话上下文失效（`invalidateContext()`）。

4. **界面**（`apps/desktop/src/renderer/src/pages/Projects.tsx` 的「删除」）：

   - 项目绑着文件夹时，点了先调 `previewUnbindProjectFolder`（P5 的预览，不新加接口），再用 `window.confirm` 问。没绑的不调预览，直接问。
   - 确认框的文字照下面写。第一段是原来的话加了一句副本；「这个项目绑着文件夹」那一段只在绑着时出现，讲授权的那一行按预览的 `grant` 三选一，带数字的两行数字是 0 就不出现：

     ```
     删除项目「<项目名>」？

     属于该项目的理解、关系、编码任务会删除，编码任务的隔离副本（里面有当时的项目文件）也一并删掉。来源会变成未归属，对话原文保留。个人记忆不动。此操作不能从列表撤销（可用备份恢复）。

     这个项目绑着文件夹：
     <路径>
     - 这个文件夹的读取授权一并撤销。
       （或）读取授权不撤销：另一个项目也绑着这个文件夹。
       （或）这个文件夹没有单独的读取授权，没有可撤销的。
     - 这条授权下导入过 <N> 份资料：之后不再读它们的原文。
     - 有 <N> 个编码任务正在排队或执行，会被取消。
     ```

     三种讲授权的说法都以「- 」开头（和 P5 一样）。

   - 取消确认：什么都不发生。
   - 确认：调 `deleteProject`，列表重新读一遍；页面上显示一句结果（`data-testid="project-delete-result"`，放在项目列表上面）：「已删除项目「<项目名>」。」后面按实际情况接：撤销了授权接「这个文件夹的读取授权已撤销。」；取消了任务接「取消了 <N> 个编码任务。」；有没删掉的副本接「有 <N> 个任务副本没删掉（文件正被占用），还在数据目录的 workspaces 里。」没有的那几句不出现。
   - 出错（预览出错、删除出错）：显示在这一页现有的报错条里；预览出错时不问、不删。

## 约束

- 不加迁移。`ProjectService.delete` 不改（它连带删什么、来源怎么变未归属，都照旧）。
- P5 的 `unbindProjectFolder`、`previewUnbindProjectFolder` 不改，P5 的锁定测试照过。
- 清副本只认数据目录 `workspaces/` 之内的目录。**项目文件夹本身、改动包、别的项目的副本，一个字节都不碰。**
- 别的锁定测试、各套回归里要是有直接调 `deleteProject`、又对返回值或审计做了全等比较的：实现之后会红。先确认是不是这个原因，是就写进交付说明，不要改锁定的。
- 测试、交付说明里的路径、项目名用合成的。

## 验收条件

1. 绑着文件夹、有自己那条授权的项目：删除之后项目没了；那条授权是 `revoked`，返回的 `revokedPermissionId` 是它；审计里先有一条 `project.folder_unbound`，再有一条 `project.deleted`（内容还是原来那三项）。
2. 这条授权下导入过的资料：删除之后变成未归属，授权状态是已撤销；资料本身一份不少。`sourcesUnassigned`、`itemsRemoved` 和原来算法一样；个人条目（不属于任何项目的）不动。
3. 别的项目也绑着同一个文件夹：项目删了，授权仍然有效，`revokedPermissionId` 是 null。只有上级文件夹的授权时：上级那条不动，`revokedPermissionId` 是 null。
4. 没绑文件夹的项目：照原来那样删掉；`revokedPermissionId` 是 null、`cancelledTasks` 是 0；审计里没有 `project.folder_unbound`。
5. 删除时有排队、执行中的任务：先取消——执行中的那个执行器收到了取消信号，而且收到的那一刻项目还在、授权还有效；发起它们的对话里有「取消了」的回报；`cancelledTasks` 是取消的个数。之后放行那个执行器：不留下未处理的错误，编排器不再占着「正在执行」（接着给别的项目派任务派得出去）。
6. 项目不存在：拒绝，什么都不变。删除让对话上下文失效（调了 `invalidateContext`）。
7. 清副本：这个项目每个有副本的任务（等接受的、完成的、失败的、取消的都算），副本目录都删掉了，`copiesRemoved` 是个数；审计 `project.task_copies_removed` 一条，内容 `{ projectId, removed, left }`。项目没有任何副本时不记这条审计，两个数都是 0。
8. 清副本的边界：别的项目的任务副本原样还在；**项目文件夹原样还在**（里面的文件一个没少）；某个任务的 `workspace_path` 要是不在数据目录的 `workspaces/` 之内（比如被改成了项目文件夹本身），那个目录原样还在，也不计数。
9. 清副本失败不拦事：有一个副本目录删不掉时（测试里让删除抛错），项目照样删了，`copiesLeft` 是 1，别的副本照删。
10. 界面：没绑文件夹的项目，确认框只有前两段；绑着的三种 `grant` 各一种说法，数字是 0 的行不出现，整段文字逐字核对。取消确认不调 `deleteProject`。确认之后调了、列表重新读过、结果那句话如实（四种成分各自有没有）。出错显示在报错条里；预览出错不问、不删。
11. IPC：`registerIpc` 注册的 `deleteProject` 调的是 `AppRuntime.deleteProject`，返回的和它一样。

## 真机检查

`scripts/real/p8-delete-project.mjs`，照 `scripts/real/p5-unbind-folder.mjs` 的规矩（临时数据目录、随机端口、`IXAEON_EMBED_MODEL=none`、`IXAEON_CODEX_EXE=none`、对话框替身、打印遮掉临时目录、`RESULT` 和退出码一致、脚本出错非零；库里和硬盘上只输出条数、状态、有没有）：

1. 新建项目，绑定合成的 git 文件夹；来源页把它导入一次；任务页建两个草案：一个批准并派发做完（替身执行器，会留下副本），一个批准后停在排队。打印：数据目录 `workspaces/` 下有几个目录、库里这条授权的状态。
2. 项目页点「删除」，**先取消确认**：项目还在，授权还有效，副本个数没变。
3. 再点一次，确认。打印确认框里的文字、结果那句话；打印：项目列表里还有没有它、库里这条授权的状态、这条授权下资料的授权状态各几条、`workspaces/` 下还有几个目录、合成的项目文件夹里的文件还在不在（应当都在）。

结果不对就以非零码退出。输出原样贴进交付说明。
