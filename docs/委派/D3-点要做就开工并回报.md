# 规格 D3：点「要做」就开工，做完回到原来的对话里回报

档位：**A**（本地调度与本地消息，不改提示词、不加外发种类；外发给编码代理仍以用户点「要做」为准）。大小：中（≤250 行源码）。依赖：无（D1 建的任务会带验收条件，没有时回报里不列）。来源：场景一。
v2 规格：验收条件写成测试（`apps/desktop/test/acceptance/d3-*.test.ts`），测试和实现一起交，Codex 审查时核对测试有没有漏掉条件。

## 要什么

现在编码任务要在「任务」页一步步点：批准、派发、接受；做完了也没人告诉你，得自己去任务页看。场景一要的是「你说把 X 做了 → 它做 → 回报」。

## 契约

1. 待办卡上点「要做」（`acceptTodo`，编码任务类）：照旧批准并排队，然后**自动派发**——没有正在执行的编码任务就立刻开始（不阻塞这次点击的返回）；有就排着，前一个结束（完成、失败、取消都算）后按批准先后开始下一个。
2. 找不到 Codex（`resolveCodexLocator()` 为空）：不派发，任务留在已批准；回报「没找到 Codex，装好后在任务页点派发」。任务页的「派发」按钮照旧可用。
3. 回报：任务走到**等你验收**（`pending_accept`）、**失败**、**取消**时，往发起它的那个对话追加一条消息（按 `origin_run_id` 找到那一轮所在的对话）。没有 `origin_run_id` 的任务（任务页手建的、研究发现开的草案）不往任何对话写。
   - 等你验收：目标第一行；验收条件逐条列出（有 `acceptance_json` 时）；验证结果（通过 / 没跑，没跑写原因；没有独立验收时写「还没有独立验收」）；改了哪些文件（最多列 10 个，多了写共几个）；下一步「去任务页看改动，点接受」。
   - 失败：目标第一行 + 原因（任务的 `error`）+ 验证输出的头几行。
   - 取消：一句话。
   - 消息是本地生成的，`meta` 标 `{ kind: 'task_report', taskId, status }`；同一任务同一状态只写一次。
4. 这条消息不调用任何模型。

## 约束

- 不改批准、验证、接受的规则；不改 T2b 的待办卡。
- 同一时间仍只允许一个编码任务在执行。
- 不加迁移。

## 验收条件

1. 点「要做」→ 任务被派发（执行器替身被调用），不用再点「派发」；这次点击立即返回，不等执行结束。
2. 第一个任务执行中又点了第二个「要做」：第二个等第一个结束后才开始，顺序按批准先后。
3. 执行器替身做完、验证通过 → 发起的对话里多一条回报：含目标、每条验收条件、「验证通过」、改动文件；同一状态不重复写。
4. 验证失败 / 执行失败 → 回报含原因；取消 → 一句话回报。
5. 找不到 Codex：不派发，任务停在已批准，对话里回报「没找到 Codex…」。
6. 没有 `origin_run_id` 的任务做完：不往任何对话写。
