# 规格 D5b：验收测试锁定之前，让核心模型对照验收条件核一遍

档位：**B**（新的提示词；把项目里的测试代码发给核心模型，是一种新的外发）。大小：中（核心层约 150 行，桌面接线约 10 行）。依赖：D5a ✅。来源：接力第 35 棒（规划棒），[三周任务单](../三周任务单.md)「接下来一周」第 6 件；用户 09-27 定的「验收把关」后一半（「先写测试，核心模型对照验收条件核一遍有没有漏或放宽，锁定后再实现」）。

## 要什么

D5a 的「验收先行」现在是：写测试 → 实现前跑一遍（不能全过）→ 锁定 → 写实现 → 跑测试。D5b 在「实现前跑一遍」通过、**锁定之前**加一步：

1. 把目标、验收条件、每个测试文件的内容交给**核心模型**（设置里「模型接入」那个、做后台分析用的，`AppRuntime.getProvider()`），让它说：哪条条件没有测试（漏了）、哪条的测试比条件松（放宽了）。
2. 没问题 → 照 D5a 锁定。
3. 有问题 → 把问题交给执行器，让它只改测试目录把测试补好；补完照 D5a 的规矩再跑一遍实现前的检查，再让核心模型核一次。
4. **最多核两次**。第二次还有问题 → 任务停下（记成失败），不写实现；失败原因里写清楚是哪几条、什么问题。
5. 没配核心模型、或者核心模型这一步出错 → 不挡任务：照 D5a 锁定，报告里记下「没核」和原因。

## 为什么

- D5a 只看「实现前不通过」就锁定。测试写得松不松没人管：只断言文件存在、只测一条条件，实现前一样不通过，锁定之后「验证通过」就是空话。10-06 整合方在真网关上看到的那次两条测试是紧的，换个任务未必。
- 这是用户 09-27 定下的，不是整合方新加的方向。

## 契约（接口写死）

1. **注入**：`CodingOrchestrator` 的构造函数加第 5 个可选参数 `testReviewer?: () => ModelProvider | null`（每次要核时现调一次）。不传 → 行为和 D5a 一字不差（D5a、D1、D3、D4、P4、P6 这些锁定测试都不传）。
   桌面端两处 `new CodingOrchestrator(`（`apps/desktop/src/main/appRuntime.ts` 第 274、2591 行附近）传 `() => runtimeRef.current?.getProvider() ?? null` / `() => this.getProvider()`。
2. **什么时候核**：只在 D5a 走到「要锁定」的那一刻（`files.length > 0`、没有沙箱拒跑、实现前没有全过，即 D5a 里 `reason === null`）。别的分支（没写出测试、全过、拒跑）不核。
3. **怎么问**：`provider.chatStructured({ system, user, schema })`。
   - `system` 原文（写死）：
     ```
     你在检查一组验收测试写得够不够。只看测试和验收条件对不对得上，不评价代码风格，不提条件以外的要求。
     对每条验收条件判断：
     - missing：没有任何测试在检查这条条件；
     - loose：有测试，但条件不成立时这个测试照样会通过（比如只查文件存在、只查函数存在、断言的值和条件说的不一样、只测了条件的一部分）。
     没有问题就返回空列表。每个问题写清楚是第几条条件、哪个测试文件、差在哪里，一两句话。
     ```
   - `user`：`要做的事：\n<任务的 goal>\n\n验收条件：\n1. …\n2. …\n\n测试文件：` 之后每个文件 `--- <相对路径> ---\n<内容>`。单个文件超过 20000 字截断并在末尾加 `\n…（后面截掉了）`；所有文件合起来超过 60000 字，后面的文件只写路径和 `（太长，没有发）`。
   - `schema`（zod）：`{ problems: Array<{ condition: number /* 整数 */; kind: 'missing' | 'loose'; detail: string }> }`。
   - 拿到之后：`condition` 不在 1..条件数里的问题丢掉；`detail` 去首尾空白后为空的丢掉。剩下的为空 → 算没问题。
4. **补测试那一步**：再调一次执行器，和 D5a 第 1 步同样的限制（`scope_json` 只有测试目录，原批准范围只读），`goal` 是：
   ```
   这一步只改验收测试，不要写实现。
   要做的事：
   <goal>

   验收条件：
   1. …

   检查的人说这些测试有问题：
   - 条件 N（漏了 | 太松）：<detail>
   …

   怎么改：照原来写测试的规矩（<D5a writeTestsBrief 里「怎么写：」那一段原样>），只改 <testDir>/ 下的文件，把上面的问题补上。
   ```
   补完照 D5a 第 1、2 步原样核：改了测试目录以外的文件 → 失败（原文 `写验收测试时改了别的文件：…`）；重新列文件；实现前跑一遍；跑的时候改了文件 → 失败；拒跑或全过 → 走 D5a 对应的「不锁定」分支（不再核）。执行器这一步报错 → 失败，原因 `补验收测试时执行器出错：<clip(报错的话)>`。每个 `await` 之后照 D5a 查取消。
5. **最多两次**：第 1 次核有问题 → 补 → 第 2 次核。第 2 次还有问题 → `failNow`，原因（写死，每条问题一行）：
   ```
   核心模型核了两次，验收测试还有问题，没有写实现：
   - 条件 N（漏了 | 太松）：<detail>
   ```
   整段截到 2000 字。
6. **不挡任务的情况**：`testReviewer` 返回 `null` → 不核，照 D5a 锁定，`review = { status: 'skipped', rounds: 0, problems: [], note: '没有配置核心模型' }`。`chatStructured` 抛错（网络、额度、格式不对）→ 不再重试，照 D5a 锁定（若已补过一次，锁补过之后的那份），`review = { status: 'error', rounds: <已核成的次数>, problems: <最近一次核出的>, note: clip(错误的话) }`。错误的话里不许带 Key、地址（`ModelError` 的 message 现在本来就不带；实现时核一遍）。
7. **记下来**：`ExecutorReport['acceptanceTests']` 加可选字段 `review?: { status: 'passed' | 'skipped' | 'error' | 'failed'; rounds: number; problems: { condition: number; kind: 'missing' | 'loose'; detail: string }[]; note: string | null }`。`passed` = 某一次核下来没问题（`rounds` 是 1 或 2）；`failed` 只出现在契约第 5 条那种失败里（失败时也把带 `review` 的报告写进 `executor_report_json`）。不走核这一步的任务没有这个字段。
8. 发给核心模型的测试内容先过 `hideWorkspacePath`（D5a 已有）——测试文件里要是写了副本的绝对路径，不把本机用户名发出去。

## 约束

- 只改 `packages/core/src/execution/executor.ts`（可以把核对的提示词和拼装放进同目录新文件 `testReview.ts`）、`packages/core/src/index.ts`（导出要导出的）、`apps/desktop/src/main/appRuntime.ts` 那两处构造。界面不改：失败原因卡片上本来就显示；「核心模型核过」要不要显示在卡片上，等用户试过再说。
- 已锁定的测试一个字不改。D5a 的提示词（契约 5 那三段）不改。
- 不新增设置项、不新增迁移。核心模型就是现在做后台分析的那个，不另选。
- **冲突风险（审测试时要查）**：桌面端在 `IXAEON_FAKE_MODEL=1` 下 `getProvider()` 给的是 FakeProvider，它的结构化队列是按顺序取的——D5a 的端到端（`apps/desktop/e2e/d5a-acceptance-first.spec.ts`）和 `d5a-executor-options` 里，核这一步可能吃掉本来给后面步骤的预置响应，或者拿到形状不对的东西走进契约第 6 条的「出错」分支。开发写测试时先跑一遍这两份，撞红了写进交付说明，**不改**，整合方审测试时处理。

## 验收条件（写成 `packages/core/test/acceptance/d5b-review-tests.test.ts`，照 `d5a-acceptance-first.test.ts` 的搭法：替身执行器 + 替身 `ModelProvider`）

1. 不传 `testReviewer` → 和 D5a 一样锁定，报告里 `acceptanceTests` 没有 `review` 字段；替身模型一次都没被调用。
2. `testReviewer` 返回 `null` → 锁定，`review.status === 'skipped'`、`note === '没有配置核心模型'`。
3. 第 1 次核没问题 → 锁定，`review` 为 `{ status: 'passed', rounds: 1, problems: [] , note: null }`；执行器一共被调 2 次（写测试、写实现）。
4. 发给模型的 `system` 与契约第 3 条逐字相等；`user` 里有 goal、编了号的每条条件、每个测试文件的路径和内容；副本的绝对路径被换成 `<副本>`。
5. 第 1 次有问题、补过之后第 2 次没问题 → 锁定，`rounds: 2`、`status: 'passed'`；执行器一共被调 3 次，第 2 次的 `goal` 含契约第 4 条的原文和问题那几行，`scope_json` 只有测试目录；锁定的是补过之后的文件（写实现时改补过的文件 → `实现时改了验收测试`）。
6. 两次都有问题 → 任务 `failed`，`error` 与契约第 5 条逐字对得上；写实现那一步没被调；报告里 `review.status === 'failed'`、`rounds: 2`。
7. 补测试时改了测试目录以外的文件 → `failed`，`写验收测试时改了别的文件：…`。
8. 补过之后实现前全部通过 → 不锁定、不再核，原因照 D5a（`验收测试在实现之前就全部通过，测不出这次改动`）；模型一共只被调 1 次。
9. 补测试时执行器抛错 → `failed`，原因以 `补验收测试时执行器出错：` 开头。
10. 第 1 次核时模型抛错 → 锁定原来的测试，`review.status === 'error'`、`rounds: 0`、`note` 是错误的话；第 1 次有问题、补过、第 2 次抛错 → 锁定补过之后的测试，`status: 'error'`、`rounds: 1`。
11. 模型返回的问题里 `condition` 是 0、超过条件数、`detail` 是空白 → 都丢掉；全丢掉了就算没问题（第 3 条那样锁定）。
12. 单个测试文件超过 20000 字 → `user` 里那个文件截断并带 `…（后面截掉了）`；合起来超过 60000 字 → 后面的文件只有路径和 `（太长，没有发）`。
13. 核的时候、补的时候取消 → 任务 `cancelled`，不再调模型、不再调执行器。
14. 走不到「要锁定」的任务（没写出测试、实现前全过、沙箱拒跑、带验证命令的、没有验收条件的）→ 模型一次都不调，结果与 D5a 一字不差。
