# 委派单 A1：分析失败耐心重试

任务来源：[三周任务单](../三周任务单.md) A1。档位：**A**（CI 绿即可由用户合并）。大小：小到中（≤200 行）。

## 背景

2026-09-18 真机：模型网关断了几个小时，23 个分析任务各自在约 2.5 分钟内重试 3 次（5 秒、30 秒、2 分钟）后判为失败，用户只能到「资料」页手动点「全部重新分析」。另外 429（账号并发满、限流）现在算不可重试的失败，一次就判死。

目标：导入以后不用人盯着。网关、网络、限流这类暂时性问题，任务自己耐心等、自己接着做；「资料」页如实显示「在等重试」，不显示成失败。

## 契约（写死，照着实现，不改名）

1. `packages/core/src/jobs/jobQueue.ts` 导出 `DEFAULT_RETRY_BACKOFF_MS: number[]`，并从 `packages/core/src/index.ts` 导出。至少 8 项；第一项 ≤ 10 秒；不递减；单项 ≤ 1 小时；合计 ≥ 4 小时。
   - `new JobQueue(db, logger)` 不传 opts 时按这张表退避。
   - **自动重试上限默认等于所用退避表的长度**。传了自定义 `retryBackoffMs` 时同样按它的长度——现有 `packages/core/test/integration/m0-core.test.ts` 用 `[30, 30, 30]`、期待重试 3 次，那个测试不许改。
2. `packages/core/src/extraction/model/openai.ts`：HTTP 429 抛出的 `ModelError` 为 `retriable: true`。5xx 照旧是 true，其余 4xx 照旧 false。
3. `JobQueue.requeueNetworkFailures(): number`：把**状态为 failed、错误是网络/网关/限流类**的任务重新排队（`status='queued'`、`retry_count=0`、`not_before=NULL`、`error=NULL`），返回条数。
   - 认定规则写死：错误文字以「网络错误」开头，或以「API 错误 429」「API 错误 5xx」开头。
   - 内容类（依据对不上原文等）、认证类（401/403）失败不动。
4. `apps/desktop/src/main/appRuntime.ts`：启动时、任务队列开始跑之前调用一次 `requeueNetworkFailures()`；条数大于 0 时记一条日志。
5. `SourceStore.list()` 返回的 `analysis` 增加 `lastJobRetryCount: number` 与 `lastJobNextAt: string | null`，即最近一次提取任务的 `retry_count` 与 `not_before`。界面用到的类型同步加上。
6. 「资料」页（`apps/desktop/src/renderer/src/pages/Sources.tsx`）：最近一次任务是 `queued` 且 `lastJobRetryCount > 0` 时，显示「模型网关暂时不通，第 k 次自动重试，约 N 分钟后」（`data-testid="source-retry-<来源 id>"`；不到 1 分钟显示「马上」），不显示成失败。
