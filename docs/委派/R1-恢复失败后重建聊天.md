# 规格 R1：数据恢复失败回滚后，聊天存取与语义索引也要重建

档位：**A**。大小：小（≤150 行）。依赖：无。v2 规格：你先把下面的验收条件写成测试（`apps/desktop/test/acceptance/r1-*.test.ts`），再实现。

## 要什么

数据恢复失败、但磁盘回滚完整时，`AppRuntime` 走 `rebuildRuntimeServices()`（`apps/desktop/src/main/appRuntime.ts`）：重开数据库，按新连接重建各项服务，应用继续运行。

有两样漏了：`conversations`（`ConversationStore`）和 `semanticIndex` 只在构造函数里用最初的数据库连接建过一次，重建时没换。回滚之后它们还拿着已经关闭的旧连接——聊天列表、打开对话、提问全部报「database connection is not open」，只能重启应用。

## 为什么

2026-09-19 整合方复审 T3 时发现（T3 给新加的 `todos` 做了重建，暴露出旧字段没做）。这条路很少走到，但走到时聊天整个坏掉，用户看不出原因。

## 约束

- 不加迁移；不改恢复流程本身（回滚、故障状态那套逻辑不动）。
- 两个字段改成可以重新赋值（去掉 `readonly`），在 `rebuildRuntimeServices()` 里和其它存取一起重建。
- 建语义索引的逻辑（看 `IXAEON_EMBED_MODEL`，`none` 或空就不建）抽成一个小函数，构造函数和重建共用，不要复制一份。
- 语义索引如果有后台工作（回填、定时器），先停掉旧的再换新的。
- 顺手查一遍构造函数里其它用最初数据库连接建的对象或闭包，有同样问题的一起修，写进交付说明。

## 验收条件

1. 恢复失败、回滚完整之后，`runtime.conversations` 能新建对话、列出对话、追加一条消息，都不抛错。
2. 回滚之后，语义索引开着时用的是新连接（查状态、检索不抛错）；嵌入模型设为 `none` 时仍然是 `null`。
3. 回滚之后旧语义索引的后台工作不再跑（如果它有的话；没有就在测试注释里写明）。

测试可以照 `apps/desktop/test/` 里现有的恢复失败测试搭（搜 `rebuildRuntimeServices` 或「回滚」）。

## 真机检查

不需要：纯内部修复，验收测试覆盖。交付说明里写「规格不要求真机检查」。
