# 规格 V4：依赖档验证的授权入口

档位：**B**（权限：让用户发起一次系统授权；改了验证结果里给用户和模型看的话）。大小：中（≤250 行源码）。依赖：无。来源：队列「整合方正在设计」里原来叫「D6 依赖档的授权入口」的那一件；`D6` 这个编号第 1 周已经用过（聊天界面重写），改叫 V4，和验证沙箱的 V1、V3 放一类。

v2 规格：先把验收条件写成测试（`packages/core/test/acceptance/v4-*.test.ts`、`apps/desktop/test/acceptance/v4-*.test.ts`），**先只推测试**，整合方看过并锁定后再写实现。

## 要什么

编码任务做完要独立验证。验证分档（D2）：零依赖的测试在 Node 的权限模型里直接跑；**带 npm 依赖的**（验证命令写成 `ixaeon:vitest run …`）要进 Codex 的提权沙箱跑——不能联网、只能写任务副本。提权沙箱要这台机器先授权一次：Windows 弹一次管理员确认，Codex 装好它的沙箱（两个专用的本机账户、一个 Windows 服务、几条防火墙规则；机器级，装过的不重装），再在 IXAEON 的数据目录里记下这次授权。之后跑验证就不再问。Codex 升级以后要再授权一次。

核心层 D2 时就写好了：`checkSandboxAuth`（只查，不弹窗）、`requestSandboxAuth`（发起授权，会弹窗）。**桌面应用里一处都没接**：

- 用户没有地方授权。带依赖的项目，验证每次都停在「没跑成」。
- 「没跑成」的原因原样写着英文代码：回报和任务卡片上是「验证没跑：依赖档沙箱检查未过：unauthorized，不派生，不算验证。」用户看不懂，也不知道去哪儿修。

这一单：设置页加一块「依赖档验证」，显示授权了没有，没授权时给一个「授权」按钮；验证没跑成时把原因说成人话、告诉用户去哪儿授权。

### 整合方在本机查到的（只读）

`%LOCALAPPDATA%\OpenAI\Codex\bin\` 下顶层的 `codex.exe` 是 2026-05 的 0.130 版；Codex 桌面应用自己更新的新版（10 月的 0.163 版）在一个带哈希的子目录里。IXAEON 找 Codex 的办法有两套，现在不一致：

- 执行器（`resolveCodexLocator`）：先看环境变量 `IXAEON_CODEX_EXE`（`none` = 不用 Codex），再看顶层的 `codex.exe`。
- 沙箱检查（`locateCodexExecutable`）：不看环境变量；先看顶层，没有再按目录名顺序翻子目录，取第一个有 `codex.exe` 的（不一定是最新的）。

授权是和某一个版本的 Codex 配对的（检查时要找那个版本的 helper），两套办法找到的要是不同的 Codex，授权了也会被判成没授权。**这一单把两套并成一套，照执行器的办法**（不改执行器现在用哪个 Codex）。要不要改用最新的那个，是另一件事，见文末「要用户定的」。

## 契约（接口写死，不改名、不加字段）

1. **类型**（`packages/contracts/src/entities.ts`）：

   ```ts
   /** V4：依赖档验证用的 Codex 沙箱，这台机器授权了没有。 */
   export interface VerifySandboxView {
     /** ok = 授权了，依赖档验证跑得了；其余三种跑不了。 */
     status: 'ok' | 'unauthorized' | 'codex_missing' | 'unsupported_platform';
     /** 用的是哪个版本的 Codex 命令行（`codex --version` 里的版本号，比如 0.130.0-alpha.5）；没找到 Codex 是 null。 */
     codexVersion: string | null;
   }
   ```

2. **两个新接口**（`packages/contracts/src/ipc.ts`、`apps/desktop/src/main/ipc.ts`、`apps/desktop/src/preload/index.ts` 三处；业务逻辑放在 `AppRuntime` 上的同名方法，IPC 只转一下）：

   ```ts
   /** 只查：不弹窗、不写任何文件、不记审计。 */
   getVerifySandbox(): Promise<VerifySandboxView>;
   /** 发起一次授权（Windows 会弹一次管理员确认），等它结束再查一遍，返回查到的。 */
   authorizeVerifySandbox(): Promise<VerifySandboxView>;
   ```

   - 两个都用应用的数据目录（`AppRuntime.dataDir`）。
   - `authorizeVerifySandbox`：调一次 `requestSandboxAuth(dataDir)`，不管它说成没成，接着 `checkSandboxAuth(dataDir)`，返回后者的结果。记一条审计 `verify_sandbox.authorize`，内容 `{ status }`（查到的那个状态，四选一）。
   - **只有设置页那个按钮会调 `authorizeVerifySandbox`。** 应用启动、打开设置页、派任务、跑验证，都不许调 `requestSandboxAuth`（无人值守时绝不弹窗，D2 定的）。

3. **核心层**（`packages/core/src/execution/verifySandbox.ts`、`executor.ts`）：

   1. **找 Codex 只有一套办法**：沙箱检查和发起授权都照执行器 `resolveCodexLocator` 的办法找——`IXAEON_CODEX_EXE` 设了就用它（`none` 就当没有 Codex，结果是 `codex_missing`）；没设就用 `<LOCALAPPDATA>\OpenAI\Codex\bin\codex.exe`；**不再翻子目录**。具体怎么并（让一个调另一个，还是抽一个两边都用的函数）由实现定，但两边找到的必须是同一个文件。
   2. **不卡住窗口**：`checkSandboxAuth`、`requestSandboxAuth` 里不许用 `spawnSync`。它们跑在 Electron 的主进程里：`requestSandboxAuth` 要等用户在 Windows 的确认框上点完，最长 120 秒，用 `spawnSync` 的话这段时间整个窗口都不动；`checkSandboxAuth` 每次也要跑 `codex --version` 和 `sc query`。改成异步的子进程，超时照旧（20 秒、15 秒、120 秒）。函数的名字、参数、返回类型都不变。
   3. **版本号拿得到**：`VerifySandboxView.codexVersion` 要的版本号，和授权检查用的是同一个 Codex。核心层导出一个拿它的办法（名字由实现定）。
   4. **没跑成的原因说人话**：`checkDependencyTier` 里授权检查没过时，验证输出（`verify_output`）现在是「依赖档沙箱检查未过：<英文代码>，不派生，不算验证。」，换成下面三句之一（逐字）：

      | 原因                   | 验证输出                                                                                           |
      | ---------------------- | -------------------------------------------------------------------------------------------------- |
      | `unauthorized`         | 这台机器还没给 Codex 沙箱授权，依赖档验证跑不了：到设置页「依赖档验证」点「授权」。授权之后新派的任务才会跑这一档验证。 |
      | `codex_missing`        | 没找到 Codex 命令行，依赖档验证跑不了（这一档要用 Codex 的沙箱）。                                 |
      | `unsupported_platform` | 依赖档验证只在 Windows 上跑得了。                                                                  |

      回报里那一行照旧是「验证没跑：<验证输出>」（`taskReport.ts` 的 `verifyLine` 不改），任务卡片上照旧显示验证输出。这几句会随回报进对话、再随对话历史发给模型。

   D2 定下的别的都不动：沙箱配置、`-C` 用数据目录里的专用空目录、派生环境走白名单、检查口径（四样缺一就算没授权）。

4. **界面**（`apps/desktop/src/renderer/src/pages/Settings.tsx`）：

   - 「编码任务交给谁」那一块后面加一块「依赖档验证（Codex 沙箱）」（`testId="settings-verify-sandbox"`）。
   - 打开设置页时调一次 `getVerifySandbox`（不定时刷新）。没拿到结果之前这一块显示「正在查……」。
   - 状态那句话（`data-testid="settings-verify-sandbox-status"`），按 `status` 四选一（逐字；`<版本>` 是 `codexVersion`）：

     | status                 | 显示                                                                                                   |
     | ---------------------- | ------------------------------------------------------------------------------------------------------ |
     | `ok`                   | 已授权（Codex <版本>）。带 npm 依赖的项目，验收测试在 Codex 的沙箱里跑：不能联网，只能写任务副本。      |
     | `unauthorized`         | 还没授权（Codex <版本>）。带 npm 依赖的项目，验收测试现在跑不了。授权一次就行；Codex 升级之后要再授权一次。 |
     | `codex_missing`        | 没找到 Codex 命令行，依赖档验证跑不了。                                                                |
     | `unsupported_platform` | 依赖档验证只在 Windows 上跑得了。                                                                      |

   - 只有 `unauthorized` 时显示按钮「授权」（`testId="settings-verify-sandbox-authorize"`）。
   - 点了先用 `window.confirm` 问（逐字）：

     ```
     给 Codex 沙箱授权？

     Windows 会弹一次管理员确认。同意之后，Codex 会在这台机器上装好它的沙箱：两个专用的本机账户、一个 Windows 服务和几条防火墙规则（已经装过的不重装）。之后跑依赖档验证不用再问。

     只有点这个按钮才会弹；任务在后台跑的时候绝不弹。Codex 升级之后要再点一次。
     ```

   - 取消：什么都不发生。
   - 确认：按钮变成不可点、文字是「授权中……（等 Windows 的确认）」；调 `authorizeVerifySandbox`；拿到结果后，状态那句话按新结果换掉，并显示一句（`data-testid="settings-verify-sandbox-message"`）：结果是 `ok` →「授权好了。」；其余 →「没授权成：可能是 Windows 的确认被取消了，也可能是 Codex 的沙箱没装好。可以再点一次。」
   - 出错（两个接口抛错）：显示在这一页现有的报错条里。

## 约束

- 不加迁移。不删数据。
- 测试里**绝不真的调 `requestSandboxAuth`**（会在跑测试的机器上弹窗），一律用替身。真的发起授权只有用户自己点。
- 真机检查**不许点「授权」**：那会在用户的电脑上弹管理员确认、装系统账户和服务。授权真的能不能成，由用户在并入之后自己点一次，整合方在旁边看结果（见文末）。
- 不改执行器现在用哪个 Codex；不改零依赖档。
- 测试、交付说明里的路径用合成的；版本号用合成的（比如 `9.9.9`）。

## 验收条件

核心层（`packages/core/test/acceptance/`）：

1. **找 Codex 只有一套**：在一个合成的 `LOCALAPPDATA` 下，顶层放一个 `codex.exe`、子目录里再放一个：`checkSandboxAuth` 用的是顶层那个（执行器 `resolveCodexLocator` 找到的也是它）。只有子目录里有、顶层没有：`codex_missing`（不再翻子目录）。`IXAEON_CODEX_EXE` 指向一个文件：用它；设成 `none`：`codex_missing`。`requestSandboxAuth` 找 Codex 的办法和它一样。
2. **不卡住窗口**：`checkSandboxAuth`、`requestSandboxAuth` 跑的时候 `node:child_process` 的 `spawnSync` 一次都没被调（测试里把它换成一调就抛错的替身，异步的子进程换成按脚本回话的替身）。
3. **检查口径不变**：四样（`cap_sid` 三类、版本配对的 helper、setup 标记、服务 RUNNING）齐了是 `ok`；缺任何一样是 `unauthorized`；`codex --version` 说不出版本号是 `unauthorized`；不是 Windows 是 `unsupported_platform`。`checkSandboxAuth` 不往数据目录写任何东西。
4. **版本号**：拿版本号的那个办法，和 `checkSandboxAuth` 问的是同一个 Codex，返回 `codex --version` 里的版本号；没有 Codex 返回 null。
5. **没跑成的原因**：依赖档验证在三种授权没过的情况下，验证输出是契约 3.4 表里那一句（逐字），`ran` 是 false，没有派生任何子进程去跑测试；回报里那一行是「验证没跑：」接这一句。

桌面（`apps/desktop/test/acceptance/`）：

6. **只查不弹**：`AppRuntime.getVerifySandbox()` 返回 `{ status, codexVersion }`，四种状态各一条；它没调 `requestSandboxAuth`，没记审计，数据目录里没有多出文件。
7. **发起授权**：`AppRuntime.authorizeVerifySandbox()` 调了一次 `requestSandboxAuth`（参数是数据目录），之后调了 `checkSandboxAuth`，返回后者的结果；`requestSandboxAuth` 说成了、再查却是 `unauthorized` 时，返回 `unauthorized`。审计 `verify_sandbox.authorize` 一条，内容 `{ status }`。
8. **别处不弹**：应用里除了 `authorizeVerifySandbox`，没有别的路径调 `requestSandboxAuth`：派一个依赖档的任务、跑完验证，`requestSandboxAuth` 一次都没被调。
9. **IPC**：`registerIpc` 注册了 `getVerifySandbox`、`authorizeVerifySandbox`，调它们得到的和 `AppRuntime` 上的方法一样。
10. **设置页**：打开时调了一次 `getVerifySandbox`；那一块排在「编码任务交给谁」后面；四种状态各显示契约 4 的那句话（逐字，带版本号）；只有 `unauthorized` 有「授权」按钮。
11. **设置页，点「授权」**：确认框文字逐字；取消不调 `authorizeVerifySandbox`；确认之后调了一次，等结果的时候按钮不可点、文字是「授权中……（等 Windows 的确认）」；结果是 `ok` → 状态换成「已授权」那句、显示「授权好了。」、按钮没了；结果是 `unauthorized` → 显示「没授权成」那句、按钮还在；出错显示在报错条里。

## 真机检查

`scripts/real/v4-verify-sandbox.mjs`，照 `scripts/real/p7-revoke-reading.mjs` 的规矩（临时数据目录、随机端口、`IXAEON_EMBED_MODEL=none`、打印遮掉临时目录的两种写法、只有全都符合才写「通过」、`RESULT` 和退出码一致、脚本出错非零）。**全程不点「授权」，不让真的 Codex 执行任何任务。**

1. `IXAEON_CODEX_EXE=none` 启动：打开设置页，打印「依赖档验证」那句话（应当是「没找到 Codex 命令行」），确认没有「授权」按钮。
2. 不设 `IXAEON_CODEX_EXE` 启动（用这台机器上的 Codex，临时数据目录里没有授权记录）：打开设置页，打印那句话（应当是「还没授权」，带版本号），确认有「授权」按钮，**不点**。打印显示的版本号和顶层 `codex.exe` 的 `--version` 一样不一样。
3. `IXAEON_CODEX_EXE=none`，用执行器替身：建一个合成项目（带一个占位的 `node_modules/vitest/vitest.mjs`，让验证走到授权检查那一步），派一个验证命令是 `ixaeon:vitest run` 的任务。打印回报里验证那一行（应当是「验证没跑：没找到 Codex 命令行……」）。

结果不对就以非零码退出。输出原样贴进交付说明。

## 并入之后，用户自己试一次（不是这一单的验收条件）

整合方并入后，请用户在自己的应用里打开设置页「依赖档验证」，点「授权」，在 Windows 的确认框上点「是」，看状态是不是变成「已授权」。这一步会改系统（装沙箱账户、服务、防火墙规则），所以只由用户自己点；整合方事先在对话里说清楚会装什么，用户同意了才开始。

## 要用户定的（不挡这一单）

IXAEON 现在用的是顶层那个 5 月的 Codex（0.130），桌面应用自己更新的 0.163 在子目录里。要不要改成用最新的那个？改了的好处是编码任务用上新版；坏处是桌面应用每次更新，沙箱都要重新授权一次（授权和版本配对）。这一单不动它，照现在的。
