# 委派单 D4c：建分支失败时带上 git 的原话，查清 CI 上那条偶发

档位：**A**（修 bug）。大小：小。依赖：无。来源：CI 上 D4 的锁定测试「真实 IPC 入口：点『接受』走的那条通道也触发落地回报」偶发失败，已经两次（Q2 那一轮、2026-10-23 L5/L6 并入时），重跑就绿。报错只有「建分支失败：Command failed: git … commit -m …」，git 自己说了什么看不到，所以查不出原因。

## 要什么

1. **报错带上 git 的原话**：`packages/core/src/execution/landing.ts` 里建分支失败的那段（`catch` 里拼 `建分支失败：${why}`），现在只取错误信息的第一行，git 写在错误输出（`stderr`）里的原话丢了。改成：`why` 后面接上 git 错误输出里**第一条非空的行**（去掉首尾空白，最多 200 字）。没有错误输出就照旧。这句话会进对话里的落地回报，用户也看得到——比「Command failed」有用。
2. **查清 CI 上为什么偶发**：先在本机复现（单独连跑那一个测试 30 遍；再在机器忙的时候跑，照 `scripts/real/q2-flaky-repro.mjs` 的做法，占 CPU 的进程限时 2 分钟）。有了 git 的原话，下次 CI 再红就知道是什么。几个可疑的方向（只是猜）：同一个任务被「接受」触发了两次落地、两次在同一个工作树里提交（第二次「没东西可提交」或者撞上 `index.lock`）；杀毒软件或别的进程捏着 `index.lock`。
3. **查到了就治本**（改应用源码），**查不到就如实写**：试了什么、跑了几遍、红了几遍。

## 约束

- D4 的锁定测试不许改（指纹在 `docs/委派/锁定验收.json`）。另加测试可以：比如造一个一定会让 `git commit` 失败的场景，断言落地回报里有 git 的原话。
- 不许放宽、删断言，不许在断言外面套重试。
- 不碰用户的真实数据；测试全在临时目录。

## 验收

- 新加的测试：建分支失败时，回报里有 git 错误输出的那一行。
- `node scripts/acceptance.mjs run D4` 全过；`node scripts/verify.mjs` 全过。
- 交付说明 `docs/委派/交付/D4c.md`：复现记录（跑了几遍、红了几遍、红在哪）、原因（或者「没查到」）、怎么治的。
- A 档：`node scripts/codex-review.mjs D4c`，照 AGENTS.md 合并。
