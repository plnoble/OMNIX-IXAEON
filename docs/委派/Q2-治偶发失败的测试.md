# 规格 Q2：治偶发失败的测试

档位：**A**（只改测试和测试配置，不改应用源码；改不了的写清楚交给整合方）。大小：小到中。依赖：无。来源：2026-10-20 整合方排的；接力调度器要 24 小时转，门禁里的偶发失败会让它无缘无故停下。

## 要什么

这几天门禁和 CI 里冒出过的偶发失败（同样的内容，有时红、重跑就绿）：

| 在哪 | 报的什么 | 谁见到的 |
| ---- | -------- | -------- |
| `review-recheck-ui` 的 `BUI01` | `Test timeout of 30000ms` | D2c 本机 verify |
| integration 的 `d3-d4` | `Electron failed to install correctly` | L0 本机 verify |
| D3、D4 的计时类验收测试 | 机器忙的时候超时 | 整合方本机（杀毒软件占 CPU 时） |
| `review-recheck` 的 `B04` | `Hook timed out in 10000ms` | C3a 的 CI（**已修**：整合方补了 `hookTimeout`） |

一个一个查清楚**为什么偶发**，治本。

## 步骤

1. 每一条先**复现**：单独连跑（比如 20 遍），再在机器忙的时候跑（同时开一个占 CPU 的进程），记下红了几遍、红在哪一行。复现不出来的，写清楚试了什么。
2. 找原因。常见的几类：等一个固定的时间而不是等条件；测试之间共用了没清干净的东西（端口、临时目录、单例）；起 Electron 太慢；文件被别的进程占着；`node_modules/electron` 被并行的安装动过。
3. 治：
   - **治本，不放宽**：把「等固定时间」改成「等条件成立（带上限）」、把共用的东西隔开、把慢的准备挪出计时区。
   - **不许**删断言、放宽断言、把重试包在断言外面「多试几次总会过」。调大超时只在「这件事本来就慢、而且写清楚为什么慢」时可以，并写进交付说明。
   - **已经锁定的验收测试不许改**（D3、D4 那几条就是）：查清原因，把「该怎么改」写进交付说明，交给整合方。
4. 治完的每一条，按第 1 步的办法再跑一遍，贴前后对比（红几遍 → 红几遍）。

## 范围

- 可以改：`apps/*/test/review/`、`apps/*/test/integration/`、`packages/*/test/integration/`、`packages/*/test/unit/` 下的测试和它们的 vitest 配置；`apps/desktop/e2e/`。
- **不许改**：应用源码（`apps/*/src`、`packages/*/src`）；`docs/委派/锁定验收.json` 里登记的锁定测试；门禁脚本 `scripts/verify.mjs`。真要动这些才能治的，写进交付说明，交给整合方。

## 验收标准

1. 交付说明 `docs/委派/交付/Q2.md`：上表每一条一节——怎么复现的、红了几遍、原因、怎么治的（或者为什么交给整合方）、治后再跑几遍的结果。
2. 改过的测试，断言一条没少、一条没放宽（Codex 审查时核对这一条）。
3. 本机 `node scripts/verify.mjs` 全过；推送后 CI 绿。
4. A 档：`node scripts/codex-review.mjs Q2`，照 AGENTS.md 合并。

## 风险

- 机器忙的时候跑（占 CPU）别把用户的电脑拖死：占 CPU 的进程限时（比如 2 分钟），跑完就停。
- 反复起 Electron 时，测试用的都是临时数据目录；不碰用户开着的 IXAEON。
