# 委派单 P2：等待回答时显示进度

任务来源：[三周任务单](../三周任务单.md) P2。大小：**小到中（≤200 行改动）**。

前置：S1/S2（回答逐字显示）已并入，本任务照它的写法做：`askDeltaSink`、`cancelledAskRuns`、界面里按 `conversationId` + 消息 id 认这一轮。

## 背景

2026-09-18 实测一问的时间线（真 Hermes）：

| 阶段 | gemini flash | grok-4.6 |
| --- | --- | --- |
| 新会话组装，期间没有任何输出 | 9 秒 | 5 秒 |
| 模型思考（第一个字之前） | 6 秒 | 22 秒 |
| 正文输出 | 一次性到达 | 约 1 秒 |

用户在这 15–30 秒里只看到一个写着「正在回答…」的转圈（`apps/desktop/src/renderer/src/pages/AskMessage.tsx` 第 67 行），分不清是在准备、在思考还是卡住了。本任务让等待气泡说清楚现在在干什么、已经等了多久。

## 契约（已定死，照着实现，不要改名、不要加字段）

```ts
// packages/contracts/src/ipc.ts
export type AskPhase = 'preparing' | 'thinking' | 'answering';
export interface AskProgressEvent {
  conversationId: string;
  messageId: string; // 占位的助手消息 id
  phase: AskPhase;
}
// IxaIpcApi 新增（preload 用 ipcRenderer.on('ixaeon:ask-progress', …) 实现，返回取消订阅函数）
onAskProgress(listener: (e: AskProgressEvent) => void): () => void;
```

主进程 → 界面的通道名：`ixaeon:ask-progress`。**事件里不带任何思考内容。**

## 阶段怎么判定（写死）

`AgentSession.run()`（`packages/core/src/runtime/session.ts`）入参加可选的 `onProgress?: (phase: 'thinking' | 'answering') => void`，在现有 `wireEventLedger` 的事件回调里判定（与 `onDelta` 同一处，同样用 try/catch 兜住）：

- **thinking**：以下任一事件**第一次**出现时——`payload.phase === 'message.start'`；或 `payload.unhandled` 为 `thinking.delta`、`reasoning.delta`、`reasoning.available` 之一。
- **answering**：第一段回答正文到达时（与 `onDelta` 的条件相同：`kind === 'text'` 且 `payload.delta` 是字符串）。
- 每个阶段每轮**最多报一次**；**只进不退**——已经 answering 之后再来的思考事件一律忽略。
- Core 兜底路径（没有 Hermes）：第一次调用模型前报 thinking；不报 answering（回答是整段到的）。

`AppRuntime.ask()`（`apps/desktop/src/main/appRuntime.ts`）：

- 占位的助手消息一建好，**立刻**报 `preparing`（在等补向量之前）；
- 把 core 报的阶段转成 `AskProgressEvent` 推给界面：新增 `setAskProgressSink(fn)`，在 `apps/desktop/src/main/index.ts` 里与 `setAskDeltaSink` 放在一起设置；
- 用户取消后不再推这一轮的进度；推送出错兜住，不影响回答。

## 界面（`AskMessage.tsx` 的等待态 + `Ask.tsx` 的订阅）

- 等待气泡按阶段显示，后面带**从发出问题起**的秒数，每秒更新：
  - 还没收到任何进度事件、或 `preparing`：`正在准备…（N 秒）`
  - `thinking`：`正在思考…（N 秒）`
  - `answering`：正文已经在逐字出现，标签改为 `正在回答…`，不再显示秒数
- 只认这一轮、且是当前显示的对话（照 S2 的匹配方式：`conversationId`，消息 id 或占位 id）。
- 回答结束、失败或取消后，计时停止（消息离开 streaming 状态即可）。
- 组件卸载时取消订阅、清掉计时器。

## 验收条件（写死；执行方不改）

1. **core 集成测试**（协议替身，照 `packages/core/test/integration/s1-ask-delta.test.ts`）：依次发 `message.start`、`thinking.delta`、`reasoning.delta`、2 段 `message.delta`、再一段迟到的 `reasoning.delta`、`message.complete`；`onProgress` 恰好收到 `['thinking', 'answering']`。
2. **core**：没有 `message.start`、第一个事件就是 `thinking.delta` 时，thinking 也只报一次。
3. **desktop 集成测试**（照 `apps/desktop/test/integration/s1-ask-delta.test.ts`）：
   - `preparing` 是这一轮的第一个进度事件，且在会话开始跑之前就发出；
   - 之后转发的阶段 `conversationId`/`messageId` 都对；
   - 两个对话同时在答：逐条核对每个事件的归属（**不要只看最终状态**）；
   - 取消后不再有进度事件。
4. **界面测试**（jsdom + fake timers，照 `apps/desktop/test/unit/ask-delta.test.ts`）：
   - 发出后立即显示「正在准备」；
   - 收到 thinking、再过 3 秒 → 显示「正在思考」且秒数正确；
   - 收到 answering → 不再显示「正在思考」；
   - 别的对话的进度事件不影响当前界面。
5. `node scripts/verify.mjs` 全过；`apps/desktop/e2e/d6-chat-ui.spec.ts` 全过。
