  ——已回退，记录为本单已知缺口。

## 组件级验收测试（apps/desktop/test/acceptance/a4-follow-live.test.ts，已 lock 登记）

6 条逐条对应规格条件（Codex 前几轮逐条提过的盲区都在这里钉住）：

- 条件 1：打开正在写的对话 → 转圈（契约 3：只见「正在回答…」，无阶段无秒数）→ 轮询追上 → 答完自动显示最终内容、转圈消失。
- 条件 2：库里逐段追加内容，每个轮询周期把新到达的分段带进气泡；答完后正文与库里精确一致、恰好出现一次。
- 条件 3：streaming→failed 转换后显示「失败：」+ 错误详情、不再转圈；补充 cancelled 终态显示「已取消」和半截回答。
- 条件 4：打开另一个对话期间，本对话照常显示与增长，另一对话（含原轮继续写的内容）不串进。
- 竞态：A→B→A 快速切换后，旧实例在途的流式快照回来不回写（不再把最终态覆盖回转圈）。对应实现：轮询 effect 加代次失效标记。
- 条件 5 由既有 d6/m2/smoke 套件照过（发起页行为不变）。

## 分段的事实（条件 2 为什么这样验）

真实回答「逐段写库」确凿发生在 Hermes 引擎路径：`session.wireEventLedger` 收到引擎
事件流里的每个 text delta 后调 `onDelta`，`appRuntime.ask` 把它并入 `pendingDelta` 并
按 200ms 批量 `appendContent` 写进当前流式消息（半个问题回答的「已经写出的半截」
场景也走这条路）。A4 不碰这条路径；切回页靠 2s 轮询把库里逐段增长的内容带进气泡，
组件测试条件 2 把这段「库里增长 → 气泡增长」钉住。CI/e2e 假模型走 core-bounded
整段落库（没有事件流），对应验证是「转圈期间切回来 → 答完自动显示与库精确一致的
最终内容」，与 Hermes 的逐段路径互补。

## 第二轮整改（2026-10-02，整合方指出 CI 上两条路径差异）

整合方审 prep/A4 CI 日志（运行 36842993422，b4ad7c4）指出两处「本机过、CI 路不同」，
已逐条落实：

1. **侧栏点「问答」会把 openConversationId 置空，对话页不自动选中**——CI 上
   「正在」断言收到的是空状态引导语「像聊天一样直接问…」，本机能过只是时机碰巧。
   → 三条 e2e 全部改为切回后**按 `data-conversation-id` 在列表里点开对话**再断言
   （条件 1/2、3、4），不依赖页面自动打开、不靠列表位置；实现里没有按时机自动
   打开的逻辑（见 App.tsx 侧栏处理与 AskPage 的 openConversationId effect，均
   确定性），未另行改动。
2. **CI 上没有 Hermes，问答走 core-bounded，每次模型调用从脚本取一条；第二个
   问题拿到「FakeProvider 队列为空」**。→ 脚本按 core-bounded 每问实际调用次数
   备量：一问 = answer(1) + 答后记忆提取(1)，两问共 4 条
   （`answer, items, answer, items`），本机清掉 `HERMES_HOME` 等探测变量后走的
   也是这条路径（launch 里已置空，两边一致）。

连带发现一处实现缺口并处理如下：模型出错的轮目前被主进程收尾成 `complete`、
失败文案存在正文里（界面上错误文案可见、不再转圈，条件 3 的字面行为成立）。
曾尝试在 `appRuntime.ask` 按 `result.steps` 把这种轮收尾为 `failed` + `error_message`，
Codex 第二轮审查判定这超出 A 档「只改显示与刷新、不改主进程回答流程」的范围，
且可能影响「priorTurns 只取 complete」的后续上下文——已回退，留作已知缺口，
由整合方按 B 档裁定（改动要点见 Codex 审查记录）。

## e2e 断言收紧

- 条件 1/2：切回后**先点列表里的对话**（`conversation-item[data-conversation-id=…]` 按 id 定位，不依赖页面自动选中、不靠列表顺序），断言跟进态出现「正在回答…」；等答完（轮询周期 2s 内），断言 UI 出现最终文本；再从库里精确比对最终消息的 status（`complete`）和 content（**相等**而非包含）；断言库里 assistant 消息恰好 1 条、界面正文恰好出现一次（不重复、不缺）。
- 条件 3：切回后**按 id 点列表里的对话**，断言消息列表出现模型错误文案（「模型动作失败」+ 错误详情）且不再有「正在」；库里这条消息内容含同一错误文案、不再 streaming。提问文案不含「失败」字样，避免断言撞上用户消息。组件测试侧补了 failed / cancelled 终态的 streaming→终态 转换（见下）。
- 条件 4：**创建并切换到另一个对话**（新对话按钮 → 不发问），按 id 在两个对话之间来回切换，断言另一个对话的 message-list 里**没有**本轮提问与回答（界面级隔离，不再只查库）。列表按 `updated_at` 排序、新对话排最前，断言一律按 `data-conversation-id` 定位，不猜位置。
- 假模型脚本备量：core-bounded 一问实际两次结构化调用（answer 1 + 答后记忆提取 1），脚本为两问备了 4 条（`answer, items, answer, items`）；本机与 CI 都不装 Hermes，走的都是这条路径。
