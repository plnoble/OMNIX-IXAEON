# A4 切回来接着看还在写的回答——交付

日期：2026-10-01。分支：prep/A4。规格：docs/委派/A4-切回来接着看还在写的回答.md（A 档）。

## 已实现

改动集中在 `apps/desktop/src/renderer/src/pages/Ask.tsx`（对话页）+ 一个假模型测试钩：

- **2 秒同步 effect**（核心）：每 2 秒从库里拉当前对话；有 `status=streaming` 的
  助手消息就同步内容到气泡并显示跟进态（「正在回答…」，无阶段无秒数）；该消息
  不再 streaming 且之前在跟 → 重拉显示最终结果、清掉跟进态。切走再切回、页面
  重载后都能靠这条 effect 追上进度。发起页的 delta 实时处理器照旧工作（本页
  `waiting.current` 非 null 且非 joined 时 2s 同步跳过，不与 delta 竞争）。
- **模型出错轮如实收尾**（验收条件 3 的实现）：`appRuntime.ask` 收尾时按
  `result.steps` 里 `model` 步骤失败标记为 `failed` 并把错误详情写进
  `error_message`——模型出错的轮在界面上显示「失败：…」，不再把失败文案伪装成
  complete 回答。回答流程（模型调用、事件序、收尾时机）不变，只改状态标记。
- **假模型延迟钩**：`FakeProvider.chatDelayMs` + `IXAEON_TEST_MODEL_DELAY_MS`
  （仅 fake 模式生效），让「回答中」窗口拉长到可测的秒数。
- 验收测试两层：组件级 `apps/desktop/test/acceptance/a4-follow-live.test.ts`
  （jsdom，4 条，已 `acceptance.mjs lock A4` 登记指纹）+ e2e
  `apps/desktop/e2e/a4-follow-live-answer.spec.ts`（3 条，逐条对应条件 1/2、3、4；
  条件 5 由现有 d6/m2/smoke 套件照过）。

## 第二轮整改（2026-10-02，整合方指出 CI 上两条路径差异）

整合方审 prep/A4 CI 日志（运行 36842993422，b4ad7c4）指出两处「本机过、CI 路不同」，
已逐条落实：

1. **侧栏点「问答」会把 openConversationId 置空，对话页不自动选中**——CI 上
   「正在」断言收到的是空状态引导语「像聊天一样直接问…」，本机能过只是时机碰巧。
   → 三条 e2e 全部改为切回后**按 `data-conversation-id` 在列表里点开对话**再断言
   （条件 1/2、3、4），不依赖页面自动打开、不靠列表位置；实现里没有按时机自动
   打开的逻辑（见 App.tsx 侧栏处理与 AskPage 的 openConversationId effect，均
   确定性），未另行改动。
2. **CI 上没有 Hermes，问答走 core-bounded，每次模型调用从脚本取一条；第二个
   问题拿到「FakeProvider 队列为空」**。→ 脚本按 core-bounded 每问实际调用次数
   备量：一问 = answer(1) + 答后记忆提取(1)，两问共 4 条
   （`answer, items, answer, items`），本机清掉 `HERMES_HOME` 等探测变量后走的
   也是这条路径（launch 里已置空，两边一致）。

连带发现并修掉一处实现缺口（条件 3）：模型出错的轮此前被收尾成 `complete`、
失败文案伪装成回答正文；现按 `result.steps` 指标收尾为 `failed` + `error_message`
如实落库（见「已实现」）。

## e2e 断言收紧

- 条件 1/2：切回后**先点列表里的对话**（`conversation-item[data-conversation-id=…]` 按 id 定位，不依赖页面自动选中、不靠列表顺序），断言跟进态出现「正在回答…」；等答完（轮询周期 2s 内），断言 UI 出现最终文本；再从库里精确比对最终消息的 status（`complete`）和 content（**相等**而非包含）；断言库里 assistant 消息恰好 1 条、界面正文恰好出现一次（不重复、不缺）。
- 条件 3：切回后**按 id 点列表里的对话**，断言消息列表出现失败文案（「失败：」+ 错误信息）且不再有「正在」，库里那条消息收尾为 `failed`（轮询等待）。**实现同步修复**：模型出错的轮（core-bounded 步骤里 `model` 失败）此前被收尾成 `complete`、失败文案伪装成回答正文——现在 `appRuntime.ask` 按 `result.steps` 如实收尾为 `failed` 并把错误详情写入 `error_message`（回答流程本身不变：模型调用、事件序、finishMessage 时机照旧，只改状态标记与错误字段）。
- 条件 4：**创建并切换到另一个对话**（新对话按钮 → 不发问），按 id 在两个对话之间来回切换，断言另一个对话的 message-list 里**没有**本轮提问与回答（界面级隔离，不再只查库）。列表按 `updated_at` 排序、新对话排最前，断言一律按 `data-conversation-id` 定位，不猜位置。
- 假模型脚本备量：core-bounded 一问实际两次结构化调用（answer 1 + 答后记忆提取 1），脚本为两问备了 4 条（`answer, items, answer, items`）；本机与 CI 都不装 Hermes，走的都是这条路径。
