## 第 1 条：`review-recheck-ui` 的 `BUI01` — `Test timeout of 30000ms`

### 怎么复现的

1. **单独连跑 20 遍**（`node apps/desktop/node_modules/playwright/cli.js test -c apps/desktop/test/review/playwright.recheck-20260907.config.ts -g BUI01`）：
   **20/20 绿**，每次 3 秒（第 20 次 4 秒）。红 0 遍。
2. **机器忙的时候**：起 **20 个占 CPU 的进程**（20 核全占，限时 150 秒）再跑 5 遍：**5/5 绿**，每次 3 秒。红 0 遍。
   → 光压 CPU 压不出来。
3. **换成「二进制不在」之后，一次就出来了**（这才是那条偶发的形状）：把
   `node_modules/.pnpm/electron@44.1.1/node_modules/electron/path.txt` 与 `dist/` 藏起来，再跑：
   - 下载镜像不可达时（`ELECTRON_MIRROR=http://127.0.0.1:9/`）：跑 1 次，**1 秒就红**，红在第 10 行 `await electron.launch({`，报 `Electron failed to install correctly`；
   - 网络正常、二进制是冷的：连跑 2 次，**一次 3 秒红（同一个地方），一次 4.1 秒绿**（那次输出里有 `Downloading Electron binary...`）。
   → **同样的内容、一次红一次绿**，就是门禁和 CI 里见到的那条。

### 原因

`@playwright/test` 的 `_electron.launch()` 第一步就是 `require('electron')`，而 electron 这个包在
`path.txt` / `dist` 不在的时候会**同步**去装（`node_modules/.pnpm/electron@44.1.1/node_modules/electron/index.js` 的
`getElectronPath()` → `downloadElectron()`：`spawnSync(install.js)`，下载并解压两百多兆，`stdio: 'inherit'`）。
这一截正好落在每个用例 30 秒的预算里：装得慢 → `Test timeout of 30000ms exceeded`；装不成 → `Electron failed to install correctly`。
**不是用例里有固定的死等**，也不是断言有问题。

### 怎么治的

把这一截**挪出用例预算**：新增 `apps/desktop/test/review/ensure-electron.ts`，用 Playwright 的 **globalSetup**
在开跑之前把二进制准备好（装不成也会抛一句能照着做的错话：「先跑一次 `corepack pnpm install`（或 `corepack pnpm rebuild electron`）」），
然后给 verify 里那 4 个界面配置都挂上 `globalSetup: './ensure-electron.ts'`：
`playwright.recheck-20260907` / `playwright.needs-lifecycle-20260908` / `playwright.understanding-20260908` / `playwright.sources-wizard-20260929`。

### 治后再跑（二进制照样藏起来）

| 跑什么 | 结果 |
| --- | --- |
| BUI01 连跑 3 遍（二进制不在） | **3/3 绿**，4 秒 / 3 秒 / 3 秒（第一次是 globalSetup 现场装的） |
| `playwright.needs-lifecycle-20260908`（3 条用例） | **3 passed**，7 秒 |
| `playwright.understanding-20260908`（2 条用例） | **2 passed**，6 秒 |
| `playwright.sources-wizard-20260929`（4 条用例） | **4 passed**，7 秒 |
| BUI01 连跑 20 遍（二进制正常） | **20/20 绿**，3 秒 |

## 第 2 条：integration 的 `d3-d4` — `Electron failed to install correctly`

### 怎么复现的

藏掉上面那两个路径 + 镜像不可达，单跑
`node node_modules/vitest/vitest.mjs run --project integration apps/desktop/test/integration/d3-d4-conversation-context.test.ts`：
**连跑 2 遍，2/2 红**，报的就是那一条，栈顶是 `electron/index.js:43` 的 `getElectronPath`
（`getElectronPath` 里 `downloadElectron()` 的 catch），1.5 秒就红。

### 原因

这个集成测试**根本不需要真 Electron**（它全程走 Core 的有界循环 + 替身执行器），但它 import 的
`apps/desktop/src/main/appRuntime.ts` 顶层 `import { app, safeStorage } from 'electron'` → 触发上面那条同步安装。
同目录早就有 9 个文件照惯例写着 `vi.mock('electron', () => ({ app: {}, BrowserWindow: {}, dialog: {}, ipcMain: {}, safeStorage: {} }))`，
这一个是漏的；连上它一共 **7 个** integration 文件漏了 mock。

### 怎么治的

给这 7 个文件补上同款 mock（一行不改断言，只是不让它去 require 真 Electron）：
`d3-d4-conversation-context`、`a03-ask-capture`、`ask-semantic-gate`、`hermes-bridge`、`hermes-bridge-config`、`localServer`、`review-followup`。

### 治后再跑（**二进制仍然不在、镜像仍然不可达**）

整个 integration 项目（`--project integration`）：**83 passed / 9 skipped（92 个文件）、488 条测试全过**，42 秒。
（治之前，单是 `d3-d4` 这一个文件都过不去。）

> 另记一句：`apps/desktop/test/unit/renderer-diagnostics.test.ts` 也被「没 mock」的脚本扫出来了，但它引的
> `rendererDiagnostics.ts` 只有 `import type { BrowserWindow } from 'electron'`（类型，运行时被擦掉），**不需要 mock**——
> 按文本匹配会误报，这里说明一下，没有改它。

1. **第 212 行那条改成行为断言**：它想验的是「派任务不挡着对话」——用替身记调用顺序（调度返回时执行器还没跑完）或用假时钟推进，别拿墙上时钟当断言。

3. **两处固定 `setTimeout` 改成等条件**（它们现在等的是「落库/状态变了」这件事）。
4. 这些改完得由整合方重新 `lock`（指纹在 `docs/委派/锁定验收.json`）。

   我的 globalSetup 只是把「万一没落地」的代价从「用例超时/失败」变成「开跑前多等几秒」。
