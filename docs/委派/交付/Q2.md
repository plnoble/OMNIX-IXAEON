## 第 1 条：`review-recheck-ui` 的 `BUI01` — `Test timeout of 30000ms`

### 复现记录（每一次都是真跑）

| 条件                                                                              | 跑了几遍 | 结果                                                                                                       |
| --------------------------------------------------------------------------------- | -------- | ---------------------------------------------------------------------------------------------------------- |
| 普通负载，单独跑 BUI01                                                            | 20 遍    | **20/20 绿**，每次 3 秒（最后一遍 4 秒）                                                                   |
| 机器忙：20 个占 CPU 进程（20 核全占，限时 150 秒）                                | 5 遍     | **5/5 绿**，每次 3 秒                                                                                      |
| **Electron 二进制不在 + 下载镜像不可达**（`ELECTRON_MIRROR=http://127.0.0.1:9/`） | 1 遍     | **1/1 红**，1 秒就红在第 10 行 `await electron.launch({`，报 `Electron failed to install correctly`        |
| **Electron 二进制不在 + 网络正常**（二进制是冷的）                                | 2 遍     | **1 红 1 绿**：红的那次 3 秒、红在同一个地方；绿的那次 4.1 秒（输出里有 `Downloading Electron binary...`） |

**原超时（30000ms）本身：没能复现。** 试过的办法在上面：单独连跑 20 遍、20 核全占跑 5 遍，都是 3 秒过；
这台机器（20 核 + SSD）压不出 30 秒那种超时。整合方见到的那次是在整条门禁（CPU + 磁盘 + 杀毒都在动）里发生的。

### 根因（已证实的是「同步安装」，30 秒超时是疑似同因）

`@playwright/test` 的 `_electron.launch()` 第一步就是 `require('electron')`，而 electron 这个包在
`path.txt` / `dist` 不在的时候会**同步**去装（`node_modules/.pnpm/electron@44.1.1/node_modules/electron/index.js` 的
`getElectronPath()` → `downloadElectron()`：`spawnSync(install.js)`，下载解压两百多兆、`stdio: 'inherit'`）。这一段落在用例的
30 秒预算里只有两种出路：**装得慢 → `Test timeout of 30000ms exceeded`**；**装不成 → `Electron failed to install correctly`**。
后一种我已经稳定复现（上面表的第 3、4 行）。

**所以：本文只主张「同步安装这一段落在用例预算里」这个根因与治法；「D2c 那次的 30000ms 就是它」属于疑似（没能复现那次超时），
不排除是同一预算下的其它慢（Electron 冷启动 + 杀毒扫描）。** 治法对两种情况都成立：把安装这一截挪出预算之后，
界面用例从「3.6 秒」掉到「1.5–2.0 秒」，冷启动那一截也少了。

### 治

把这一截**挪出用例预算**：新增 `apps/desktop/test/review/ensure-electron.ts`，用 Playwright 的 **globalSetup**
在开跑之前把二进制准备好（装不成也会抛一句能照着做的错话：「先跑一次 `corepack pnpm install`（或 `corepack pnpm rebuild electron`）」），
然后给 verify 里那 4 个界面配置都挂上 `globalSetup: './ensure-electron.ts'`：
`playwright.recheck-20260907` / `playwright.needs-lifecycle-20260908` / `playwright.understanding-20260908` / `playwright.sources-wizard-20260929`。

### 结论：**复现出来了，位置就在 `vi.waitFor` 的默认 1 秒上限上**

同一台机器上，负载轻的时候 15 遍全绿；把 20 个核占满、每遍拖到 30–50 秒之后，**两轮 6 遍里红了 3 遍**，
红的位置全都落在我静态查出来的那些「没给上限的 `vi.waitFor`」上（`d4-landing-report.test.ts:203:55`、
`d3-auto-dispatch-report.test.ts:219:60`）。也就是说这一条的机理是：
**队列/数据库那几步在忙时超过 1 秒，`vi.waitFor` 的默认上限就判超时**（不是断言写错）。
212 行那条墙上时钟断言（`expect(Date.now() - started).toBeLessThan(1000)`）这两轮没红，但它属于同一类隐患。
**这些文件是锁定的，我没改；改法见下面「该怎么改」。**

### 该怎么改（请整合方定，改锁定测试是整合方的关卡）

1. **第 212 行那条改成行为断言**：它想验的是「派任务不挡着对话」——用替身记调用顺序（调度返回时执行器还没跑完）或用假时钟推进，别拿墙上时钟当断言。
2. **所有 `vi.waitFor` 补上显式上限**（例如 `{ timeout: 10_000, interval: 50 }`）：这是规格允许的「等条件成立（带上限）」，不是放宽断言。
3. **两处固定 `setTimeout` 改成等条件**（它们现在等的是「落库/状态变了」这件事）。
4. 这些改完得由整合方重新 `lock`（指纹在 `docs/委派/锁定验收.json`）。

## 复现/复测脚本与原样输出

复现/复测都落在一条命令上：**`scripts/real/q2-flaky-repro.mjs`**（这次新加的，随本分支提交）。它做四件事：
把 Electron 二进制藏起来（`path.txt` / `dist` 改名成 `.q2bak`）、起**限时**的占 CPU 进程（默认 20 个、150 秒后自己退）、
把下载镜像指到不可达地址（`ELECTRON_MIRROR=http://127.0.0.1:9/`）、按场景连跑 N 遍并打印每遍的退出码/用时/结果行；
**收尾一律还原**（二进制、`--baseline` 临时换回的文件、占 CPU 的进程）。

实际用的七条命令（就是下面那七段输出的出处，本机的原样输出在 `.logs/q2-repro.txt`）：

```
node scripts/real/q2-flaky-repro.mjs --scenario d3d4 --runs 3 --expect pass
node scripts/real/q2-flaky-repro.mjs --scenario d3d4 --runs 3 --load 20 --expect pass
node scripts/real/q2-flaky-repro.mjs --scenario b04 --runs 10 --expect pass
node scripts/real/q2-flaky-repro.mjs --scenario b04 --runs 3 --load 20 --expect pass
node scripts/real/q2-flaky-repro.mjs --scenario bui01 --runs 3 --load 20 --binary hidden --expect pass
node scripts/real/q2-flaky-repro.mjs --scenario integration --runs 2 --load 20 --binary hidden --mirror broken --baseline --expect fail
node scripts/real/q2-flaky-repro.mjs --scenario integration --runs 2 --load 20 --binary hidden --mirror broken --expect pass
```

## 已知缺口

1. **BUI01 的 30000ms 原超时没能复现**（20 核机器压不出来），所以那一格的根因只是疑似；治法是按「把同步安装挪出预算」做的，
   实测：干净状态下「二进制不在 + 忙」冷启动 **1/1 绿、整条 4.0 秒、用例 1.9 秒**（install 在 globalSetup 里）。
2. **复测脚本自己也出过两次错，都改掉了**：第一版收尾会无条件删 `path.txt`/`dist`（`--binary keep` 时会误删正常装好的 Electron，
   也没有处理上次崩掉留下的残留备份，导致一次 `EPERM` 崩在收尾）——现在只在**这一次真的藏过**时恢复、藏之前先收拾残留、改名带重试、
   删不掉会打印原因；`--baseline` 现在遇到未提交改动会拒绝执行。**建议整合方用之前先 `node scripts/real/q2-flaky-repro.mjs --restore-only`
   看一眼机器上有没有残留备份。**
3. **二进制「装不好」的根子在安装环节**：这次查到的是 `pnpm install` 之后 `apps/desktop/node_modules/electron` 的
   `path.txt` / `dist` 有时没落地（本工作目录一开始就是这样），这属于 `scripts/worktree.mjs` / 安装配置，**不在 Q2 允许改的范围**（规格只许改测试和测试配置）。建议整合方在安装环节补一步「检查二进制在不在，不在就 `corepack pnpm rebuild electron`」。
4. **还有 4 个锁定文件会在二进制不在时触发同一条同步安装**（我只治了没锁的）：`apps/desktop/test/acceptance/a3-bridge-origin-tag.test.ts`、
