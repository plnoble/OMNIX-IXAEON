## 已实现

`packages/relay/src/push.ts`：

- 每一条 `git push` 失败后隔 2 秒重推，再失败隔 5 秒重推，第 3 次还失败才算这一条失败；
  `dev/` 分支和 `main` 都这样（`pushWithRetry`，与 `fetchMain` 共用同一组等待）。
- `rebaseThenPush` 里的 `git fetch origin main` 改用 `git.ts` 已有的 `fetchMain`（同样的
  2 秒 / 5 秒、3 次；回环地址绕开代理），不再自己跑一次不重试的 fetch。
- rebase 加 `--rebase-merges`：开发那一棒里的 `merge --no-ff` 合并提交推上去之后还是合并提交。
- rebase 成功后的第二次推同样最多试 3 次；成功记 `ok: true, rebased: true`，失败记
  `ok: false, rebased: true` 并停下。

`packages/relay/src/git.ts`：把 `fetchMain` 里的等待抽成 `waitBeforeRetry(attempt)` 共用
（2 秒 / 5 秒），`fetchMain` 的行为不变。

`packages/relay/src/engine.ts`：调 `relayPushes` 的那一处加 `await`（`relayPushes` 改成
`async`、返回 `Promise<PushResult>`，参数和返回字段都没变）。

契约里说不变的部分都没动：`PushResult` / `PushRecord` 没有加字段；「先全部查一遍、有一条不过就
一条都不推」那段；`stopReason` 的写法；不加 `--force`、不带 `+`、不动 `dir` 以外的目录。

## 验收测试（v2 规格任务）

新文件 `packages/relay/test/acceptance/l13b-push-retry.test.ts`，4 个 `it`，逐条对应规格「验收」：

- 条件 1：开发推 `dev/x`，裸仓库 `pre-receive` 钩子拒第 1 次 → 裸仓库 `dev/x` 就是开发那一笔；
  记账 `ok: true`、没有 `rebased`、没停下；钩子被调了 2 次；钩子两次调用的时间戳间隔
  `>= 2_000` 毫秒——直接量两次尝试之间的重试等待，不看整棒的耗时（整棒里还有建仓库、
  提交等耗时，整棒超过 2 秒不能证明实现真的等了）。
- 条件 2：开发推 `main`（没人先推过），钩子拒前 2 次 → 推上去了，`ok: true`、没有 `rebased`；
  钩子被调了 3 次；第 1→2 次调用间隔 `>= 2_000` 毫秒、第 2→3 次 `>= 5_000` 毫秒。
- 条件 3：开发推 `dev/x`，钩子一直拒 → 停下、`stoppedReason` 含「第 1 棒替开发推送失败：dev/x」；
  钩子被调了正好 3 次；后面那条 `RELAY-PUSH <dev> dev/y dev/y` 没推（裸仓库上没有 `dev/y`）。
- 条件 4：别人先往裸仓库 main 推一笔别的文件；开发在检出的 `relay-dev` 上 `merge --no-ff`
  了一支（那一支改另一个文件），`RELAY-PUSH <dev> relay-dev main` → 推上去了：裸仓库 main 最新
  一笔有两个父提交（`git rev-list --parents -n 1` 三个词），别人那一笔是它的祖先
  （`merge-base --is-ancestor`），那一支改的文件在 main 上；`ok: true, rebased: true`。
- 条件 5（L13 条件 2：同一个文件冲突、停下、不留未完成的 rebase）：沿用已锁定的
  `l13-rebase-push.test.ts`，按规格不在这里重写；下面的「自动化通过」里记了 `run L13`、`run L6` 的结果。

「推一次失败一次」是裸仓库里的真 `pre-receive` 钩子：钩子把计数文件加一，并把调用时刻
（`date +%s%3N`，毫秒）追加到时间文件；前 N 次 `exit 1`、之后放行。测试用真 `git`，但 origin
是临时裸仓库，不连 GitHub。重试间隔直接由钩子时间戳量，**不靠整棒耗时**（Codex 第 1 轮意见）。

已用 `node scripts/acceptance.mjs lock L13b "L13b 替开发推送时网络抖一下不停（推送重试三次），rebase 保留合并提交" packages/relay/test/acceptance/l13b-push-retry.test.ts`
登记指纹。实现之前先跑过一次：4 条全红（条件 1/2/3 钩子只被调 1 次，条件 4 的合并提交被旧的

## 已知缺口

1. 真 GitHub 上的握手失败没有演练过，等接力里真碰上时看记账（规格要求的写法）。
2. 每一条推失败都会重试（包括非快进、钩子拒、认证失败），所以被拒的那一条现在要多等约
   7 秒才 rebase 或停下；规格就是这么写的，L13 / L6 的锁定测试因此变慢但都还过。
3. rebase 冲突时先试 3 次推（约 7 秒）、再 `fetchMain`、再 rebase，冲突后才 `--abort`；这期间
   开发目录里短暂有进行中的 rebase，结束后 abort 干净（L13 条件 2 覆盖）。
4. `--rebase-merges` 需要 git 2.18 以上；本机和 CI 的 git 都满足，没有另做版本检查。
5. 真实 GitHub 上「push 成功但回包丢了」这种情况没有专门处理：重试时若远端已经收下，第二次会是
   up-to-date 成功，记账照样 `ok: true`。
6. `ops` 操作目录里有第 22 棒（V4）崩溃留下的未提交改动：队列第 54 行被改成「进行中（dev）」，
   而 main 在 10:38 已把它改成「等 L16」。为不覆盖它，原 diff 存到了
   `ops/.logs/turn22-crashed-v4-claim.diff` 再还原；本棒的领活/合并提交里队列只改第 75 行。
