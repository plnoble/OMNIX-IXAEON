## Codex 审查（A 档）

第一次（2026-09-24）退出码 3：额度用完。2026-09-26 20:27 重跑，退出码 1，结论「需要修改」，全文见 `docs/委派/交付/G05-Codex审查.md`。两条「必须改」都在锁定测试上，测试本身不许改，用补充测试补上：

- 「所有用例都预置了会话，漏测首次提问尚无会话时的准备阶段取消」：补 `g05-cancel-preparing-extra.test.ts` 第一条。空的 `askSessions`、阻塞语义补齐、取消后放行，断言取消返回成功、`newAskSession` 调用 0 次、不建会话、回答是 `cancelled`。
- 「回答中取消的替身无条件返回取消提示，删掉 `session.cancel(runId)` 也能过」：同文件第二条。断言会话 `cancel` 收到的正是 `cancelAsk` 返回的那个 `runId`。

审查另有两条从「建议」升为「必须改」，核对过代码，不改，证据如下：

- 「真实会话在异步准备后、启动 Hermes 和调用 Core 模型之前是否检查取消」。检查了，而且不依赖本单的改动：`AgentSession.cancel`（`packages/core/src/runtime/session.ts:132`）把 runId 记进 `cancelled` 并调用 `adapter.cancel`；Hermes 路径由 `adapter.start` 返回 `status === 'cancelled'`（同文件 278、309 行）；Core 模型路径在每一轮调用 `provider.chatStructured` **之前**检查 `this.cancelled.has(runId)`（404 行），调用返回后**再检查一次**（424 行），命中就按取消收尾、不再进入下一轮。`cancelAsk`（`appRuntime.ts:1625`）对已有会话调用的就是这个 `session.cancel(runId)`，补充测试第二条锁住了「传过去的是这一轮的 runId」。
- 「界面收到 `cancelled: false` 时会不会显示已停止」。不会，因为界面根本不看这个返回值：`Ask.tsx:484` 是 `void api.cancelAsk(activeId)`，返回值被丢掉。界面的「已取消」只来自重新拉取的消息状态（本单让准备阶段的回答收尾为 `cancelled`）；全仓界面代码里没有「已停止」这几个字，它只出现在主进程日志里。所以不存在把没生效的取消显示成已停止的路径。这条契约在改动前就成立，本单没有改界面。
