# IXAEON 全局审核报告｜2026-09-20

## 一、结论先说

**方向已经比此前正确，但目前不能通过“可日用的个人 Agent”整体验收。不是推倒重来，而是先把已有能力可靠地连起来。**

目前已经有真实的个人记忆、持久对话、可替换的 Hermes 接入、资料导入、研究关注和编码任务基础，并非全部空壳。把 Door、模型池、多设备、自我升级暂时停住，符合当前阶段，不等于放弃长远目标。

但本轮发现：已有功能在跨模块交接时，仍会丢上下文、串项目、错误归属任务，甚至在撤销来源读取权限后继续拼接资料。现有测试大量通过，不能证明这些用户路径可靠。

本报告只做审核，不另起路线图，不认领开发任务，不修改规格、锁定验收、迁移、队列或业务代码。修复的安排仍由整合方回填当前《三周任务单》。

## 二、审核基线与范围

- 代码基线：`039f3b7`；仓库版本 `0.2.9`；迁移账本最新为 34。
- 依据：当前 `AGENTS.md`、`docs/三周任务单.md`、`docs/委派/队列.md`，以及相关任务规格、交付说明和实际代码。
- 历史规划仅作为背景，不据此要求继续 P0–P6。
- 工作开始时检出目录干净；本轮仅新增审核脚本、合成数据测试和本报告，没有修改既有生产代码，没有提交或推送。
- 未读取用户真实聊天、记忆、数据库内容或密钥；所有新复现均使用合成数据、临时库或受控替身。
- 没有调用云端模型，没有执行真实 Codex 编码任务，没有安装或升级正式应用。

当前唯一的整体验收信号仍是：打开 IXAEON，连聊三轮，它记得住，并且至少有一件事是它替用户做完的。本轮没有完成这项真实环境验收，不能代签“用户接受”。

## 三、已复现的缺陷

下表按影响排序。P1 表示应优先解决；P2 表示明确存在但影响相对局部。编号是本轮定位标签，不是新的开发阶段。

| 编号 | 优先级 | 通俗说明 | 证据 |
| --- | --- | --- | --- |
| G02 | P1 | 撤销来源读取权限后，项目简报仍读取并拼入资料 | 合成权限撤销反例 |
| G01 | P1 | 记忆或权限版本变化使 Hermes 重建后，旧对话没有补进去 | 实际适配器＋协议替身 |
| G06 | P1 | 打开 A 项目的旧对话，下一问仍可能按 B 项目处理 | 组件测试＋真实 Electron |
| G04 | P1 | 对话 A 可能收到对话 B 刚创建的任务，误认为是自己的建议 | 实际 ask 路径＋受控运行替身 |
| G03 | P1 | 从用户聊天里提取的目标，点击关注却被后端拒绝；确认后也不行 | 两种确认状态反例 |
| G05 | P2 | 在“准备中”点击取消，之后仍可能启动模型调用 | 阻塞准备阶段的反例 |

### G02：撤销权限后，项目简报仍继续收集资料

**位置：** `packages/core/src/runtime/projectBrief.ts:53–85`；调用方 `packages/core/src/runtime/session.ts:265–277`。

项目简报以已有 `project_snapshot` 判断是否可继续，没有重新检查当前来源权限及其与当前项目根目录的绑定。随后直接运行 Git 查询，并直接读取编码会话的 `segments.text`。

**复现：** 在临时项目中建立已授权来源、快照和一段合成会话。撤销读取权限后再次生成简报，Git 查询替身仍被调用一次，简报仍包含被撤销来源中的合成标记。

**影响：** 这些内容随后会参与发给 Hermes 的提示词拼接。用户以为“已经不许读了”，这一条路径却还在取用。本轮没有真正向云端发送，因此不能说已发生真实数据泄露；能够确认的是，撤销后的访问与出站资料组装未被正确阻断。

**修复边界：** 复用现有来源授权及原文外发范围检查，核验当前项目根目录；已有快照不能充当永久授权。这属于权限与隐私 B 档，应由整合方明确规则和验收。

### G01：Hermes 实际重建了，对话层却以为还在原会话

**位置：** `packages/core/src/runtime/session.ts:248`；`packages/core/src/runtime/adapter.ts:135–142,195–207`；`packages/core/src/access.ts:43–50`。

对话层只在 `hermesSessionId === null` 时补入历史轮次；适配器在权限版本变化后会销毁常驻会话并重新建立。版本计算还包含记忆条目数量与更新时间，因此不只是用户手动改权限才会触发。

**复现：** 第一轮写入合成口令；随后增加一条无关记忆；第二轮提供正确的历史轮次。实际适配器建立了第二个协议会话，但第二次提示词没有补入第一轮口令。

**影响：** 看似仍在同一窗口聊天，底层却可能已经换成没有上文的新会话。这直接影响“三轮记得住”。真实模型是否会通过其他检索偶然找回，不改变会话历史丢失这个缺陷。

**修复边界：** 是否重放历史，必须与底层是否真正复用了原会话一致；不能靠关掉权限失效机制解决。涉及模型上下文约定，按 B 档处理。

### G06：旧对话的项目与界面当前项目脱节

**位置：** `apps/desktop/src/renderer/src/pages/Ask.tsx:111–120,230–235,450–453`；`apps/desktop/src/main/appRuntime.ts:989–1020`。

打开历史对话只恢复对话 ID 和消息，没有恢复其项目选择。下一次提问使用界面当前下拉框的项目；后端也没有校验它与会话归属是否一致。

**复现：** 在真实 Electron 的独立临时数据目录中创建 A、B 两个合成项目，选择 B 后打开 A 的历史对话。读回的当前项目仍是 B。组件测试也复现同一问题。

**影响：** 下一问可能检索和发送错误项目的记忆或简报。后续资料归属是否还受影响需另测，本轮不扩大断言。

**修复边界：** 整合方先确定“会话项目固定”还是“允许显式转移”的规则，再同时处理界面与后端一致性。只把下拉框看起来改对，还不足以建立可靠边界。

### G04：用时间窗口猜任务来自哪次对话

**位置：** `apps/desktop/src/main/appRuntime.ts:1133–1158`。

提问完成后，当前实现用“创建时间晚于本轮开始、且有项目”的全局任务查询来寻找建议待办。它没有限制到本次运行、当前对话，甚至没有限制到当前项目。

**复现：** 对话 A 正在等待时，受控运行替身创建项目 B 的任务。A 的返回结果把 B 的任务当成自己的建议待办。

**影响：** 用户可能在错误的对话中采纳或拒绝一个真实任务。即使增加项目过滤，同一项目中并行的两次运行仍会串单。

**修复边界：** 需要可靠的任务产生来源，而不是时间猜测。若需要新增字段、接口或迁移，必须由整合方先定规格。原 T2b 规格要求沿用现有查询，也存在规格缺口，不能仅归咎于执行方。

### G03：“用户说的目标”被旧规则当作 AI 自说自话

**位置：** `packages/core/src/research/researchStore.ts:118–128`；`packages/core/src/research/watchDirections.ts:88–97`；`apps/desktop/src/main/appRuntime.ts:1751–1762`。

正常提取器把用户聊天中的目标记成 `origin='ai'`、`said_by='user'`：前者表示记录由提取器生成，后者才表示是谁说的。关注建议允许这种目标进入，但创建研究主题仍要求 `origin='user'`。

**复现：** 用户表述的目标被正常提取后，点击关注会失败；先确认该目标再关注仍然失败，因为确认不会改写记录来源。人工直接创建的目标正向对照可以通过。

**影响：** 越符合“从聊天中自动理解用户”的正常路径，越容易卡在最后一步。让用户全部改成人工录入或逐条确认，不是正确修复。

**修复边界：** 研究端与现有记忆语义保持一致，同时继续阻止未采纳的 AI 建议冒充用户目标。属于记忆含义 B 档。

### G05：“准备中”的取消没有覆盖准备阶段

**位置：** `apps/desktop/src/main/appRuntime.ts:1102–1115,1587–1599`。

语义补齐完成后，运行才登记到可取消集合。界面在准备阶段已经允许取消，但后端此时找不到运行，返回失败；准备结束后仍继续启动模型。

**复现：** 人为阻塞补齐过程，点击取消，再放行准备过程。取消返回 false，模型运行替身随后被调用一次。

**影响：** 用户已表示停止，仍可能继续产生外发和费用。本轮使用替身，没有实际外发。

**修复边界：** 从准备开始就建立取消状态，在真正外发前再次检查；界面不得把没有生效的取消表示成已停止。

## 四、还需整合方决定的问题

### G07：研究“每天最多搜三次”与实际累计预算不一致（P2）

界面 `apps/desktop/src/renderer/src/pages/Research.tsx:310` 与 W1a 测试说明表达的是每天的搜索上限。关注方向初始化为 3 次预算后，检查器逐次扣减，并没有按天恢复。

本轮用成功的搜索和网页替身模拟四个不同日期，是否发起新搜索依次为 `[true, true, true, false]`；剩余额度为 0，主题仍 enabled、未 paused、连续失败数为 0。因此这不是搜索失败或自动暂停造成的。

准确说法是：当前更接近“累计三次新搜索”，而不是每天三次；已有来源的检查不一定停止。

**不要直接偷偷加每日重置。** 这会扩大自动网络调用预算。应由整合方决定是累计试用三次，还是明确授权的每日预算，并让界面说明及耗尽提示一致。本项观测测试通过，只代表证实了现状，不代表验收通过。

### 交付状态没有完全遵守“真机没跑不能合并”

W1a 交付说明明确写了真实模型检查未完成，原因与系统加密密钥的可用性有关；队列却已标完成。当前任务单也承认相关真实效果未验证。

这不证明功能必然失效，但说明“已完成”的证据口径没有严格执行。应补真实检查，或由整合方明确记录例外和剩余责任，不能以自动化全绿替代，更不应为了测试读取或导出用户密钥。

## 五、方向是否走偏

### 已经走对的部分

- 核心数据和记忆由 IXAEON 自己持有，Hermes 作为可替换运行引擎，符合此前讨论的边界。
- 已有持续对话、记忆检索、用户与 AI 表述区分、导入及本地语义检索等基础，不能再简单说它只是单项目交接工具。
- 减少逐条确认、区分用户决定和 AI 建议，是正确方向；G03 正是不同模块尚未统一执行这一方向。
- 暂缓多设备和自我升级，先验证一条真正有用的主流程，是当前合理收敛。

### 尚未兑现的核心体验

**“聊到要做什么 → 它提出执行 → 用户批准 → 真执行 → 带证据回报”仍未形成完整的真实链路。**

当前真实 Hermes 配置启用的是 `web`、`ixaeon` 工具集；记忆桥接公开的是 `search_memory`、`get_evidence`、`record_observation` 三个工具。核心回退路径中的 `propose_task`，不等于真实 Hermes 已经拥有并调用了该工具。

目前采纳待办只完成批准、入队；实际编码分发仍通过任务页按钮及 `coding.dispatch` 入口启动，没有发现负责自动接续这些批准任务的消费者。

因此它现在更接近“个人记忆对话＋手动研究和编码工作台”，还不是用户想象中可以自然接手工作的个人 Agent。当前三周任务单已经承认聊天到编码仍需整合方设计，这属于**已知阶段缺口**，不冒充本轮新发现的回归。

不能为了打通而直接开放全部终端工具；仍要分别处理本地读取、云端外发、编码执行、正式升级权限。

### 未完成任务不能被包装成已有能力

- X1、N1 的测试已锁定，不代表实现完成；本轮基线下仍待实现。
- C3 测试体系整理尚未完成。
- 浏览器当前对话采集、多平台文件导入，不等于已经自动取得所有平台的全部历史聊天。
- 未重新测量真实资料提取覆盖率；任务文档里的旧数字不是本轮的新证据。

## 六、开发质量判断

**已有一定工程基础，但跨模块语义一致性与真实流程验证仍弱于单模块测试。**

这次的问题主要出在接缝：记录来源与发言者混淆、会话与项目脱节、权限失效与上下文重放脱节、任务与产生它的运行脱节。多写几个只测当前函数的测试，未必能发现这些问题。

另一个审查盲点是：`scripts/codex-review.mjs` 主要提供差异、规格及交付说明，并限制读取其他文件。这样的审查能检查局部改动，但很容易漏掉 G03 这种“新规则已经变了，别处的旧规则没变”的问题。这不是认定既有审查全部无效，而是说明它不能替代跨模块审核。

建议整合方把本轮反例纳入现有任务体系，由规定的角色审核验收条件；不要由修复执行方自行改标准、给自己判通过。本轮诊断测试没有加入锁定验收，不是新的授权标准。

## 九、交给整合方的处理建议（不是新规划）

1. 先修 G02 权限边界，以及 G01、G06 的上下文和项目一致性。
2. 修 G04 任务归属、G03 用户目标关注路径；明确 G07 的预算授权含义。
3. 修 G05 取消行为，补齐 W1a 缺失的真实检查或明确记录例外。
