## 已实现

- `packages/core/src/execution/landing.ts`（新增，落地主流程）：
  - 前提核对——项目有根目录、根目录在某个仍有效的文件夹授权之内（`isPathInside`）；不满足 → 不落地，`apply_error` 写「没有这个项目目录的读取授权」。
  - 冲突核对（契约 3）——基线是派发时存进执行报告的 `baseHashes`（改之前每个改动文件的指纹，新文件 null），落地时与项目当前 HEAD 逐一比对；对不上 → 不建分支，改走改动包，原因点名文件。基线从执行报告读（持久化），换一个编排器实例接受也能对上。
  - git 仓库（契约 4）——分支 `ixaeon/<任务 id 前 8 位>`（重名加 `-2`）；**临时工作树建在 IXAEON 数据目录里**（`<数据目录>/worktrees/…`，整合方定的：不在用户项目里、也不在它旁边），从当前 HEAD 用 `git worktree add -b` 建；把副本里改动文件的最终内容写进去（删掉的照删）；提交标题「IXAEON：<目标第一行>」、正文任务 id + 验证结果；仓库没配提交人时 `-c user.name=IXAEON -c user.email=ixaeon@localhost` 兜底；用完 `git worktree remove` + `prune` 清干净。任何一步失败 → 清掉工作树（含半成品与已建分支）改走改动包。不推送、不碰用户的工作区/当前分支/暂存区。
  - 改动包（契约 5）——`<数据目录>/patches/<任务 id>/` 按原路径放改动后的文件 + `manifest.json`（`changed`/`added`/`deleted`/`conflict` 四个数组）。

## Codex 审查

B 档，审查不作为合并关卡（锁定仍由整合方做）。用户 2026-09-28 说可以审、Codex 有额度，已跑六轮 `node scripts/codex-review.mjs D4`（0.158.0，对照 `docs/委派/D4-接受后在项目里建分支.md`），记录在 `docs/委派/交付/D4-Codex审查.md`（该文件每轮覆盖，最新一轮为 12:33，结论**「可以合并」**，仅剩一条建议：`manifest.json` 四字段格式与 `AppRuntime.acceptCodingTask` 入口须由整合方在锁定前确认——即「已知缺口」里已写明的两项）。第一轮结论「需要修改」，十条「必须改」都是测试漏条件或放宽条件，已全部改，对应关系：

### 并入后 CI 红了一次（整合方修，2026-09-30）

并入后第一次在 GitHub 的 Windows 机器上跑，D4 的 12 条测试失败（运行 36664540178）：任务都退成了改动包，原因是「读取 ../../../../../../RU… 失败」。

- 原因：项目在仓库里的偏移是自己拿两条路径相减算的（`relative(仓库根, 项目根)`）。git 报的仓库根是长路径（`C:\Users\runneradmin\…`），测试的项目根来自临时目录，是 8.3 短名（`C:\Users\RUNNER~1\…`），相减得出一串 `../..`，每个文件都读不出来。执行方和整合方的机器上用户名不超过 8 个字符，没有短名，所以本地一直是绿的。用户把项目放在短名路径下（或经短名打开）时同样会触发。
- 修法（`landing.ts`）：
  - 偏移改为直接问 git（`git rev-parse --show-prefix`）；
  - 比对「git 登记的工作树是不是我们的临时工作树」时（清理，以及建分支失败后判断分支归属），两边都先取真实路径，Windows 上再忽略大小写，不再按字符串硬比。
- 复现与验证：把 `TMP` / `TEMP` 指到本机一个 8.3 短名目录之后，旧代码同样挂 12 条（和 CI 一致），新代码 30/30 通过；不设短名时也是 30/30。锁定测试没有改动。
