# 交付说明

每个任务一份 `<任务号>.md`，随任务分支提交（v2 起不再靠用户转话）。Codex 审查的结论由 `node scripts/codex-review.mjs <任务号>` 写进 `<任务号>-Codex审查.md`。

四样分开写，不能互相冒充：**已实现 / 自动化通过 / 真机通过 / 用户接受**。没做的写没做。

## 模板

```markdown
# <任务号> <标题> 交付

- 分支：<你的名字>/<任务号>，基于 main <提交号>；档位 A / B
- 执行方：<名字>

## 已实现

一两句话说做了什么。改动文件与行数（`git diff --stat origin/main...HEAD` 原样贴）。
和规格或委派单不一样的地方，逐条写清楚为什么。

## 验收测试（v2 规格任务）

测试文件；每条测试对应规格里的哪条验收条件（逐条对照，规格里的条件一条都不能少）。

## 自动化通过

- `node scripts/acceptance.mjs run <任务号>`：结果（通过几条）
- `node scripts/verify.mjs`：结果
- GitHub 上的 verify：绿 / 红 / 没看（附运行号）

## 真机通过

规格或委派单要求的真机检查：跑了哪个，把输出原样贴上（`scripts/real/` 的脚本只输出数字与合成问答，可以贴）。
没跑就写「没跑」和原因——**没跑的不能合并**。

## Codex 审查（A 档）

结论：可以合并 / 需要修改 / 额度用完待审。「必须改」的问题怎么处理的，逐条写。

## 已知缺口

## 用户接受

未发生（用户用过并认可之后才写）。
```
