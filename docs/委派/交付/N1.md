实现要点与规格的差异，逐条：

1. **`requirements.ts`（新文件，141 行）**：`listRequirements` / `addRequirement`（1–200 字，`sort_order` 用 INSERT 子查询 `COALESCE(MAX(sort_order),0)+1` 尾部追加，再读回返回）/ `removeRequirement` / `judgeFindings` / `listMatchedFindings` / `markMatchedFindingsSeen`（写 `app_settings` 的 `overview.matched_seen_at`）。
   - `judgeFindings` 用一条 JOIN（`findings × requirements`，`NOT EXISTS` 已判对）直接取「待判对」，按 `fetched_at DESC, sort_order ASC` 排序；没有待判对时不调模型；`provider` 为空时整批记 `failed` 不写库；单条模型失败 try/catch 记 `failed`，不影响其余。
   - 发给模型的只有标题、摘录、URL、要求原话（条件 4 由假模型截请求核对）。
2. **`checker.ts`**：检查成功收尾（`finishRun('succeeded')`）之后调用 `judgeFindings`，try/catch 包住——判定失败不影响发现入库，也不让这次检查算失败（条件 5）。检查本身失败（外层 catch）的轮次不判，等下次成功轮次再判。
3. **IPC**：五个通道按规格名称直连核心函数（`ipc.ts` 不经 AppRuntime 包装，`runtime.db` 本就是公开字段）。契约类型复用两个新别名 `OverviewMatchedFindingView` / `ResearchRequirementView`。
4. **概览页**：`overview-matched-findings` 卡片放在 W1b「最近的新发现」上面，每条含标题（系统浏览器打开）、所属方向、日期、对上的每条要求与理由、新标记，「都看过了」调 `markMatchedFindingsSeen` 并刷新。
   - 本地 `OverviewData` 接口改为 `Awaited<ReturnType<typeof api.getPersonalOverview>>`（以 IPC 契约为单一事实来源；W1b 原接口是手抄副本，删 40 行、不再需要为 N1 加字段）。
5. **研究页**：每个方向下「你的要求」块——一行一条可删、输入框 +「加一条」、无要求时提示「没有要求就不会提醒你，只会在页面上列发现」；超 200 字 IPC 报错进 `error-banner`，列表不变。加一条读的是输入框当前 DOM 值（锁定测试用原生 `input` 事件设值，React 受控组件读不到）。
   - `reload` 里对 `listResearchRequirements` 做了 `typeof === 'function'` 防卫：**U1 的锁定测试替身没有这个方法**，不防卫会把 U1 的「error-banner 不出现」断言打红。真机上 preload 与主进程同版本，恒有此方法。
6. **侧栏角标**：`nav-research-badge` 显示未看的对上条数，0 不渲染（App 刷新时从 `listMatchedFindings` 取 `isNew` 计数）。

## 已知缺口

- **模型判定待用户在应用里验证**（Key 在 Electron 加密存储，脚本进程解不开）：真配模型后，`judgeFindings` 的实际判定质量、理由可读性需要用户看一眼。
- 检查失败（外层 catch，如抓取异常）的轮次不判，该轮已入库的发现等下次成功轮次再判——规格写的是「产生新发现之后」，失败轮次的发现也是新发现，现按成功轮次判，若整合方认为失败轮次也该判请指出。
- `addRequirement` 用「INSERT 子查询定序 + 读回」替代「先 SELECT MAX 再插」，行为等价（同事务内单连接）；并发写同一 topic 时两者语义相同（better-sqlite3 单写者）。
- 研究页「加一条」按钮没有 `disabled={topicBusy}`（其余要求操作走 `topicAct` 序号防乱序）；锁定测试不检查该按钮的 disabled。
