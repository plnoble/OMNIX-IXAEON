## 已实现

规格：`docs/委派/K1-项目清单导入.md`。这一支交 **契约 + 核心**，界面入口在 K1b。

- `packages/contracts/src/entities.ts`：`projectImportListSchema` / `projectImportEntrySchema`（version 1；name 1..80 字；status 用现有 `projectStatusSchema`；`root_path` / `description` / `note` 可选；未知字段丢弃）、`ProjectStatus`、`ProjectImportEntry`、`ProjectImportList`、`ProjectImportPlan`。
- `packages/core/src/projectImport.ts`：
  - `planProjectImport(db, list)`：只读、纯计算。已有项目按 `name` 匹配（大小写不敏感，和 `ProjectService.create` 的判重口径一致）；只把状态不同的放进 `update`；`unchanged` 放库里的项目；`invalid` 放 status 不合法、name 为空 / 超 80 字、清单内重名、库里同名项目不止一个的条目，并给原因。`root_path` 只做登记前检查（目录已登记给别的未归档项目、或清单内同目录两新条目都算无效），不读目录。
  - `applyProjectImport(db, plan)`：一个事务里只用 `ProjectService.createMany` / `updateStatus`；新建后按清单改状态（`create` 只会建出 active）；已有项目只改 status，不动 `root_path` / `description`；不直接写 SQL，不建 `project_snapshot` 来源。

## 已知缺口

- 条件 7 的真实同名项目在现 schema 下建不出来（`name UNIQUE`）；代码分支按「查询结果多于一行」处理，测试用替身库。
- 预览后到确认前如果库被别人改了，`apply` 会按**确认时**的库重新算一遍（不照旧预览盲写）；两次数目可能不同，界面只显示实际写入数。规格没要求提示这种并发差异。
- `root_path` 只登记，不授予读取、不建 `project_snapshot`；这是规格约束，不是缺口。
