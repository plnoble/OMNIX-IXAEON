## Codex 审查（A 档）

三轮都由 Claude 代审（本机 Codex 额度用完，脚本自动改的；每轮输出在 `.logs/k1-codex*.log`），最终结论：**可以合并**，记录见 [K1-Codex审查.md](K1-Codex审查.md)。

- **第 1 轮：需要修改。** 1 条必须改：交付说明写着「`apply` 会按确认时的库重新算一遍」，但核心 `applyProjectImport` 不重读库，重算实际在 K1b 的 IPC 层。已改成如实描述（见「已知缺口」）。5 条建议里：补了「新建项目 paused / archived」测试；条件 7 改成真库 `E` / `e` 两行；`seen` 的顺序问题顺手改到「只有真正收下的条目才记名字」（第 2 轮又发现这个改法漏了已有项目，见下）；`sameNameRows` 用 `ProjectService.get` 再取一次——看源码 `ProjectService.get` 就是 `SELECT *`，没有字段映射，不改。
- **第 2 轮：需要修改。** 4 条必须改都是真的：① 清单里同一个**已有**项目写两遍时，第一条 `return` 前没记名字，第二条也会进 `update`；已改成匹配到已有项目时立刻 `seen.set`，并补「条件 3：重名的是库里已有项目」。② 条件 7 原来只比了 plan 后的快照、没执行 apply；现在清单里另加一个合法新项目真的 apply，再比 `E` / `e` 两行。③ 条件 6 原清单没有 `root_path`，等于没测到「只登记目录」那条路；现在带临时合成目录，并同时断言 `project_snapshot` 来源 0、`permissions` 0。④ stat 数字过期，已按最终分支更新。
- **第 3 轮：可以合并**（0 条必须改）。剩下的建议和「需要人工确认」的处理：
  - `lower()` 只转 ASCII、JS `toLowerCase()` 转 Unicode：没改。清单以中文为主；统一口径要动 DB 查询或 done 后的共享代码，收益小于改动面。
  - `root_path: ""` 报「必须是字符串」不准确：没改，只在预览显示原因上有出入，不影响写入。
  - `ProjectService.create` 还有没有别的拒绝条件：看源码只有「空名 / 同名 / 同目录已登记给未归档项目」三条，不 `stat`、不规范化路径、不读目录；`rootOwner` 用的就是 `create` 同一条 `lower(root_path)` 比较，口径一致。`createMany` 中途抛错会整个事务回滚，不会半写。
  - 条件 8 只比 `description`、没比 `root_path`：没再加测试（审查已经过了，再改测试会变成第 4 轮）；实现里已有项目的 update 路径只调 `updateStatus`，根本不传 `root_path`。
  - 真机检查在 K1b：本支交付引用的 [K1b.md](K1b.md) 里有原样输出、两张截图路径和断言；K1b 的 `verify` 里 `local-user` 通过（1006 个跟踪文件无本机账户名），截图与输出都是合成数据。
  - GitHub 上的 CI：本棒不推（调度器替推），所以还没看；下一棒推送后先看 CI 绿再合并。
  - `ProjectService.updateStatus` 的副作用：看源码只改 `status` / `updated_at`，不撤授权、不碰别的表。

## 已知缺口

- 条件 7 的完全同名项目在现 schema 下建不出来（`name UNIQUE` 区分大小写）；代码按「查询结果多于一行」处理，真库上能用 `E` / `e` 这种大小写并存的历史数据覆盖，测试就是这么做的。
- `applyProjectImport` **完全信任传进来的 plan**（不重读库）。「确认时按当时的库重算」不在核心这一层，在 K1b 的 IPC：预览只把清单留在主进程，确认时重新 `planProjectImport(db, list)` 再 `applyProjectImport`。所以直接调用核心 `apply` 时不会防「预览后库被改」；界面路径不会照旧预览盲写。两次数目可能不同，界面只显示实际写入数（规格没要求提示这种并发差异）。
- `root_path` 只登记，不授予读取、不建 `project_snapshot`；这是规格约束，不是缺口。
