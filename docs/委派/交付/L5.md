```
## 3. git push 原样输出（失败）
fatal: unable to access '…': schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030e)
   Git 的远端分支存在吗：false
   收尾复查：远端 relay-probe/* 是空的

```

**为什么 `GIT_CONFIG_KEY_0` 不见了**：DSH 的子进程层会把「名字像凭据」的环境变量擦掉。它自己的代码里写得很清楚（`@deepseek-ai/dsh-subprocess/lib/index.js`，只读 DSH 自带文件）：

```
/**
* Credential-shaped environment names are NOT forwarded to children (the
* harness's own `DEEPSEEK_API_KEY`/secrets must not leak into a spawned
* process implicitly). One heuristic for every in-repo spawner; a
* deliberately supplied entry survives because explicit env layers merge
* after the scrub.
*/
const SENSITIVE_ENV_PATTERN = /KEY|PASSWORD|SECRET|TOKEN/i;
```

`GIT_CONFIG_KEY_0` 命中 `/KEY/i` → 被擦掉；`GIT_CONFIG_COUNT`、`GIT_CONFIG_VALUE_0` 不含那几个词 → 活下来。于是 git 看到「有个 count、没有 key」，**任何 git 命令都起不来**。也就是说**契约第 1 条照字面实现也推不上去**（见「已知缺口」第 1 条）。

**这一跑说明什么：**

1. **schannel 的那个错没了**——换成 OpenSSL 之后 TLS 这一层通了，git 一路走到「要用户名/凭据」。
2. 新的卡点是**凭据助手**：系统 gitconfig 里的 `credential.helper = manager` 要靠 `sh.exe`/`bash.exe` 起一个提示脚本；在 DSH 的受限令牌下**建不了 MSYS/Cygwin 的信号管道**（`couldn't create signal pipe, Win32 error 5`，和 L4 甲里 `git push` 那个失败同一类），于是 `error: failed to execute prompt script (exit code 66)` → `fatal: could not read Username for 'https://github.com'`。
3. DSH 自己也没有绕：它是**空提交建好、分支留在本地**，如实记了报错。远端**没有留下任何分支**（收尾复查 `relay-probe/*` 是空的；两次都没推上去，所以也没有要删的远端分支）。

## 已知缺口

1. **契约第 1 条（用 `GIT_CONFIG_KEY_<n>` 注 OpenSSL）在 DSH 里行不通**：DSH 的子进程层按 `/KEY|PASSWORD|SECRET|TOKEN/i` 擦环境变量，`GIT_CONFIG_KEY_0` 到不了 git 手里，git 反而**所有命令都起不来**（真机甲第 1 次的原样输出）。测试仍然照契约测启动器有没有注这三个变量（那部分是对的），但**实现照契约写也推不上去**——要改契约。
2. **就算 TLS 通了，凭据助手在受限令牌下起不来**（`sh.exe`/`bash.exe` 建不了信号管道，Win32 error 5）→ 认证这步过不去。这一单**没有**去改 git 的凭据设置、没有换协议、没有把令牌写进任何文件或环境变量。
3. 建议（这一单不做，交整合方与用户定）：**TLS 用仓库级 `http.sslBackend=openssl`**（已证明能通），**推送交给 relay 代做**（relay 不在沙箱里，登录态是用户本机的）——或者换一个不经 `sh.exe` 的凭据助手（这属于凭据设置的改动，得用户拍板）。
4. 甲只量到「建分支、空提交成功；推送失败」；两轮都没有在远端留下探测分支。
