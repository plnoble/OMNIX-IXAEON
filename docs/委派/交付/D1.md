## 验收测试（v2 规格任务）

两份测试，开头注释逐条对应规格条件：

- `apps/desktop/test/acceptance/d1-coding-task-draft.test.ts`（9 条）：条件 1–5 与条件 6 的名单、MCP 声明、本地服务放行。
  - 条件 1：替身会话挂起模拟「项目对话正在回答」，桥接调用从提问的异步上下文之外发起（真 Hermes 经 MCP 服务转 HTTP 进来，不在 `withAskRun` 的上下文里）。断言：任务 `project_id` 是这个对话的项目、`origin_run_id` 是这一轮的 runId（和 `ask()` 返回的 runId 相等）、`acceptance_json` 是给的条件、状态 draft；返回 `{ taskId, status: 'draft', project: 项目名, note }`，note 提「要做」与「不要说已经做完」；`scope` 缺省整个项目（`['.']`）、显式时存相对路径；验证命令留空（`allowed_commands_json` 为 `[]`）；这一轮回答下面出现待办卡（`linked_id` 指向任务、挂在这条回答的消息上）；审计 `hermes.propose_coding_task` 记任务 id 与项目 id。
  - 条件 2：没有正在回答的提问、正在回答的对话不属于项目 → 报「编码任务只能在项目对话里提（先选项目、开新对话）」，不建任务。
  - 条件 3：两个项目对话同时在回答 → 报「同时有多个项目对话在回答，分不清是哪个，请稍后再提」，不建任务。另有一条对照（自加）：一个项目对话加一个个人对话同时在回答 → 用那个项目，正常建出。
  - 条件 4：目标为空/空白/超 2000 字、条件 0 条/9 条/单条超 200 字、`scope` 越出项目（`../` 与绝对路径）→ `VALIDATION_FAILED`，不建任务。开头先合法调用建出一条草案再测非法——排除「工具没接上、任何调用都报 VALIDATION_FAILED」的假绿（现状里 `hermesTool` 对未知工具落到 `record_observation` 兜底，恰好也报 VALIDATION_FAILED）。
  - 条件 5：参数里写了别的项目（`projectId`、`project` 双写进去）→ 不认，任务仍建在正在回答的那个项目下。
  - 条件 6：`HERMES_BRIDGE_TOOLS` 名单里有 `propose_coding_task`；`apps/mcp` 的 `registerHermesBridgeTools` 声明它（替身服务只记录注册，断言 schema 键含 goal/acceptance/scope）；本地 `/api/hermes/tool` 按名单放行（LocalServer 注入转发到 `hermesTool`，断言 200 且真的转发了）。
- `packages/core/test/acceptance/d1-convention.test.ts`（2 条）：条件 6 的约定文字。协议替身（PassThrough），不启动本机 Hermes，看 `prompt.submit` 实际发出去的文字。记忆桥开着：约定里写模型真正看得到的名字 `mcp__ixaeon__propose_coding_task`，说明草案要点「要做」才开工、不要自己说已经做完，且原有记忆路由约定还在；桥关着：全文不提这个工具（这条现状就过，留着防实现只加一半）。
