## 验收测试（v2 规格任务）

两份测试，开头注释逐条对应规格条件：

- `apps/desktop/test/acceptance/d1-coding-task-draft.test.ts`（13 条）：条件 1–5 与条件 6 的名单、MCP 声明、本地服务放行。
  - 条件 1：替身会话挂起模拟「项目对话正在回答」，桥接调用从提问的异步上下文之外发起（真 Hermes 经 MCP 服务转 HTTP 进来，不在 `withAskRun` 的上下文里）。断言：任务 `project_id` 是这个对话的项目、**`goal` 与传入一致**、`origin_run_id` 是这一轮的 runId（和 `ask()` 返回的 runId 相等）、`acceptance_json` 是给的条件、状态 draft；返回 `{ taskId, status: 'draft', project: 项目名, note }`，note 提「要做」与「不要说已经做完」；`scope` 缺省整个项目（`['.']`）、显式时存相对路径；验证命令留空（`allowed_commands_json` 为 `[]`）；这一轮回答下面出现待办卡（`linked_id` 指向任务、挂在这条回答的消息上）；审计 `hermes.propose_coding_task` 记任务 id 与项目 id。
  - 条件 2：没有正在回答的提问、正在回答的对话不属于项目 → 报「编码任务只能在项目对话里提（先选项目、开新对话）」，不建任务。
  - 条件 2/契约 3（两条）：没有正在回答时、只有个人对话在回答时，**参数里带了合法项目 id 也不认**——项目一律不由模型选，不能拿参数兜底。都断言报「编码任务只能在项目对话里提」且不建任务。
  - 条件 3：两个项目对话同时在回答 → 报「同时有多个项目对话在回答，分不清是哪个，请稍后再提」，不建任务。另有一条对照：一个项目对话加一个个人对话同时在回答 → 不建草案（契约 3 的成功路径只认「恰好一个正在回答」；报哪种错规格没写死，见已知缺口）。
  - 条件 4：目标为空/空白/超 2000 字、条件 0 条/9 条/单条超 200 字/**单条为空字符串或空白**（契约 2：每条 1–200 字）、`scope` 越出项目（**`../outside`、裸 `..`、`..\outside`、`/outside`、`a/b/../../..` 嵌套越界、`C:\tmp` 绝对路径**）→ `VALIDATION_FAILED`，不建任务。开头先合法调用建出一条草案再测非法——排除「工具没接上、任何调用都报 VALIDATION_FAILED」的假绿（现状里 `hermesTool` 对未知工具落到 `record_observation` 兜底，恰好也报 VALIDATION_FAILED）。
  - 条件 5：参数里写了别的项目（`projectId`、`project` 双写进去）→ 不认，任务仍建在正在回答的那个项目下。
  - 条件 6：`HERMES_BRIDGE_TOOLS` 名单里有 `propose_coding_task`；`apps/mcp` 的 `registerHermesBridgeTools` 声明它（替身服务记录注册与处理函数，断言 schema 键含 goal/acceptance/scope；**对注册的 raw shape 做字段级 `safeParse` 核对**——goal/acceptance 必填、goal 上限 2000 字含边界、acceptance 必须是数组且 1–8 条、单条 1–200 字含边界、scope 可省略；并**真的调用一次**注册进去的处理函数，核对名称与参数原样转给调用通道、返回值原样回来）；本地 `/api/hermes/tool` 按名单放行（LocalServer 注入转发到 `hermesTool`，断言 200 且真的转发了）。
  - 约束（自加一条）：草案不批准、不派发、不跑命令——执行器替身与验证替身计数，提问期间和回答结束后都是 0，任务停在 draft、没有批准行。
  - 契约 4（自加一条）：验证命令留空的草案点「要做」走 D3 的自动派发后，验收回报里如实写「还没有独立验收」（承载处是 D3 已有的 `taskReport.verifyLine`：验证没跑且原因为「没有有效验证命令」时输出这句）。

## Codex 审查

B 档，审查不作为合并关卡（锁定仍由整合方做）。用户 2026-09-28 说可以审、Codex 有额度，跑了两轮 `node scripts/codex-review.mjs D1`（0.158.0，对照 `docs/委派/D1-聊天里提编码任务.md`），记录在 `docs/委派/交付/D1-Codex审查.md`。第一轮结论「需要修改」，七条意见已全部改：

- 项目对话与个人对话同时回答：原测试自行规定「仍建草案」，放宽了契约 3「恰好一个正在回答」。改为断言不建草案（报错文案规格没写死，见已知缺口）。
- 补 `acceptance: ['']` 与空白条件：每条至少 1 字，空条件必须拒绝。
- 补执行监测：执行器替身与验证替身计数，提问期间和回答结束后都断言 0 次，任务停在 draft、无批准行。
- 约定文字加严：除工具名外，断言写明触发条件（写代码、修 bug、加功能）、写清目标与能验收的条件。
- 「还没有独立验收」：补一条走 D3 自动派发的用例，断言验收回报含这句（承载处是已有的 `taskReport.verifyLine`，见上）。
- MCP 声明：替身改为记录处理函数并真的调用一次，核对转发的名称、参数与返回值（原为「建议」，一并改了）。
- 本交付说明补贴了实际命令与输出（见上）。

第二轮结论仍是「需要修改」，五条意见也已全部改：

- 成功用例没核对任务保存的目标：条件 1 补 `goal` 断言，传入什么存什么。
- 没测「没有正在回答（或只有个人对话）时参数带合法项目」：契约 3「项目一律不由模型选」要兜底也拒，补两条，都断言报「编码任务只能在项目对话里提」且不建任务。
