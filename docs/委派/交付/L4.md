1. **DSH 的默认沙箱里推不了 GitHub。** 失败在 Windows schannel 取 TLS 客户端凭证那一步（`SEC_E_NO_CREDENTIALS`），**请求还没到 GitHub 的鉴权**；同一条报错里还有「No such host is known」，DNS 可能也被沙箱挡住。
2. 建分支、空提交都成了；那条空提交只留在临时克隆里（临时目录已删）。
3. **探测分支从来没到过远端**，所以没有要删的远端分支（脚本自己查 `git ls-remote` 是 `false`；网络恢复后我也手动查过，没有 `relay-probe/*`）。
4. 按交代，DSH 没有改任何凭据设置、没有换 SSH、没有别的绕过。

这意味着「开发怎么把分支推上去」还没有落地答案：要么 relay 在 DSH 这一棒之后自己推（登录态在用户本机，relay 不是沙箱里的进程），要么给 DSH 一条能用的网络/凭证通道——后者是新的外发与权限，得用户拍板，不能我们自己开。

### 丙：额度字样 —— **判定：真额度，不是误认**

L2 丙第二次的输出已经跟着临时目录删掉了，交付说明里只剩那一行「撞额度的字样：usage_limit_reached」（是脚本在 DSH 的标准输出里匹配到的）。为了查清它的出处，我在 DSH 的安装目录里按只读方式找了这串字（没碰任何凭据文件，没跑 `--dump-config`），只有一处，是它自己的错误处理代码：

```
const err = parsed?.error;
if (err) {
    const code = err.code || err.type || "";
    if (/usage_limit_reached|usage_not_included|rate_limit_exceeded/i.test(code) || response.status === 429) {
        const plan = err.plan_type ? ` (${err.plan_type.toLowerCase()} plan)` : "";
        const mins = err.resets_at
            ? Math.max(0, Math.round((err.resets_at * 1000 - Date.now()) / 60000))
            : undefined;
        const when = mins !== undefined ? ` Try again in ~${mins} min.` : "";
        friendlyMessage = `You have hit your ChatGPT usage limit${plan}.${when}`.trim();
    }
    message = err.message || friendlyMessage || message;
}
```

结论：

1. `usage_limit_reached` 是**模型 API 返回的错误码**（`error.code`），DSH 把它识别成「撞额度」，并按 `error.resets_at` 算出还要等多少分钟。它不是仓库内容、工具输出里能巧合出现的东西。
2. 看 L2 丙第二次的表现：**没有 `final` 行、跑满 10 分钟被杀**——和「撞额度后等待/重试」完全对得上。所以那次是真额度。
3. 甲这一次同样长跑 555 秒，**没有**这串字 → 是间歇的，不是常量的误报。

建议（写进实现那一单的 `config.example.json`）：`quotaPatterns` 保留 `["usage_limit_reached", "session limit"]`；可以加 `rate_limit_exceeded`（DSH 也当同类处理）；**不要**加裸的 `429` 或人话 `usage limit`——DSH 的友好提示里有 `You have hit your … usage limit`，正常回答里也可能出现这几个词，会误伤。恢复时间/看用量：`error.resets_at` 有值时 DSH 自己会算出分钟数；具体额度窗口和用量页要去 DeepSeek 平台/DSH 桌面版看，我没有登录去看。

## 真机检查丁：只给 DSH 放开联网（2026-10-22）

**结论先说：DSH 没有「只放开联网」这种设置，而且也不需要——它的沙箱压根没挡联网。真正挡住的是 Windows 的 schannel TLS 后端在受限令牌下拿不到客户端凭据；换成 git 自带的 OpenSSL 后端，HTTPS 立刻就通。**

真调用共用 3 次（上限 3），没有额度字样，没调 Claude、没跑真 Codex。

### 一、先查「有没有只放开联网的设置」——**没有**

按任务书的三条路都走了（只读 DSH 自己的文件，没碰 `.credentials.yaml`，没跑 `--dump-config`）：

1. **`dsh --help`**：只有 `--profile` / `--patch <path>`（可叠加的补丁层）/ `--dump-config*`。没有联网开关。
2. **`dsh --profile headless --dump-config-schema`**（只打结构、不打凭据）：把 98 个挂载项的配置字段全看了一遍，凡是管限制的都在这儿——
   - `sandbox-policy`（`config24`）：只有 `mode`（`read-only` / `workspace-write` / `danger-full-access`）和 `workspaceRoot`；
   - `permission-presets`（`config28`）：预设的字段只有 `sandbox`、`approval`（`ask` / `never`）、`name`、`description`，**没有网络项**；
   - `bash-sandbox` / `pwsh-sandbox`：只有 `cwd`、超时、输出上限；
   - `sandbox-local`：只有 `runnerCommand`、`probeTimeoutMs`。
     全 schema 里跟「网络」沾边的只有一个 `allowLoopbackHttp`（`web-fetch` 插件，默认 false，管的是取本机回环地址），不是沙箱策略。
3. **读 DSH 自己的实现**（从 `resources/app.asar` 里解出 `@deepseek-ai/dsh-*` 的包文件，只读）：Windows 的沙箱是 `dsh-sandbox-windows-acl` 的 **WRITE_RESTRICTED 受限令牌 + ACL 写入授权**，包注释里把边界写死了：

   ```
   Known boundaries (inherent to restricted tokens, not this port):
    - writes are restricted; reads, network, and process visibility are NOT
      (WRITE_RESTRICTED intersects only write accesses);
   ```

   也就是说：这个沙箱**只管写入**，读、联网、进程可见性都不管。所以「只放开联网」这个开关在 DSH 里根本不存在——没有可叠的补丁项。

**没有写 `packages/relay/dsh-network.patch.yml`**：规格要求「找到了才写补丁，只改联网那一项」；没有这一项，硬造一个补丁就是无中生有。

### 二、那为什么乙推不上去？——**是 TLS 凭据，不是网络**

（`scripts/real/l4-dsh-network.mjs`，1 次真调用）

```
== 丁：DSH 的沙箱里能不能联网（只读探测）
   对照（脚本自己在沙箱外量）：ls-remote 退出码 0｜origin/main=86681e1
   DSH 退出码 0｜用时 41.3s
   JSONL 行 50｜tool_call 9 条｜最终回答 1 条
     tool=pwsh｜Resolve-DnsName github.com | Select-Object -First 3
     tool=pwsh｜git ls-remote https://github.com/plnoble/OMNIX-IXAEON.git HEAD
     ...
```

逐条的原样输出（脚本把所有工具调用与输出一条条对上打印，第二次跑；已遮临时目录）：

```
     ▶ Resolve-DnsName github.com | Select-Object -First 3
       ← Name Type TTL Section IPAddress ---- ---- --- ------- --------- github.com AAAA 1 Answer 2001:2::7a github.com A 1 Answer 198.18.0.123
     ▶ git ls-remote https://github.com/plnoble/OMNIX-IXAEON.git HEAD
       ← [stderr] fatal: unable to access 'https://github.com/plnoble/OMNIX-IXAEON.git/': schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030e) - <控制台乱码：安全程序包没有可用的凭证> [exit code: 1]
     ▶ curl.exe -sS -o NUL -w "%{http_code}" --max-time 30 https://github.com
       ← 000 [stderr] curl: (35) schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030e) [exit code: 1]
  ✓ DNS 解析出了地址
  ✓ 公开 HTTPS（schannel 后端）失败在拿不到凭据（不是网络不通）
  ✓ 没改文件（工作区干净）
```

要点：

- **DNS 通**（`github.com` 解析到 `198.18.0.123`，是本机代理的 fake-IP，说明流量确实被代理接走了）。
- **`git` 和 `curl` 都断在同一处**：Windows schannel 的 `AcquireCredentialsHandle` 报 `SEC_E_NO_CREDENTIALS`。这是 TLS 客户端凭据拿不到，**不是连不上、也不是没权限**——连公开仓库（本来不需要任何凭据）都一样失败。
- 第二次里 DSH 自己顺手试了 `git -c http.sslBackend=openssl ...`，但把 `-c` 写在了子命令后面，语法错（`unknown switch 'c'`），那次不算数。

### 三、绕开 schannel 就通（`scripts/real/l4-dsh-openssl.mjs`，1 次真调用）

```
     ▶ git -c http.sslBackend=openssl ls-remote https://github.com/plnoble/OMNIX-IXAEON.git HEAD
       ← 86681e170fce365f0672d5ecb9dbafb231058d7a HEAD
     ▶ git -c http.sslBackend=openssl ls-remote https://github.com/plnoble/OMNIX-IXAEON.git refs/heads/main
       ← 86681e170fce365f0672d5ecb9dbafb231058d7a refs/heads/main
     ▶ $env:GIT_SSL_BACKEND="openssl"; git ls-remote ... HEAD
       ← [stderr] fatal: ... schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS ...
  ✓ 沙箱里用 OpenSSL 后端读到了公开仓库的 sha
  ✓ 没改文件（工作区干净）
```

- **`git -c http.sslBackend=openssl` 在沙箱里读公开仓库：成了**（两次都读到 `main` 的 sha，和沙箱外量到的 `86681e1` 一致）。
- **`GIT_SSL_BACKEND=openssl` 这个环境变量写法不生效**（还是走 schannel）。要用就得用 `-c` 单次参数或写进仓库配置。
- 所以乙的失败不是「沙箱不给联网」，而是「schannel 在这枚受限令牌下取不到 TLS 凭据」。

### 给 L5 的建议（这一单不做，写清备选）

「开发怎么把分支推上去」现在有据可依了：
