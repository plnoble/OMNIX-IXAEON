# D2 沙箱实验：副本工作区里能不能跑真实项目的测试

日期：2026-09-29。分支：`prep/D2-spike`（基于 main @ `e77a6c8`）。
执行：调研 agent（prep）。所有实验在临时目录用合成项目完成，跑完即清理；
未调用任何模型、未跑 `codex exec`、未触碰用户真实数据。

## 0. 背景与问题

场景一（用户 2026-09-27 定的流程）：编码代理先按验收条件写测试 → 核心模型
对照条件核一遍 → 锁定指纹 → 再实现 → **独立跑测试验收**；实现时改了测试
就算失败。当前卡在独立验收：

- `CodingOrchestrator.verify` → `defaultCheck`
  （packages/core/src/execution/executor.ts:665）在 Node 权限模型下跑：
  只认 node，强制 `--permission --allow-fs-read=<工作区> --allow-fs-write=<工作区>`，
  剥离命令自带的 --permission/--allow-fs-*（验证器不能自己扩权），其他程序
  一律不跑（ran=false）。
- 工作区由 `copyProjectWorkspace`（packages/core/src/execution/workspaceCopy.ts）
  复制项目副本，**跳过 node_modules** 等依赖目录与密钥文件。
- 结果：TypeScript + vitest 这类项目（IXAEON 自己就是）的测试在副本里跑不起来。

## 2. E1：junction 挂 node_modules（原样输出摘录）

设置：`proj/node_modules`（内含 pnpm 风格相对 symlink 的合成依赖）→
`copy/node_modules` 为 junction 指回 `proj\node_modules`。

**只授权副本读取（`--allow-fs-read=<copy>`）→ 读依赖被拒：**

```
exit=1
Error: Access to this API has been restricted. Use --allow-fs-read to manage permissions.
    at realpathSync (node:fs:2799:17)
  code: 'ERR_ACCESS_DENIED',
  permission: 'FileSystemRead',
  resource: '\\\\?\\C:\\Users\\<用户>\\AppData\\Local\\Temp\\ixaeon-d2-e1-17816\\proj\\node_modules\\dep'
```

→ **读按 junction 解析后的真实路径判权**：必须补
`--allow-fs-read=<真实 node_modules>`。补上后 `DEP_VALUE=dep-1.0.0`、
`DECL_LEN=76`（依赖经 junction 正常解析，pnpm 风格包内 symlink 也能走通）。

**只授权副本写入 → 经 junction 写真实依赖竟然成功：**

```
### write-through-junction
exit=0
WRITE_OK (危险：真实依赖被写入)
[verify] 真实依赖里是否真的出现了写入文件: true
```

→ **写按链接路径判权（与读不对称）**：`--allow-fs-write=<copy>` 挡不住
经 junction 写穿到真实 node_modules。对照实验：显式授权真实 node_modules
写入后同样成功（语义确认）。**意味着 junction 方案下「编码代理和测试写不进
真实 node_modules」无法用权限模型保证**（缓解见 §6）。

**pnpm 单仓要不要挂每个包的 node_modules**：包内依赖经根 node_modules 的
`.pnpm` 硬布局解析（E1 已覆盖）；但 `workspace:*` 依赖的 symlink 指向
**兄弟包源码目录**（不在任何 node_modules 里）——单仓场景需要为每个兄弟包
目录加 `--allow-fs-read`（或直接授权真实仓库根读）。

## 3. E2：vitest 在 Node 权限模型下（原样输出摘录）

vitest 5.0.0 + vite 8.3.0（rolldown 打包线），Node v24.14.0。
渐进加旗标，最终最小集（全部变体与失败原因见 .logs/d2-e2-vitest-output3.txt）：

```
--permission
--allow-fs-read=<copy>              # 副本
--allow-fs-read=<真实 node_modules> # E1：读按真实路径
--allow-fs-write=<copy>
--allow-addons                      # rolldown 原生 .node 绑定加载
--allow-worker                      # tinypool worker 线程
--allow-child-process               # fork 池 / esbuild 子进程
--allow-fs-read=<os.tmpdir()>       # tinypool/vite 落临时目录
--allow-fs-write=<os.tmpdir()>
```

外加一个关键小动作：**副本里放一个空的 `pnpm-workspace.yaml`**——否则 vite
的 `searchForWorkspaceRoot` 会向上级目录探测（探测到未授权的临时根被拒）：

```
Error: Access to this API has been restricted. Use --allow-fs-read to manage permissions.
    at Object.existsSync (node:fs:290:18)
    at hasRootFile (...vite/dist/node/chunks/node.js:20394:38)
    at searchForWorkspaceRoot (...)
  resource: '\\\\?\\C:\\Users\\<用户>\\AppData\\Local\\Temp\\ixaeon-d2-e2-3760\\pnpm-workspace.yaml'
```

最终结果：

```
### D C + tmp 读写（tinypool/vite 落临时目录）
exit=0
Test Files  1 passed (1)
      Tests  1 passed (1)
```

三个必加的宽权旗标，Node 自己的安全警告（原样）：

```
SecurityWarning: The flag --allow-addons must be used with extreme caution. It could invalidate the permission model.
SecurityWarning: The flag --allow-child-process must be used with extreme caution. It could invalidate the permission model.
SecurityWarning: The flag --allow-worker must be used with extreme caution. It could invalidate the permission model.
```

**安全边界退到了哪里**：
1. `--allow-child-process` 下，node 主进程受限，但**它派生的子进程不受任何
   限制**——恶意/被诱导的测试可以 spawn 任意程序（全权）。
2. **Node 权限模型完全不限制网络**（无 --allow-net 概念）——测试可随意联网。
3. E1 的 junction 写不对称——真实 node_modules 可被写穿。
4. 结论：此组合是「防误伤」（主进程意外写坏工作区外的文件）而不是「防恶意」。

排障过程中排除的红鲱鱼（记录避免后人重踩）：vitest 5 已移除
`--reporter=basic`（会被当自定义模块加载而报错，用默认 reporter）；rolldown
的 `rolldown-binding.wasi.cjs` 不存在是加载失败的兜底文案，真实缺的是
`--allow-addons`。

## 4. E3：codex sandbox windows（原样输出摘录）

本机 codex-cli 0.130.0-alpha.5 提供 `codex sandbox windows <COMMAND>`
（Windows 受限令牌沙箱）。**不调模型、不花 Codex 额度**（纯本地执行器）。

配置考古（对 0.130 alpha 实测反推，schema 见 openai/codex
`codex-rs/config/src/permissions_toml.rs`）：

- `workspace-write` 等模式下 **必须提供 `--permissions-profile <NAME>`**；
- profile 定义在 `config.toml` 的 `[permissions.<NAME>]`（字段：filesystem
  glob→`read/write/deny`、workspace_roots、network.enabled）；
- `[permissions]` 有 profile 时还必须设 `[permissions.default_permissions]`
  （可 `extends = "<NAME>"`）；
- `codex sandbox` **没有 `--ignore-user-config`**，而本机用户
  config.toml 的 `service_tier = "default"` 被这个 alpha 版直接拒绝：

```
Error: C:\Users\<用户>\.codex\config.toml:1:16: unknown variant `default`, expected `fast` or `flex`
Caused by: unknown variant `default`, expected `fast` or `flex` in `service_tier`
```

→ 用独立 `CODEX_HOME`（临时目录+专用 config）绕开。**这条对 IXAEON 执行器
同样适用**：派发 `codex exec` 时如果用户 config 兼容性出问题，executor 现在
的 `--ignore-user-config` 是必要的（已在产品里）。

**elevated 模式实测（关键结果）**：

```
### 3b vitest @ profile + elevated   （.logs/d2-e3-codex-sandbox-output7.txt）
exit=0
Test Files  1 passed (1)
      Tests  1 passed (1)
[vitest-in-sandbox] PASSED
### 2b profile + elevated（同文件探针）
NETWORK=BLOCKED EACCES
```

- elevated（`-c windows.sandbox="elevated"`，IXAEON 执行器 Windows 同款）下：
  **vitest 真实跑通 + 联网被 OS 级拦截（EACCES）**——比 Node 权限模型强得多；
- 非 elevated 模式实测**很弱**：越界写（Local 根）放行、联网放行——不能用作
  安全边界；
- **elevated 的代价**：setup helper 需要 UAC 提权。本次连续三轮自动化重跑中，
  两轮出现 `orchestrator_helper_launch_canceled: ShellExecuteExW failed to
  launch setup helper: 1223`（UAC 被取消/无法弹出）→ **无人值守验证不可依赖**；
  helper 安装成功后的会话可连续工作（run7 证明），但 helper 失效/重装的时点
  不可控。

## 5. E4：零依赖路线 + 执行验证的 node 是谁（原样输出摘录）

**执行验证的 node**：

- 系统 node：`D:\Development\Node.js\Install\node.exe` @ **v24.14.0**；
- 打包应用的"node" = IXAEON.exe（Electron 内置 **Node 24.19.0**）：

```
打包 IXAEON.exe + ELECTRON_RUN_AS_NODE=1: exit=0 输出=AS_NODE=24.19.0
打包 IXAEON.exe 不带 ELECTRON_RUN_AS_NODE: exit=null stdout={"ts":"...","level":"info","message":"运
```

→ **产品缺口（P1 级）**：`defaultCheck` 的 `isNode` 检查
（`exe === process.execPath`）在打包环境命中 IXAEON.exe，而
`minimalChildEnv` 不传 `ELECTRON_RUN_AS_NODE=1` → 打包环境的验证命令会把
IXAEON 再启动一个 GUI 实例而不是跑测试。dev/CI 环境（真 node.exe）不受影响。
修复很小：defaultCheck 给子进程 env 注入 `ELECTRON_RUN_AS_NODE=1`（当
exe 是 Electron 时），或解析真 node 路径。

**零依赖测试（node:test 直跑 .ts，类型剥离默认开启）**：

```
== 3a) --permission 直跑 .ts 测试（零依赖，node:test 进程内） ==
exit=0
✔ add returns erasable-typed result (0.4383ms)
ℹ tests 1  ℹ pass 1  ℹ fail 0
```

只需 `--permission --allow-fs-read=<copy> --allow-fs-write=<copy>` 三个旗标
（进程内、无 worker/子进程/插件）。覆盖面：

```
== 4) 不可剥离语法（enum）==
ENUM_FAIL: TypeScript enum is not supported in strip-only mode
```

- 支持：类型注解、interface、泛型等**可剥离**语法；相对导入必须写
  `.ts` 扩展名（`import { add } from './math.ts'`）；
- 不支持：enum、命名空间、参数属性等不可剥离语法；**任何 npm 依赖**
  （IXAEON 自身的 vitest 测试不适用此路线）；
- `node --test` 模式（会为测试文件起子进程）在本环境实测异常
  （`Could not find ...math.test.ts`），**直跑模式没有问题**——推荐直跑。

## 6. 结论与推荐

| 路线 | 能跑 vitest | 隔离强度 | 无人值守 | 依赖 |
| --- | --- | --- | --- | --- |
| A. Node 权限模型 + junction | ✅（8 旗标+workspace 标记） | 弱（子进程无沙箱、网络不管、junction 写穿） | ✅ | 无 |
| B. codex sandbox windows (elevated) | ✅（实测 PASSED） | 强（OS 级：联网拦、越界写拦） | ❌（UAC 不可控；非 elevated 又太弱） | Codex CLI（已装机） |
| C. 零依赖 node:test 直跑 | ❌（不用 vitest） | 强（进程内、最小旗标） | ✅ | 无（Node 24 内置） |

**推荐：C 为默认，A 为依赖型项目的受控扩展，B 不作为验证依赖。**

1. **默认路线 C**：验收条件要求「测试可独立运行」时，委派单直接规定测试用
   `node:test` + 可剥离 TS 语法 + 显式 `.ts` 扩展名 + 零 npm 依赖（纯逻辑
   测试完全够用：算法定义、纯函数、数据变换类验收）。defaultCheck 现有实现
   已能跑（3a 实测），只需在规格里写清测试书写约束。
2. **路线 A（扩展，需整合方拍板风险）**：对必须用项目自身测试栈（vitest）的
   任务，按 E2 旗标集执行，并接受三条缓解：
   - 接受「防误伤不防恶意」定位，配合现有 A05 工作区哈希（改动范围守卫）；
   - **junction 写穿真实 node_modules 的风险**：无法用权限模型堵（E1 不对称）。
     可行缓解：真实 node_modules 对执行进程设拒绝写 ACL（实现复杂度另评），
     或接受风险并把真实依赖完整性检查（npm/pnpm verify 前后哈希）列入真机
     检查。此项**必须**由整合方拍板，不自行决定。
   - `pnpm-workspace.yaml` 标记 + 真实仓库根读授权（workspace:* 依赖）写入
     copyProjectWorkspace 的配套改动。
3. **路线 B**：不建议作为 verify 的默认依赖（UAC 不可控、alpha CLI 配置易
   变、用户 config 兼容性问题）。它的价值是给**执行阶段**（CodexCliExecutor
   已在用 elevated）提供一致性——验证若也要走它，必须先解决 UAC（一次性
   安装 helper 的产品化流程），列为待解决问题。

## 7. 顺带发现的产品缺口（交整合方排期，不在 D2 范围内实现）

1. **打包环境验证命令失效（P1）**：`defaultCheck` 在打包环境命中
   IXAEON.exe 但不传 `ELECTRON_RUN_AS_NODE=1` → 验证命令变成再启动一个
   GUI 实例。修复小（env 注入），影响大（打包版的独立验证完全不可用）。
2. `stopServer` 的日志文案「本地服务已停止（数据恢复）」出现在普通退出路径
   （appRuntime.ts:714），文案误导（2026-09-08 用户验收时即被误导）。

## 8. D2 规格草稿（交整合方定稿）

> **任务**：D2 独立验证执行器支持真实项目测试（沙箱实验结论落地）
>
> **要什么**：编码任务的 `allowed_commands` 验证能按项目测试栈分三档执行，
> 全部走统一沙箱入口（defaultCheck），档位由委派单在 `allowed_commands`
> 里显式声明，验证器不得自行扩权：
> 1. **零依赖档**（默认可用）：`node <test.ts>` 直跑——测试必须用
>    `node:test` + 可剥离 TS 语法 + 显式 `.ts` 导入扩展名 + 零 npm 依赖；
> 2. **依赖档**：`node <node_modules/vitest/vitest.mjs> run`——按实验旗标集
>    执行（见 §3），前提是 copyProjectWorkspace 建 junction 并放
>    pnpm-workspace.yaml 标记、defaultCheck 追加真实 node_modules 读授权；
> 3. **拒绝档**：其他程序维持 ran=false 不裸跑（现状不变）。
>
> **契约**：
> - defaultCheck 保持「剥离自带 --permission/--allow-fs-*、强制副本读写边界」
>   现状；新增旗标由产品按档位注入，不经命令自带；
> - 打包环境先修 ELECTRON_RUN_AS_NODE 缺口（§7.1），否则档位 1/2 在打包版
>   不可用；
> - 改动范围守卫（A05 哈希）不变；junction 写穿风险按 §6.2 由整合方拍板
>   缓解方案后才允许启用依赖档。
>
> **约束**：不新增外部依赖；不放宽 locked 测试；实验脚本
> scripts/real/d2-*.mjs 保留为回归证据。
>
> **验收条件**（写测试时逐条对应）：
> 1. 零依赖档：合成 TS 项目（node:test）在副本内经 defaultCheck 跑通，
>    exit=0；含故意失败的测试 → exit=1 且 verify_status=failed；
> 2. 依赖档：合成 vitest 项目在副本内按 §3 旗标集跑通；旗标集少任何一项
>    → 如实失败不静默降级；
> 3. 拒绝档：`npm test` 等非 node 命令 ran=false 且输出说明不变；
> 4. 打包环境 ELECTRON_RUN_AS_NODE 修复后，IXAEON.exe 作为验证 node 能
>    正确执行 `-e` 脚本（不再启动 GUI）；
> 5. 现有 execution 相关 locked 测试全部继续通过。
>
> **真机检查**：用 IXAEON 本仓副本（worktree）按依赖档跑
> `vitest run --project unit`（限单文件）并贴原样输出；打包版跑零依赖档
> 冒烟。检查脚本入 scripts/real/。
>
> **档位**：A（executor 行为扩展 + copyProjectWorkspace 配套，无权限/隐私
> 语义变化；junction 写风险缓解若选 ACL 方案则该部分升 B 交整合方）。
>
> **大小**：executor.ts + workspaceCopy.ts + 测试 ≈ 150–250 行（≤300 拆分
> 规则内）。

## 9. 没做成 / 没验证的（如实）

1. E2 的 `--offline` pnpm 安装失败（store 无元数据），退回
   `--prefer-offline`（有网络参与版本解析）——离线纯安装路径未验证；
2. E3 elevated 的 UAC 弹窗行为无法在无人值守下复现成功路径（一次通过依赖
   helper 缓存）；「helper 一次性安装后长期可靠」未验证；
3. `codex sandbox windows` 的 glob 语义（`:...`/`C:/...` 混用）未穷尽——
   只验证了实验所需的最小配置可用；
4. junction + 拒绝写 ACL 的缓解方案未实验（超出本轮范围，已列规格待拍板）；
5. `node --test` 子进程模式异常未深挖（直跑模式已满足需求）；
6. scripts/worktree.mjs 在 main 尚不存在（grok/D1、grok/D4 分支携带）——
   本次按同样目标布局用原生 `git worktree add` 建工作区。
