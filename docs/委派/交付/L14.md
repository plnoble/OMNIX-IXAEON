## 真机通过

### 1. 规格要求先确认原因：`electron.exe` 的两个退出码

在调度器起的 DSH 里（就是这一棒），先清掉宿主带进来的 `ELECTRON_RUN_AS_NODE`（`scripts/verify.mjs` 第 14 行本来就会清）：

```
electron.exe --version                  → 退出码 -2147483645（0x80000003），无输出
electron.exe --no-sandbox --version     → v44.1.1，退出码 0
```

不清 `ELECTRON_RUN_AS_NODE` 时（直接在 DSH shell 里跑）看到的是另一回事：`--version` 当纯 Node 跑、打印 `v24.19.0` 退出 0；`--no-sandbox` 反而报 `bad option: --no-sandbox` 退出 9。所以门禁里的症状确实是沙箱，`--no-sandbox` 能过这一步。

### 2. 四步界面复审：`--no-sandbox` 过了崩，但应用还是起不来

同一份 `playwright.needs-lifecycle-20260908.config.ts`：

- 不带 `IXAEON_ELECTRON_NO_SANDBOX`：3 条都 `Error: Process failed to launch!`（`0x80000003` 那条路）。
- 带 `IXAEON_ELECTRON_NO_SANDBOX=1`：Electron 起来了，但紧接着日志里是

```
Lock file can not be created: 拒绝访问。 (0x5)
Error writing DevTools active port to file <用户目录>\AppData\Roaming\Electron\DevToolsActivePort: 拒绝访问。 (0x5)
<process did exit: exitCode=0>
```

3 条仍失败。`apps/desktop/src/main/index.ts:56` 的 `app.requestSingleInstanceLock()` 失败后 `app.quit()`——应用自己退出了，不是界面断言失败。

### 3. 进一步查到的原因：工作区的低完整性标签让 `electron.exe` 以 Low IL 起

用合成的最小 Electron 探针（`scripts/real/l14-electron-integrity.mjs`，`node scripts/real/l14-electron-integrity.mjs` 直接跑；输出遮掉用户目录）：

```
Electron 进程的完整性级别：Low（本机 shell 一般是 Medium）
单实例锁（--user-data-dir 在工作区）：true
写 TEMP：EPERM
写 APPDATA：EPERM
写 LOCALAPPDATA：EPERM
写 workspace：ok
```

`--user-data-dir` 指到 `%TEMP%` 时 `requestSingleInstanceLock()` 为 `false`。把同一份 electron dist 原样复制到 `%LOCALAPPDATA%\Temp`（不在工作区、Medium 标签）再起：进程变成 **Medium**，上面三个目录都写得进。

结论：DSH 的 Windows 沙箱给工作区打了低完整性标签；`electron.exe` 在工作区里（`node_modules`）就带着这个标签，进程被降到 Low IL。Low IL 写不了 Medium 的 `%TEMP%`/`%APPDATA%`，所以单实例锁建不起来、应用退出。**这不再是 `--no-sandbox` 能解决的**（`--no-sandbox` 只关 Chromium 自己的沙箱）。

### 4. 反过来验证代码本身是对的

把本棒的 `TEMP`/`TMP`/`APPDATA`/`LOCALAPPDATA` 都指到工作区下面（Low IL 写得进的地方）再跑四套界面复审，**12 条全过**：

```
needs-lifecycle-ui：3 passed (11.9s)
understanding-ui：2 passed (19.6s)
sources-wizard-ui：4 passed (13.6s)
recheck-ui（含 project-audit-ui）：3 passed (12.0s)
```

也就是说：`electronArgs` 的改动和启动器加的环境变量是有效的；在本机跑不过的是「门禁的临时目录/应用数据默认落在 `%TEMP%`/`%APPDATA%`，而 DSH 工作区里的 Electron 是 Low IL」这一层。

## 已知缺口

1. **主要缺口**：DSH 的沙箱给工作区打低完整性标签，工作区里的 `electron.exe` 以 Low IL 运行，写不了 Medium 的 `%TEMP%`/`%APPDATA%`。`--no-sandbox` 只修掉了 `0x80000003`，修不了这一层。要整合方（可能需要用户拍板）定怎么办，可选的方向：
   - DSH 的沙箱不要把工作区里的 `electron.exe`（或整个工作区）降到 Low IL，或给门禁的 Electron 开 Medium；
   - 门禁跑界面复审时把 `TEMP`/`APPDATA` 指到工作区（这会动 `scripts/verify.mjs`，本单规格明确不许动，所以这单没做）；
   - 接受 DSH 里这四步跑不了、只在别的机器/CI 上跑（那样接力的「verify 全过」永远拿不到，需要改接力对门禁的判法）。
2. 本单没有推送，CI 没验。CI 的工作区没有低完整性标签，预期 `--no-sandbox` 不影响 CI 的这四步；但这一棒没有数据能证明，交给调度器推送后看。
3. 本机 `node scripts/verify.mjs` 是带着 `IXAEON_ELECTRON_NO_SANDBOX=1` 手动跑的（这一棒的 DSH 是改代码之前起的，启动器的新环境变量还没生效）。启动器那一层由验收测试的假安装目录覆盖。
