## 已实现

`OpenAIResponsesProvider` 的两条路（`/responses`、`/chat/completions`）都改成 `stream: true`，按服务端推送事件读。网关一开始生成就先把响应头发回来，慢模型思考超过 100 秒不再被按「没回应」掐断。

```
packages/core/src/extraction/model/openai.ts | 170 行新增、8 行删除（相对 main）
```

源码改动计入 300 行上限。没有新增迁移，没有改提示词、发给模型的内容和聊天（Hermes）那条路。

行为：

- `/responses`：累加 `response.output_text.delta`，`response.completed` 结束；`response.failed` 与 `error` 事件抛 `ModelError`，限流和服务端类（`rate_limit`、`server_error`、`overloaded`、`unavailable`、`timeout`、5xx）算暂时性。
- `/chat/completions`：累加 `choices[0].delta.content`，`data: [DONE]` 结束。
- 事件按空行切分，被拆在两次读取之间的能拼回去。
- 网关不支持流式：返回的不是 `text/event-stream` 就按原来的非流式解析；对 `stream` 报 400 就记住「这个实例不支持」，去掉 `stream` 重发一次，之后不再带。
- 没有另加超时，Node 自带的 300 秒没收到字节照旧算网络错误。429 / 5xx 与网络错误的一次重试不变。

和规格不一样的地方：无。

## Codex 审查（A 档）

第一轮（2026-09-27）退出码 1，九条「必须改」都改了：读取中断纳入网络错误的一次重试；`error` 事件的 code 与 message 认顶层；流式错误套进既有的「API 错误 429 / 500 / 400」前缀（队列按这三个前缀认类别）；返回普通 JSON 也记住不再尝试流式；chat 回退去掉 `stream` 字段而不是发 `stream: false`；只有错误正文提到 stream 的 400 才回退；条件 1 的测试改成规格要求的三次读取、两段 delta；真机脚本先 `flushHeaders()` 并记录响应头到达时间；verify 的运行号见下。

第二轮（2026-09-27）退出码 1，六条「必须改」也都改了：事件分隔兼容 CRLF 并跨读取拼接；`response.completed` 与 `[DONE]` 即刻停止读取并释放 reader；没等到完成标记算截断、按网络错误重试，只有 completed 没有文字仍报空文本；`stream` 的识别用词边界匹配，`upstream` 不再误判；错误分类只认 code 里的限流与 5xx 码，不在消息正文里找数字；条件 1 改成三块读取、两段非空 delta。

第三轮（2026-09-27）退出码 1，三条「必须改」：5xx 只从 code 字段认（`500`、`503` 这类，前后有边界），消息正文里的数字完全不参与判定，测试补了「invalid_prompt + 超过 512 tokens」的反例；`unsupported` 的匹配同样加词边界，「unsupported upstream model」不再命中，测试补了反例；条件 1 的三块改成第一段完整、第二段跨块，两段都非空。截断重试在 `readOrRetry` 里识别「流在完成前结束」并按网络错误重试一次，测试断言共两次请求。

第四轮（2026-09-27）退出码 1，三条「必须改」：`rejectsStream` 现在要求正文同时出现独立的 `stream`（词边界）和拒绝类动词（unsupported / not support / unknown parameter / invalid parameter / not enabled / does not），「invalid schema property 'stream'」不再误触发；`streamError` 把 code 归一化为字符串再认，JSON 数字 429/503 可重试、400 不可重试，各有测试；条件 1 补回 `response.created` 事件（与 delta 同在第 1 块），保持三次读取、两段非空 delta、第二段跨块。

第五轮（2026-09-27）退出码 1，两条「必须改」：`rejectsStream` 改成「拒绝词与独立的 stream 之间不超过 12 个字符」的成对匹配——「stream must be false」命中（禁用词紧挨 stream），「unsupported schema property 'stream'」不命中（中间隔了 16 个字符的 schema property），「unsupported upstream model」不命中（没有独立的 stream），都有测试；`streamError` 增加 `type` 类别参数，`error.type="server_error"` 没有 code 也算可重试，测试补了这条。真机输出补了脚本必然打出的 `FAKE_SERVER` 与 `HEADERS_FLUSHED` 两行。

「建议」：条件 5 的重试次数由既有测试断言，见上面验收测试一节；源码统计按完整 diff 更新。
