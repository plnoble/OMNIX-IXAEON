# M1 慢模型不再超时 交付

- 分支：grok/M1，基于 main `e1ccd72`；档位 A
- 执行方：Grok

## 已实现

`OpenAIResponsesProvider` 的两条路（`/responses`、`/chat/completions`）都改成 `stream: true`，按服务端推送事件读。网关一开始生成就先把响应头发回来，等待期不再是没有回应的死等。本机假流式服务验证了响应头第 0 秒到达、文字第 110 秒到达仍能拿全；真实网关上是否消除 524 超时，待用户切回 grok-4.6 重分析后确认（见「真机检查」）。

```
packages/core/src/extraction/model/openai.ts | 233 行新增、8 行删除（相对 main），合计 241 行
```

源码改动计入 300 行仓库上限与 M1 规格的 250 行上限（审查按新增+删除合计；合计 241）。没有新增迁移，没有改提示词、发给模型的内容和聊天（Hermes）那条路。

行为：

- `/responses`：累加 `response.output_text.delta`，`response.completed` 结束；`response.failed` 与 `error` 事件抛 `ModelError`，限流和服务端类（`rate_limit`、`server_error`、`overloaded`、`unavailable`、`timeout`、5xx）算暂时性。
- `/chat/completions`：累加 `choices[0].delta.content`，`data: [DONE]` 结束。
- 事件按空行切分，被拆在两次读取之间的能拼回去。
- 网关不支持流式：返回的不是 `text/event-stream` 就按原来的非流式解析；对 `stream` 报 400 就记住「这个实例不支持」，去掉 `stream` 重发一次，之后不再带。
- 没有另加超时，Node 自带的 300 秒没收到字节照旧算网络错误。429 / 5xx 与网络错误的一次重试不变。

和规格不一样的地方：无。

## Codex 审查（A 档）

第一轮（2026-09-27）退出码 1，九条「必须改」都改了：读取中断纳入网络错误的一次重试；`error` 事件的 code 与 message 认顶层；流式错误套进既有的「API 错误 429 / 500 / 400」前缀（队列按这三个前缀认类别）；返回普通 JSON 也记住不再尝试流式；chat 回退去掉 `stream` 字段而不是发 `stream: false`；只有错误正文提到 stream 的 400 才回退；条件 1 的测试改成规格要求的三次读取、两段 delta；真机脚本先 `flushHeaders()` 并记录响应头到达时间；verify 的运行号见下。

第二轮（2026-09-27）退出码 1，六条「必须改」也都改了：事件分隔兼容 CRLF 并跨读取拼接；`response.completed` 与 `[DONE]` 即刻停止读取并释放 reader；没等到完成标记算截断、按网络错误重试，只有 completed 没有文字仍报空文本；`stream` 的识别用词边界匹配，`upstream` 不再误判；错误分类只认 code 里的限流与 5xx 码，不在消息正文里找数字；条件 1 改成三块读取、两段非空 delta。

第三轮（2026-09-27）退出码 1，三条「必须改」：5xx 只从 code 字段认（`500`、`503` 这类，前后有边界），消息正文里的数字完全不参与判定，测试补了「invalid_prompt + 超过 512 tokens」的反例；`unsupported` 的匹配同样加词边界，「unsupported upstream model」不再命中，测试补了反例；条件 1 的三块改成第一段完整、第二段跨块，两段都非空。截断重试在 `readOrRetry` 里识别「流在完成前结束」并按网络错误重试一次，测试断言共两次请求。

第四轮（2026-09-27）退出码 1，三条「必须改」：`rejectsStream` 现在要求正文同时出现独立的 `stream`（词边界）和拒绝类动词（unsupported / not support / unknown parameter / invalid parameter / not enabled / does not），「invalid schema property 'stream'」不再误触发；`streamError` 把 code 归一化为字符串再认，JSON 数字 429/503 可重试、400 不可重试，各有测试；条件 1 补回 `response.created` 事件（与 delta 同在第 1 块），保持三次读取、两段非空 delta、第二段跨块。

第五轮（2026-09-27）退出码 1，两条「必须改」：`rejectsStream` 改成「拒绝词与独立的 stream 之间不超过 12 个字符」的成对匹配——「stream must be false」命中（禁用词紧挨 stream），「unsupported schema property 'stream'」不命中（中间隔了 16 个字符的 schema property），「unsupported upstream model」不命中（没有独立的 stream），都有测试；`streamError` 增加 `type` 类别参数，`error.type="server_error"` 没有 code 也算可重试，测试补了这条。真机输出补了脚本必然打出的 `FAKE_SERVER` 与 `HEADERS_FLUSHED` 两行。

第六轮（2026-09-27）退出码 1，一条「必须改」：固定 12 字符间隔会漏掉「stream parameter is not supported」这类拒绝词与 stream 隔着 parameter 的说法。当时放宽成 16 字符。

第七轮（2026-09-27）退出码 1，一条「必须改」：字符距离判断本质上不可靠——「unsupported schema property stream」（不带引号，中间 17 个字符）会被 16 字符间隔加边界字符误吞。改成纯词法判断：把正文拆成小写单词，看 `stream` 紧挨着的词——紧邻拒绝词（unsupported / not supported / must be false…）或隔一个 parameter/option 类称谓后是拒绝词才算；隔着 `schema property`、`upstream` 这种名词短语不算。二十个正反例（含第七轮的反例与「does not support streaming」等真实说法）逐一验证过，测试补了不带引号的 schema property 反例、「does not support streaming」正例。条件 5 的建议也落实了：不再引用间接证据，直接在本文件断言 429、5xx、网络错误各恰好两次请求（一次原始加一次立即重试）后抛出。

第八轮（2026-09-27）退出码 1，两条「必须改」：一是结构化错误不认——`{"error":{"code":"unsupported_parameter","param":"stream",…}}` 明确点名了 stream 参数却不回退。加了 `structuredRejectsStream`：正文能解析成 JSON 且 `error.param`/`error.parameter` 是 `stream`、错误码属「参数被拒」类（unsupported / unknown / not_enabled / disabled / unrecognized）才算；`invalid_type`（值类型错）、`param` 指向别的参数都不算，各有测试。二是「schema property stream is not supported」会命中向后匹配——补了跳过规则：stream 前面是 `schema property`/`schema field` 链时，这个 stream 是 schema 属性名，跳过不判。三十个正反例（含上述两条与「Unsupported param: 'stream'」等）逐一验证过。「建议」也落实：开头「不再被掐断」的表述收敛为已实现流式、真网关 524 是否消除待用户验证。

第九轮（2026-09-27）退出码 1，两条「必须改」：一是 400 正文是合法 JSON `null` 时 `structuredRejectsStream` 取 `error` 属性会抛 TypeError——解析成功后先确认根值是对象再取，测试补了「正文 null 照旧报 API 错误 400、一次请求不重试」。二是源码 257 行超出 M1 规格的 250 行上限——参数称谓表与取值写法压缩后降到 242 行。「建议」也落实：CRLF 用例改成事件分隔符真正跨在两次读取之间（第 1 块停在 `\r\n\r`，第 2 块以 `\n` 开头）；CI 运行号见下。

第十轮（2026-09-27）退出码 1，一条「必须改」：「Streaming is disabled for this model」向后匹配没认 `disabled`——`is` 后面直接跟 `disabled` 也算拒绝，测试补了这条。「建议」也落实：Content-Type 比较改成小写；SSE 行结束兼容单独的 CR。

第十一轮（2026-09-27）退出码 1，三条「必须改」：流内 429/503 被转成 `ModelError` 后跳过立即重试——`readOrRetry` 对可重试的 `ModelError` 也立即重试一次，测试断言流内 429/5xx 恰好两次请求；完成事件以 `\r\r` 结束且连接保持打开时，块尾 CR 暂存会挂死——CR 立刻当行结束，下一块开头的 LF 跳过，测试补了「完成事件后不关流也能立刻结束」；源码按新增+删除合计超 250——压缩注释与词法判断后合计 236 行。

第十二轮（2026-09-27）退出码 1，一条「必须改」：跨读取的 CRLF 检查了整个 buffer 开头，事件内部 `data:` 行末尾的 `\r` 不会丢掉下一块开头的 `\n`，会提前切出半截 JSON。改成在拼接前处理新块开头的 LF。

第十三轮（2026-09-27）退出码 1，一条「必须改」：所有 `retriable` 的 `ModelError` 都会立即重试，空文本也会多发一次请求。`readOrRetry` 只对截断、429、500、网络错误立即重试，空文本一次就抛。跨块 CRLF 用例改成同一事件两条 `data:` 行、在第一条行末 CR 处拆块。 CI 运行号推送后补。
