## 规格约束与实现问题

- **必须改 — 拆分超 300 行的源码改动。** 按 `git diff --numstat origin/main...HEAD` 只计 `apps/*/src`、`packages/*/src`，本分支为 360 行新增、7 行删除，共 367 行改动源码，超过规格与 `AGENTS.md` 的 300 行拆分门槛。规格明确拆为 CF4/CF4b（core + IPC、界面两支）；当前把两部分都放在同一分支。交付说明称“约 300 行”“未超 300 才不拆”与实际统计不符，须按规格拆分交付。
- **必须改 — 任务创建与审计不是原子操作。** `appRuntime.ts` 先调用 `this.coding.create(...)` 插入任务，之后才调用 `recordAudit(...)`；`recordAudit` 是独立的 SQL `INSERT`，两者没有事务。若审计插入失败，IPC 报错但任务已经留下，造成“建任务与审计不在同一事务”的部分成功状态。应将建任务和审计放进同一事务，并补测试模拟审计写入失败，断言任务回滚、审计不存在。
- **必须改 — 聊天 UI 在 render 阶段发请求，空结果会持续触发请求。** `AskMessage.tsx` 的 `TaskFromConversation` 在 render 中执行 `void reload()`；当 `listConversationTasks` 返回空数组时，IPC 每次返回新的数组引用，`setTasks` 触发重渲染，条件仍成立，又发一次请求。每个完整助手消息各自创建组件，会造成持续 IPC 请求/渲染。当前 jsdom 替身复用同一个数组引用，掩盖了该问题。应移到有正确依赖/加载状态控制的 effect（或提升为按对话加载一次），并测试空结果下不会循环请求。
- **必须改 — 来源跳转尚未集成到 App。** 见条件 10；需由 `App.tsx` 传入回调，设置 `openConversationId` 并切到聊天页，并补集成验证。
- **建议 — 路径值仅支持默认值。** 见条件 10；实现和测试都没有可编辑的路径输入，因此不满足规格所说的“可修改”。
- **建议 — empty scope 的主进程语义值得明确。** 主进程把显式传入的 `scope: []` 也静默替换为 `['.']`，而接口规格只写“不传 = ['.']”。UI 完成可编辑范围后，应确定空输入是拒绝还是默认，并以测试固定语义，避免把显式无效输入当成整个项目范围。
