# CF4 代审结论

审查基准：`origin/main...HEAD`，规格 `docs/委派/CF4-讨论转任务.md`、仓库 `AGENTS.md` 与 `docs/委派/交付/CF4.md`。`origin/main` 已含迁移 43 和锁定验收测试；本分支没有改它们。审查执行 `node scripts/acceptance.mjs run CF4`：37/37 通过。测试通过不等于规格满足，以下逐条说明覆盖及缺口。

5. **建议** — 覆盖充分。个人视角传入已绑定项目后核查归属及来源列。
6. **建议** — 覆盖充分。审计详情严格等于 taskId、conversationId、messageCount，并排除目标和消息正文；还测了单轮范围的条数，不只依赖固定 4。**但测试没有覆盖审计写入失败时任务是否回滚**，这一原子性缺口见后文。

8. **建议** — 覆盖充分。经原 `createCodingTask` IPC 建任务，查到三个来源列均为 null。现有任务新建语义未被改变。
9. **建议** — 覆盖充分。测试真正批准并派发给假执行器，断言执行器至少被调用一次、收到目标及验收条件、没有对话原文（含合成暗号）。派发内容回退会被捕获。

## 三、实现及边界问题

- **必须改 — 建任务与审计不是同一事务。** `appRuntime.ts:3060-3075` 先由 `this.coding.create(...)` 插入 `coding_tasks`，后在 `recordAudit(...)` 执行另一个 INSERT；`recordAudit` (`packages/core/src/audit.ts:6-10`) 本身没有事务。审计插入失败时调用会报错，但任务已留下，产生部分成功。将两项写入同一数据库事务，并补“人为令审计插入失败，任务和审计都不留”的回归测试。
- **必须改 — 空范围被静默扩大为项目根目录。** `appRuntime.ts:3060-3065` 用 `input.scope && input.scope.length > 0 ? input.scope : ['.']`，把显式传入的 `scope: []` 也改成 `['.']`。接口契约仅规定“**不传** = `['.']`”；显式空范围不应悄然扩大可修改范围。区分 omitted 与空数组，并对显式空值按校验错误拒绝（`CodingTaskStore.create` 本已有空范围校验）；补 IPC/主进程测试。该问题在新增可编辑范围前也应修好。
- **必须改 — 普通手建任务 IPC 可伪造来源，绕过 CF4 校验与审计。** `ipc.ts:739` 把 `createCodingTask` payload 原样传给 `runtime.coding.create`，`CodingOrchestrator.create` 再原样传给 `CodingTaskStore.create` (`executor.ts:582-583`)；虽然 `IxaIpcApi.createCodingTask` 类型只列出普通字段，Electron IPC 的运行时 payload 仍可附加 `originConversationId/originFromSeq/originToSeq`。`CodingTaskStore.create` 会接收并写入这些额外字段 (`taskStore.ts:152-155,217-219`)，于是可绕过新入口的消息/项目检查并无审计地伪造来源；迁移没有检查 seq 成对或顺序。普通任务 IPC 必须显式白名单/剥离来源字段，来源列只能由经校验的 CF4 专用入口写入，并补测试断言附带字段无效且手建任务来源列仍为 null。
- **必须改 — IPC 输入只靠 TypeScript 类型，缺运行时形状校验。** Electron 收到的 payload 不受编译期类型约束。`createTaskFromConversation` 在 `appRuntime.ts:3043-3044` 先调用 `input.goal.trim()`，非字符串会变成 TypeError 而不是 `VALIDATION_FAILED`；`scope: "src"` 会通过当前 truthy/length 分支，Store 按字符串逐字符校验后将 JSON 字符串而非数组写入 `scope_json`，后续 `assertChangedPathsInScope` (`taskStore.ts:361`) 对其 `.map` 会崩溃。对 IPC 数据做运行时形状校验（至少 `goal` 字符串、`scope` 为字符串数组、消息 id 字符串），不合格统一拒绝，避免无效值写入和后续派发崩溃。
- **必须改 — 聊天 UI 在 render 中持续发 IPC。** `AskMessage.tsx:503-513` 在组件 render 时执行 `void reload()`。当 `listConversationTasks` 返回空数组时，每次返回都是新数组引用，`setTasks` 触发重渲染，`tasks.length === 0` 条件仍成立，于是重复请求；每条 complete 助手消息都建一个该组件。锁定替身在 `cf4-ui.test.ts:77-80` 重用同一个 `h.tasks` 引用，掩盖了无限空结果场景。把加载移到有依赖/加载状态控制的 effect，最好按对话集中加载，并测试空结果下请求次数有限。
- **必须改 — 源码改动超出 300 行拆分门槛。** 按 `git diff --numstat origin/main...HEAD -- apps/desktop/src packages/core/src packages/contracts/src`，源码为新增 360、删除 7，共 367 行改动，超过 `AGENTS.md` 与规格的 300 行要求；规格也明确要求超出时拆为 CF4/CF4b（core + IPC、界面）。交付说明称“未超 300 才不拆”与统计不符。需按规定拆分交付，不应把超限改动留在同一支。
- **建议 — 补齐表单边界反馈。** 主进程对目标 1–2000 字、验收 1–8 条且每条 1–200 字做了权威校验；但界面只在验收文本全空时禁用按钮，9 条、201 字、空/超长目标仍可提交后才报错。规格明确了表单必填与长度规则，建议前端同步禁用或就地提示，并补边界 UI 测试；这不取代主进程校验。
- **并发与 SQL 核查。** 创建路径的校验、任务 INSERT、审计 INSERT 都是同步 sqlite 调用，方法体内无 `await`，同一 Electron 主事件循环的 IPC 不会在这些语句之间插入另一处理器；规格也允许同一范围重复创建，因此未见同事件循环重复请求竞态。跨连接/进程仍需事务保护数据库一致性。当前查询/插入均使用参数化 SQL，来源 LEFT JOIN 与迁移 43 的外键、索引本身未发现 SQL 拼接或语法问题；主要 SQL 数据形状风险是上条所述把 `scope` 字符串存成非数组 JSON。

## 四、真机检查证据

- **建议 — 脚本输出字段合适。** `scripts/real/cf4-task-origin.mjs` 最终只输出页面来源布尔值、任务/有来源任务数、seq 范围、状态、消息数和审计数；不打印对话正文或临时目录。检查使用临时数据目录、合成对话与本机假网关；截图中的内容也是合成数据。脚本对任务数、来源数、范围、状态、消息数、审计数均有断言，条件不符会非零退出。本次实际运行的是验收套件，不是该真机脚本；此处复核的是提交的脚本和交付记录。
- **必须改 — 截图遮蔽尚未充分证明。** `.logs/cf4-form.png`、`.logs/cf4-origin.png` 文件存在，但当前审查模型不能视觉读取图片。脚本没有对截图执行遮罩；它仅在截图前检查 `document.body.innerText`，第一张只查 `dir`，第二张才查 `dir` 与 `folder`，并未检查输入值等非文本节点。脚本的 `mask()` 只用于输出 seq，不用于截图。因此交付说明“截图遮掉临时目录”尚无可核验依据。应采用截图遮罩/裁剪或检查最终截图确无临时目录后提供证据；尤其第一张需检查并遮蔽项目临时目录，而不是只查页面文本。

## 结论依据

目前实跑 CF4 锁定验收 37/37 通过；条件 1–9 的锁定测试较完整，条件 10 有真实集成缺口。关键问题包括规格明确要求的范围编辑、任务来源实际导航断链、空任务列表导致的 render 循环、建任务与审计非原子写入、普通 IPC 可伪造来源、空范围/错误类型导致的校验绕过或数据损坏，以及超 300 行未拆。真机脚本输出合成且只报统计，但截图遮蔽无法据当前证据确认。以上“必须改”项完成并补足验证前不宜合并。
