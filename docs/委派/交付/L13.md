# L13 替开发推 main 被拒时，先 rebase 再推一次 交付

## 已实现

`packages/relay/src/push.ts` 的 `relayPushes`：某一条 `git push` 失败、`remote` 是 `main`、并且
`local` 是 `HEAD` 或正是 `dir` 里当前检出的分支时，依次在 `dir` 里跑 `git fetch origin main`、
`git rebase FETCH_HEAD`，成功后再 `git push origin <local>:refs/heads/main` 一次。rebase 冲突时
`git rebase --abort` 后按原来的「替开发推送失败」停下；第二次还推不上也停下。别的推送
（`dev/` 分支、`local` 不是这个目录检出的分支）不重试，照原来。`PushRecord` 加了可选字段
`rebased?: boolean`，只有 rebase 成功的那一条写 `true`。

契约里说不变的部分都没动：「先全部查一遍，有一条不过就一条都不推」那段、`verifyTurn`、
`--force`/`+`、`dir` 以外的目录。

## 已知缺口

1. `git fetch origin main` 自己失败时不重试，直接按「替开发推送失败」停下。规格只写了 rebase
   冲突与第二次推不上，没写 fetch 失败；保守处理，免得拿旧的 `FETCH_HEAD` rebase 到过期的提交上。
2. 只重试一次。fetch 与第二次 push 之间如果又有人推 main，第二次仍被拒 → 停下，符合规格
   「第二次还推不上，再照原来停下」。
3. `git rebase FETCH_HEAD` 会把 `local` 分支上的提交逐个重放；如果开发那一棒里有 merge 提交，
   默认的 rebase 会丢掉 merge 结构（只保留改动）。调度器替开发推的是 DSH 一棒的普通提交，
   本棒没处理 merge 提交，规格也没要求。
4. 真实 GitHub 上没演练过（见「真机通过」）。
