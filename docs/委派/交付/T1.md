# T1 交付说明：本机同一时间只跑一个完整 verify

分支 `dev/T1`，A 档。

## 已实现（scripts 约 110 行）

- `scripts/lib/verify-lock.mjs`（新）：`acquireVerifyLock({ path?, wait?, pollMs?, maxWaitMs?, log? })`。
  - 锁文件默认 `<os.tmpdir()>/ixaeon-verify.lock`，内容只有 `{ pid, startedAt }`，不写工作目录；
  - 用 `openSync(path,'wx')` 独占创建；拿不到按 `pollMs`（默认 10 秒）轮询，每分钟最多打印一次「另一次 verify 正在跑（进程 <pid>，<HH:MM> 开始），等它跑完」；
  - 锁里的 pid 已不在（`ESRCH`）或内容读不懂 → 删掉重拿，打印「上一次 verify 留下的锁已失效，接手」；
  - 最多等 60 分钟，仍拿不到返回 `{ busy: true, holder }`；
  - `release()` 只删自己的锁（先读 pid 比对）；`wait:false` 拿不到立刻返回。
- `scripts/verify.mjs`：一开始拿锁（`process.env.CI` 有值时整段跳过）；拿不到时打印「另一次 verify 正在跑（进程 <pid>），本次不跑，退出」并退出码 4；`exit` / `SIGINT` / `SIGTERM` 都释放自己的锁。各步骤与超时未改。

## 自动化通过

```
$ node scripts/acceptance.mjs run T1
Tests  9 passed (9)
```

覆盖条件 1–8：拿到锁/字段/无路径、活锁 `wait:false` 返回 busy、`wait:true` 等到对方退出且 log 有等待行、死锁与坏 JSON 接手、并发只有一个拿到、`release` 不删别人的锁、`maxWaitMs` 超时 busy、`verify.mjs` 的 CI 判断在锁调用之前。

## 真机通过

两个工作目录（`T1`、`T1b`，同一分支）几乎同时跑 `node scripts/verify.mjs`：

- 第二个在开头打印并等着：
  ```
  另一次 verify 正在跑（进程 41816，21:41 开始），等它跑完
  ```
- 第一个退出后第二个接着跑（两份都跑到了 integration 一步；这一步在本机因 `localServer.test.ts` 收集失败而红，和锁无关，本机此前也偶发）：
  ```
  ✗ integration（Vitest 集成测试） 失败（31.6s）   # 第一个
  ✗ integration（Vitest 集成测试） 失败（29.6s）   # 第二个（等第一个结束后才开始）
  ```

Ctrl+C：跑起来后确认锁文件里有本进程 pid（`{"pid":9964,...}`），按 Ctrl+C 后：

```
Ctrl+C 后锁已删掉
```
