## 为了让测试能跑，我定的接缝（规格只写死了位置、事件、`formatEvent`、`sendFeishu`，**请整合方看这一节**）

1. 入口照 L1 的做法：`packages/relay/src/index.ts` re-export，测试一律 `import … from '../../src/index.js'`；实现在 `packages/relay/src/notify/feishu.ts`（规格写死的）。
2. `formatEvent(e: RelayEvent): string`：第一行「【IXAEON 接力】」，第二行起照规格那张表；可选字段没有就不写那一截。
3. `sendFeishu(text, target, opts?)`：签名照上面那段（**没核对上官方**）；失败重试 2 次（默认等 2 秒、再等 5 秒）；永远不抛错，失败回 `{ ok: false, error }`（`error` 里不放地址与密钥）。
4. 限频的封装（规格说「名字由实现定」，我定成）：`createNotifier(target, store, opts?)`，`target` 可以是 `null`（没配置）；`store` 是调用方给的对象，形状 `{ sent: Record<string, string> }`（键 → 上次发出去的 ISO 时间）；`opts` 是 `{ fetch?, now? }`。`notify(event)` 回 `{ ok: true, sent: boolean }` 或 `{ ok: false, error }`：被限频、或没配置时 `sent: false`（不算失败）。限频键 = `kind` 加上 `taskId` / `role` / `why`；窗口固定 30 分钟；`daily` 不限。**置 30 分钟窗口没有做成可配**（测试用 `now` 往后推 31 分钟来验，不需要缩短窗口）。
5. `loadFeishuTarget(path?)`：读 `<数据目录>/feishu.json`（数据目录同 L1：`IXAEON_RELAY_DIR` 有值用它，否则 `<Worktrees>/IXAEON/relay/`），文件不在或读不出来 → `null`（「没配置」）。测试都传显式路径，避免依赖本机那个文件在不在。
6. 假飞书只做两件事：把请求体记下来、按脚本回 `code`。不校验签名（签名由测试自己算、逐字比），因为假服务「验签通过」不能证明客户端算法对。

## 已知缺口

1. **签名算法没和官方原文核对过**（原因见上）；这是这一支最大的一条。
2. **「背面」的算法细节没验**：`timestamp` 的容差（飞书允许多久的旧时间戳）没测；`sign` 是否要 URL 编码没测；假飞书不验签。
3. **限频的键是「kind + taskId/role/why」**：`stopped` 没有 taskId 时所有 stopped 共用一个键（30 分钟内只发一条）；规格没说这种情况下要不要分开，我按字面理解定的。
4. **重试的等待时间只量了「总用时 ≥ 6 秒」**，没有逐次量间隔；`fetch` 超时（服务不回也不断）没测。
5. **`daily` 里的 `costUsd` 只测了「保留两位」**（3.4567 → 3.46）；负零、很大、`NaN` 这类没测。
6. 这一支基于 `dev/L1`，所以合并顺序要**先 L1 后 L3**（或整合方自己 rebase）；L1 的 11 条条件、L3 的 7 条条件，两条分支的交付说明分别在 `docs/委派/交付/L1.md` 和 `docs/委派/交付/L3.md`。
