# 治理发现：验收测试文件不在类型检查覆盖内（main 现存 49 条类型错误）

> 2026-10-27 dev2（窗口）实测。发现契机：修 G1b 时自查，发现门禁全绿但我的验收测试有类型错误。
> **本文件只报事实与建议，不改任何已锁定的验收测试**（AGENTS：已并入 main 的锁定验收测试不许执行方改）。

## 1. 根因（一句话）

`tsconfig.json` 的 `exclude` 里有 `packages/*/test/acceptance/**` 与 `apps/*/test/acceptance/**`；
而 vitest 对 TS **只转写、不做类型检查**。于是 `verify.mjs` 的 `typecheck（tsc --noEmit）` 一步
从来不会碰验收测试文件——它报 exit 0，不代表这些文件没有类型错误。

## 3. 这些错误的实际风险等级（不夸大也不轻描）

- **不会让 CI 红**：vitest 不看类型，测试照跑照过（main 的 acceptance 段一直是绿的）。
- **但它们是「假断言」的温床**：`TS2554 Expected 0 arguments, but got 1`（`a5-model-failure.test.ts:155`）
  这类意味着**测试调用了一个签名不符的函数**——参数被忽略，被测行为可能根本没被触发。
  `TS2352` 那种把 `AppRuntime` 断言成 `Record<string, unknown>` 再取属性，等于绕过了类型系统去戳内部实现，
  源码一改就可能静默测不到东西。
- 换句话说：**门禁对验收测试这一层没有类型守卫**，而验收测试正是「不许自己写验收标准」那条规矩的载体。

## 4. 我自己的那一处（已修，说明发现路径）

`dev2/G1b` 上我写的 `g1b-links-regression.test.ts` 有 4 条类型错误：
`Goal` 缺 `watch` / `watch_reason` / `next_review_at` 三个字段的类型
（用户 10-25 定这三列归 G1b，G1a 的类型没带；而 `links.ts` 在读写它们），
外加 `events()` 返回未定型（`TS18046`）。
**门禁与我的 `tsc=0` 报告都没抓到它**——我是专门补查才发现的。已在 `dev2/G1b` 修掉（`99fcd0a`）：
补 `Goal` 三字段（注释写明归属）、给 `events()` 加返回类型。
改的是本轮新写、从未 lock 的文件（`锁定验收.json` 里 `g1b` 命中数 = 0），不违反「不动锁定测试」。

## 5. 建议（都归整合方，我不自行动手）

1. **先清这 49 条**：它们分布在已完成任务的锁定测试里，改动需要整合方判定「这是修类型、不是放宽条件」；
   逐条改完由整合方重锁指纹（`acceptance.mjs lock`）。
2. **再把覆盖补上**：清完后，在 `verify.mjs` 加一步
   `typecheck-acceptance（验收测试也过 tsc）`，或在 `tsconfig.json` 里把 acceptance 从 `exclude` 移到
   一个专门的 `tsconfig.acceptance.json`。**顺序必须反过来**：现在就加会立刻红 49 条。
3. 队列建议开一行 `Q1 验收测试纳入类型检查（先清 main 上 49 条）`，档位 **A**（纯测试/门禁，不碰产品语义），
   但**锁定指纹的变更归整合方**——所以它实际是「执行方改 + 整合方重锁」的两段活。

## 6. 我不做什么

- 不改任何 `锁定验收.json` 里登记过的测试文件；
- 不擅自把 `exclude` 改了（会让门禁当场红 49 条，等于自断门禁）；
- 不把这件事写成「已完成」——修复与重锁都还没发生。
