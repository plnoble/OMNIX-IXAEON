状态机（8 态）：

```text
observed → proposed → approved → experimenting → validated → deployed
                  ↘ rejected            ↘ (失败) rolled_back ↖ (失败)
```

**发布语义（统筹 2026-10-28 修正，逐条写死）**：

- `approved` **仅允许进入受控实验**（canary），**不等于可以上线**；
- `validated` 表示通过预定评测，**不自动授权生产发布**；
- `deployed` 必须**同时**具备两件东西：①发布授权（人/整合方批准）；②**实际启用证据**
  （配置版本已生效、或代码已并入的记录）——只有其一不算 `deployed`；
- `rolled_back` **可来自 `experimenting` 或 `deployed`**（两处失败都要能落此状态）；
- **任何状态都不允许模型自己迁移**：`observed→proposed` 可由系统生成；
  `approved` 必须人/整合方确认；`deployed` 必须 Relay 侧回报实际启用证据；
- **S1 不能直接写代码或部署**，继续交给 Relay / 执行控制层（见 §7）。

## 4. Baseline → Candidate 对照（原文 4 节，落成硬要求）

原文的例子正是要害：

```text
Memory Recall v1：30 场景正确 22
Memory Recall v2：30 场景正确 27
但如果旧场景退化 5 个，则不能只看总体分数。
```

落成规则：

1. **必须逐例对照**，保存「哪些从对变错」「哪些从错变对」的**具体清单**，不只存两个总分；
2. **净提升 ≠ 可接受**：出现**任何回归用例**时，报告必须显式列出，且不允许用
   「总体 +5」掩盖「旧场景 −5」；
3. `baseline` 与 `candidate` 必须**同口径、同用例集、同判定标准**——换口径就等于没比较；
4. 判定要么是**用例级可复现的自动判定**，要么标注为**人工判分**（沿用 E1 §2a：
   用户是最终真值），**禁止**「综合打分通过」这种无法复核的结论。

**依赖现实**：这套逐例对照正是 E1b 的产物。**E1 没落地前，S1 只能记录候选，不能声称「验证变好」。**

## 5. Canary 与 Rollback（原文 5 节）——**实测当前零基础，且范围已由统筹限定**

### 5.0 实测基础（写规格前查过）

- **core 与 relay 都没有** canary、feature flag、配置版本号、自动回滚机制
  （全仓 `canary|featureFlag|rollback` 只在 `storage/archiveStore.ts` 出现，那是文件备份还原，不是配置回滚）；
- 现有「配置」是 `settings.ts`（少量开关）+ relay 的 `config.json`，**都没有版本与历史**。

→ 所以 §5 不是「接现成能力」，而是要从零建。**这条是 S1 最大成本与最高风险**，
必须单独成支（S1c）、独立 B 档复审，不得与「候选记录」混在一支。

### 5.1 Canary 第一阶段范围（统筹 2026-10-28 定，逐条写死）

1. **只允许功能级 / 能力级隔离灰度**——一次只影响一个明确功能或能力；
2. **可进一步选择** 项目 / 设备 / 实例 作为隔离范围；
3. **不允许未经隔离就直接切换全局配置**；
4. **时间窗只是观察期限，不等于隔离**——「跑够 7 天」不能替代「只影响一部分」；
5. **不可逆操作、真实外发、生产数据修改必须另行授权**（不因进入 canary 就获得这些权限）；
6. **硬违规时立即停止候选版本**（硬违规口径沿用 E1 的 Hard Quiet Violation 等硬失败线，
   一旦触发不进入观察期剩余部分，直接停）。

### 5.2 「已知稳定版本」的定义（统筹 2026-10-28 定）

**不能默认「上一个 deployed 就稳定」**。一个版本要被称为「已知稳定」，必须同时具备：

| 条件             | 说明                                         |
| ---------------- | -------------------------------------------- |
| 不可变版本 ID    | 版本一旦生成不得原地修改                     |
| 配置快照 / 哈希  | 能证明「恢复到的是这一份」，不只是「上一次」 |
| 对应成功验证记录 | 指向通过评测的那次实验/评测记录              |
| 明确的稳定标记   | 显式标记，不是从「最近一次部署」推断         |
| 已验证的恢复路径 | 恢复动作本身被演练或验证过                   |

「上一个 deployed」可能本身就是一次失败上线，或从未经过验证——所以**只能显式指定**。

### 5.3 回滚必须真正恢复，且不得谎报（统筹 2026-10-28 定）

- Canary 失败时**必须真正恢复稳定配置**，并**验证恢复结果**（读回生效配置/哈希比对）；
- **记录 rollback 事件及证据**（谁触发、恢复到哪个版本、验证结果）；
- **失败恢复不得报告成功**：恢复动作失败要显式记 `rollback_failed`，
  不允许出现「已回滚」但实际仍是候选配置的状态；
- 回滚事件与证据一并留存（与 §4 的逐例证据同等级）。

### 5.4 `rollback_failed` 的归属：**独立 Attempt 结果，不是候选的第九态**（采统筹倾向）

候选的 `status` **保持 8 态不变**（§2）。回滚是**一次操作**，它有它自己的执行结果，
两者混用正是统筹点出的隐患（候选状态、部署状态、恢复状态三件事搅在一起）。

拆开后的形状（暂名，**迁移归整合方**）：

```text
rollback_attempts
  id                       -- 一次尝试一条，重试是新记录，不覆盖旧的
  candidate_id             -- 指向 improvement_candidates.id
  target_stable_version    -- 要回到的「已知稳定版本」id（§5.2 五项齐备者）
  started_at / finished_at
  outcome ∈ pending | recovered_verified | recovery_failed
  verify_evidence          -- 恢复后读回的生效配置 / 哈希比对结果
  error                    -- 失败原因
```

规则（逐条可测）：

1. `status = rolled_back` **只能**由 `outcome = recovered_verified` 的 attempt 触发；
2. `outcome = recovery_failed` 时候选**保持原状态**（`experimenting` 或 `deployed`）——
   因为它**事实上还挂在候选配置上**，谎称已回滚比留着更危险；
3. 「回滚待处理」用**派生视图**表达，不写进 `status`：
   `rollback_state ∈ none | in_progress | recovered | failed_unresolved`，由 attempts 计算；
4. 候选与 attempt **不得互相改写权威状态**（呼应 §6.1 第 1 条）：attempt 只记执行结果，
   候选状态由转换表（§2a #8/#10）在满足条件时改；
5. **回滚失败后允许的操作**（穷举，其余禁止）：
   ① 再开一条新 attempt 重试（不覆盖旧记录）；② 升级给人 / `REQUEST_USER_DECISION`；
   ③ 在隔离范围内停用该功能（若 §5.1 的开关已具备）；
6. **回滚失败后禁止的操作**：标记 `rolled_back` 或任何成功语义；删除/覆盖失败 attempt 与证据；
   把失败 attempt 当作不存在；据其继续 `deployed`；
7. **失败恢复不得报告成功**（统筹原话）：报告层必须把 `failed_unresolved` 显式呈现，
   不允许汇总里消失。

对应测试（并入 §2a 矩阵）：`S1c-R01` 只有 recovered_verified 才置 rolled_back；
`S1c-R02` recovery_failed 后状态保持 + 派生视图为 failed_unresolved；
`S1c-R03` 重试新增记录不改写旧记录；`S1c-R04` 报告不得隐藏 failed_unresolved。

## 6. 归属：**已定案 —— 方案 C（两层）**（统筹 2026-10-28 定）

### 6.0 重叠事实（决策依据，实测）

`skill_candidates`（`migrations.ts`，已存在并有运行时生命周期 `runtime/skills.ts`）已有：

```text
problem / method / eval_case / status(proposed|evaluated|approved|rejected|retired)
/ eval_before / eval_after / benefit / version / eval_evidence_json / approved_version
/ created_from_work_run_id
```

与 Improvement Candidate 对照：

| Improvement Candidate                                                      | skill_candidates 里的对应                                      | 差异                                  |
| -------------------------------------------------------------------------- | -------------------------------------------------------------- | ------------------------------------- |
| `problem`                                                                  | `problem`                                                      | 同                                    |
| `baseline`                                                                 | `eval_before`                                                  | 同                                    |
| `proposedChange`                                                           | `method`                                                       | 同                                    |
| `evaluationPlan`                                                           | `eval_case`                                                    | 同                                    |
| `expectedBenefit`                                                          | `benefit`                                                      | 同                                    |

| 状态 8 态                                                                  | 5 态（缺 `observed`/`experimenting`/`deployed`/`rolled_back`） | 缺 4 态（且 `evaluated`≈`validated`） |

### 6.1 定案内容（照抄决定，逐条落成约束）

| 表                             | 只负责                                       |
| ------------------------------ | -------------------------------------------- |
| `skill_candidates`（既有）     | **技能、工作方法、Agent 能力成长**           |
| `improvement_candidates`（新） | **系统级代码、运行配置及能力改进的变更管理** |

硬约束：

1. 两者**可**通过**稳定 ID 建立引用**，但**不得共享同一套状态机**、**不得相互改写对方的权威状态**；
2. **GKD Pattern 属于知识与技术证据，不直接等同于已经批准的 Improvement**
   —— pattern `promoted` 不等于 improvement `approved`，两者之间必须有一次显式的验证与批准；
3. 新候选**必须**包含：真实来源、基线、风险、验证计划、回滚计划（缺任一项不得入库）。

### 6.2 为什么选 C（决策存档）

`affectedCapability` + `canary/rollback` 说明它本质是**变更管理**，不是技能库；
而 GKD 已定「capability 复用 skill_candidates」，若再把系统变更塞进同一张表，
会出现「一个 agent 会什么」与「系统这版改了没有」混在一条记录里的语义混乱。

被否掉的两个方案（保留理由备将来重议）：

| 方案                          | 为什么不选                                                                       |
| ----------------------------- | -------------------------------------------------------------------------------- |
| A. 扩展 `skill_candidates`    | 要动既有表 + 既有生命周期（迁移归整合方），且**污染技能语义**（技能 ≠ 系统发布） |
| B. 新表但两套独立生命周期并存 | 会形成两套互不相干的「候选→评估→批准」，违反「不要第二套知识系统」               |

### 6.3 统一实验基础设施：`gkd_experiments` → **`experiments`**（领域中立）

统筹要求：**在 GKD-1 尚未落正式迁移之前**，把设计草稿里的 `gkd_experiments`
调整为**领域中立**的 `experiments`，`subject_kind ∈ (pattern | capability | improvement)`。

必须明确（已同步进 GKD 设计稿与迁移草稿）：

- **主体 ID 和版本绑定**——实验必须指向「哪个主体的哪一版」，不能只指 id；
- **baseline 与 candidate 的用例及判分口径**——同 §4，逐例可比；
- **环境、配置、结果与证据来源**——复原一次实验所需的信息齐全；
- **失败与回归的逐例记录**——不只存 PASS/FAIL 汇总；
- **多态引用完整性由代码层校验**（`subject_kind` 决定查哪张表，SQL 无法建 FK）；
- **实验证据不能因候选或 Pattern 删除而静默消失**——删除主体时实验记录必须留存
  （可标 `subject_retired`，**不允许 CASCADE 静默删除**）。

**S1 的第一个实验就落这张表**（`subject_kind='improvement'`），**不新建第三套实验台账**。

### 6.4 `experiments.subject_retired` 的触发规则与事务一致性

统筹定的前提：主体被删**不 CASCADE**，证据必须留下。那么「谁在什么时候置位」必须写清，
否则会出现主体已退役、新实验还在往里塞的情况。

**触发点（唯一入口）**：

- 新增一个集中入口 `retireSubject(kind, id)`，由**主体所属模块**调用；
  **禁止**各处散写 `UPDATE experiments SET subject_retired=1`（散写必然漏）；
- 置位动作与主体自身退役（`status=retired` 或删除）**必须在同一事务内**完成：

```text
db.transaction(() => {
  1) 主体置 retired（或删除主体行）
  2) UPDATE experiments SET subject_retired=1, updated_at=? WHERE subject_kind=? AND subject_id=?
})().call()
```

**退役后行为（逐条可测）**：

1. **保留**：历史实验行全部留存，且**当时的版本快照字段不得改写**——
   `subject_version` / `baseline_ref` / `candidate_ref` / `judge_rule` / `env_json` /
   `regression_json` / `evidence_json` 退役后转**只读**；
2. **禁止新实验**：`subject_kind` + `subject_id` 指向已退役主体时，insert 前校验主体状态，
   命中则抛 `IxaError(VALIDATION_FAILED)`；
3. **历史证据仍可用于复盘，但不得作为新批准的依据**——这条最容易做错：
   晋升闸/`validated` 判定若依据某条实验，而该实验的主体已退役，
   **不得据此批准新的候选**（旧结论是事实，但不能拿来给新版本背书）；
4. **硬删主体仍要留证据**：若整合方最终允许硬删主体行，`experiments` 行**不得级联删除**，
   靠 `subject_retired=1` 表达悬挂，不靠外键；
5. **幂等**：重复退役不产生差异；退役与置位两步的顺序颠倒也不留下不一致状态。

**待整合方定（我不自行选）**：

| 选项                                      | 说明               | 我的倾向与顾虑                                          |
| ----------------------------------------- | ------------------ | ------------------------------------------------------- |
| A. 保留手写标记列 `subject_retired`       | 实现简单，查询直接 | 但存在「忘置位」风险，需靠不变量测试守                  |
| B. 改用视图/生成列，由主体表实时推导      | 不会忘             | SQLite 下跨表推导只能用视图，写入校验仍需在代码层做一遍 |
| C. 两者都要（视图给读、标记给写路径审计） | 最稳               | 复杂度最高                                              |

对应测试：`S1a-S01` 退役同事务置位；`S1a-S02` 新实验引用退役主体被拒；
`S1a-S03` 退役后快照字段只读；`S1a-S04` 历史实验不得作为新批准依据；`S1a-S05` 幂等。

## 7. 与 Relay 的边界（原文 6 节，写死）

- S1 **只产出** `improvement_candidates` 与验证结论，**不写代码、不改仓库、不提 PR**；
- 真正的代码改动**一律交给 Relay / Coding Executor**（`coding_tasks`）；
- 交接方式：`approved` 的候选 → 生成一条 coding task（引用候选 id）→ Relay 执行 →
  回报结果写回候选的 `status`/证据；
- **禁止**：S1 自己调用编码执行器绕过 Relay 的流水线；也**禁止** S1 直接把候选标 `deployed`
  ——`deployed` 必须由 Relay 侧确认改动已并入后才成立。
