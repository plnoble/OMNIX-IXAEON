# 规格 G01：Hermes 会话重建了就补上前几轮；新增记忆不再触发重建

档位：**B**（改变派给模型的上下文、改变披露版本的含义）。大小：中（≤300 行源码）。依赖：无。来源：[全局审核 2026-09-20](交付/全局审核-2026-09-20.md) G01。
v2 规格：先把验收条件写成测试（`packages/core/test/acceptance/g01-*.test.ts`），**先只推测试**等整合方看过并锁定，再实现。

## 要什么

直接打在唯一验收信号「连着聊三轮，它记得住」上：

- `AgentSession`（`packages/core/src/runtime/session.ts`）只在自己手里的 `hermesSessionId === null` 时补前几轮对话；
- 适配器（`adapter.ts` 的 `reusableResident`）在**披露版本**变化时会丢掉长驻会话、新开一个；
- 披露版本（`access.ts` 的 `getDisclosureEpoch`）里包含**记忆条目的数量和最后更新时间**——每提炼出一条新记忆，版本就变。

结果：聊着聊着，底层已经换成没有上文的新会话，对话层却以为还在原会话里，不补历史。X1 修好后提炼会频繁产出新记忆，这个问题只会更频繁。

把记忆算进版本号是对的——你把一条记忆标成「不对」，它就不该留在进行中的会话里。但**新增**记忆不需要重建：下一轮注入时自然会带上。

## 契约

1. **补不补历史，只看底层会话是不是新的。** 适配器提供一个和 `start()` 同一套规则的判断（例如 `willReuseSession(contextRef)`：同一 `contextRef` 有长驻会话、进程活着、启动参数与披露版本都没变）。`AgentSession` 组装这一轮时用它决定补不补：会新开 → 补；会复用 → 不补。不再以自己手里的 `hermesSessionId` 为准。
2. **披露版本里记忆那一块，只对「收回可见性」的变化敏感**：拒绝、标过时（`time_status` 改成 ended）、被取代、改范围、删除一条记忆会让版本变；**新提炼出一条记忆不会**。具体怎么算由执行方定，测试写明。
3. 授权、披露记录、设置（含「个人记忆给聊天用」）变化时照旧让版本变。

## 约束

- 不能靠关掉披露版本失效机制来「修」：收回可见性之后，旧会话必须作废（这是隐私要求）。
- 不改记忆选材与注入格式；不加迁移。

## 验收条件

1. 第一轮说一句合成口令；然后往库里新增一条无关记忆；第二轮：仍复用同一个 Hermes 会话（协议替身里只建过一次会话），派出去的文字里不重复补历史。
2. 把第一轮注入过的一条记忆标成「不对」；下一轮：新开会话，派出去的文字里**补上了前几轮对话**（含第一轮的合成口令）。
3. 授权撤销、或「个人记忆给聊天用」开关变化：新开会话并补历史。
4. 应用重启后重开旧对话：补历史（原有行为，不许退化）。
5. 同一会话连续复用时，每一轮都不重复补历史（原有行为）。

## 真机检查

在 `scripts/real/` 加一个多轮脚本：真 Hermes、临时空库。第一轮说一个合成口令；往库里加一条合成记忆；第二轮问口令；把一条记忆标成不对；第三轮再问口令。贴三轮的回答，如实写模型有没有记住。
