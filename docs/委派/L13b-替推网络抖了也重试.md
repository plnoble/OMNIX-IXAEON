# 委派单 L13b：替开发推送时网络抖一下不停，rebase 保留合并提交

档位：**A**（还是推开发自己的提交、不强推、只碰 `RELAY-PUSH` 写的那个目录，没有放开新的权限）。大小：小（约 30 行源码）。依赖：L13 ✅。来源：接力第 17 棒（规划棒），[L13 交付说明](交付/L13.md)「已知缺口」第 1、3 条，没人接。

## 要什么

调度器替开发推送（`relayPushes`）现在只要 `git push` 一次没成就停下整个调度器，等用户 `relay resume`。这台机器上 git 连 GitHub 隔三差五握手失败（手册第 6 节「网络会抖」，L2 已经给 `fetch` 加了重试），推送这一步却没有。改成：

1. 每一次 `git push`（第一次推、rebase 之后再推）失败了，隔 2 秒、再隔 5 秒重试，最多 3 次；3 次都失败才算这一次推失败。
2. L13 的「被拒先 rebase」里那一次 `git fetch origin main` 改用 `git.ts` 的 `fetchMain`（同样的 2 秒 / 5 秒重试，回环地址绕开代理）。
3. 那一次 rebase 加 `--rebase-merges`：开发这一棒里的合并提交（A 档自己合并时 `merge --no-ff` 出来的）推上去之后还是合并提交，不被拍平。

## 为什么

- 接力要 24 小时转。现在每棒开发都要替推，一次握手失败就把调度器停下、发飞书等用户——和 L2 修掉的「拉不下来就漏查」是同一类毛病，只是在推这一边。
- 开发做 A 档时自己 `merge --no-ff` 并入 main（L13 那一单就是：`41bff5e 合并 dev/L13`）。推 main 被拒时 L13 用的 `git rebase FETCH_HEAD` 会丢掉合并提交、把那一支的提交逐个重放，main 上看不出是哪一支并进来的。

## 契约（接口写死，不改名、不加字段）

1. 只改 `packages/relay/src/push.ts`，外加 `packages/relay/src/engine.ts` 里调它的那一处。`relayPushes` 改成 `async`、返回 `Promise<PushResult>`，参数不变；`engine.ts` 那一处加 `await`。`PushResult`、`PushRecord` 的字段不变（不加「重试了几次」之类的字段）。
2. 推一条（`git push origin <local>:refs/heads/<remote>`）失败时：等 2 秒重推，再失败等 5 秒重推，第 3 次还失败才算失败。推 `dev/` 分支和推 `main` 都这样。
3. 推 `main` 3 次都失败、并且满足 L13 契约第 2 条的条件（`local` 是 `HEAD` 或 `dir` 里检出的分支）→
   - `await fetchMain(dir)`：返回 `false` → 不 rebase、这一条算失败（和现在一样）；
   - `git rebase --rebase-merges FETCH_HEAD`：失败 → `git rebase --abort`、这一条算失败（和现在一样）；
   - 成功 → 照第 2 条再推（同样最多 3 次）。成功记 `ok: true, rebased: true`；失败记 `ok: false, rebased: true`，停下。
4. 先全部查一遍、有一条不过就一条都不推，那一段不变。推的时候有一条最终失败 → 停下、后面的不推、`stopReason` 的写法不变（`第 N 棒替开发推送失败：<远端分支>`）。
5. 不加 `--force`、不带 `+`，不动 `dir` 以外的目录。

## 约束

- 只改 `packages/relay/`。已锁定的测试一个字不改。
- L6、L13 的锁定测试照过。推被拒的那几条现在会多等约 7 秒（重试的等待），vitest 的上限是 180 秒，不该超时；真有哪条因此超时，停下、写进交付说明，转整合方。
- 不另写一份重试：`push` 的重试和 `fetchMain` 用同一组等待（2 秒、5 秒）。可以把等待抽成 `git.ts` 里的一个小函数两边共用，`fetchMain` 的行为不变。

## 验收

新测试 `packages/relay/test/acceptance/l13b-push-retry.test.ts`，照 `l13-rebase-push.test.ts` 的合成仓库做法（`l6-harness.ts` 可以用）。「推一次失败一次」用裸仓库里的 `pre-receive` 钩子造：钩子读写裸仓库里的一个计数文件，前 N 次 `exit 1`、之后放行（Git for Windows 自带 sh，本机和 CI 都跑得了）。逐条：

1. 开发推 `dev/x`，钩子拒第 1 次 → 推上去了：裸仓库 `dev/x` 指向开发那一笔；记账那一条 `ok: true`、没有 `rebased`；没停下；钩子被调了 2 次；这一棒的推送至少等了 2 秒。
2. 开发推 `main`（没人先推过），钩子拒前 2 次 → 推上去了：`ok: true`、没有 `rebased`；钩子被调了 3 次。
3. 开发推 `dev/x`，钩子一直拒 → 停下、`stoppedReason` 含「第 1 棒替开发推送失败：dev/x」；钩子被调了正好 3 次；后面还有一条 `RELAY-PUSH` 的话那一条没推（裸仓库上没有那个分支）。
4. 裸仓库 main 先被别人推了一笔别的文件；开发这一棒在检出的分支上 `merge --no-ff` 了一支（那一支改另一个文件），`RELAY-PUSH <dev> relay-dev main` → 推上去了：裸仓库 main 的最新一笔有两个父提交（`git rev-list --parents -n 1`），别人那一笔是它的祖先，那一支改的文件在 main 上；`ok: true`、`rebased: true`。
5. L13 条件 2（同一个文件冲突）照旧停下、开发目录里没有留着没做完的 rebase——由已锁定的 L13 测试照着，这里不重写；交付说明里写上 `run L13`、`run L6` 的结果。
