# 委派单 S1+S2：回答逐字显示（流式）

任务来源：[三周任务单](../三周任务单.md) S1、S2。大小：**中（≤300 行改动；超了就拆：先交 S1 主进程，再交 S2 界面）**。

## 背景

用户 2026-09-18 反馈「等待回答的时间太长」。实测一问的耗时几乎全在模型本身（快模型约 8 秒，推理模型 grok-4.6 约 70 秒），这部分我们省不掉；但现在界面要**等整段回答生成完**才一次性出现，用户盯着一个转圈的气泡干等。

Hermes 其实一直在逐段吐字：`packages/core/src/runtime/tuiGateway.ts` 收到 `message.delta` 事件后调用 `this.push('text', { delta })`，只是没人转给界面。本任务把这些分段一路送到聊天气泡里。

## 契约（已定死，照着实现，不要改名、不要加字段）

```ts
// packages/contracts/src/ipc.ts
export interface AskDeltaEvent {
  conversationId: string;
  messageId: string; // 占位的助手消息 id
  delta: string;     // 本段新增的回答文字
}
// IxaIpcApi 新增（preload 用 ipcRenderer.on('ixaeon:ask-delta', …) 实现，返回取消订阅函数）
onAskDelta(listener: (e: AskDeltaEvent) => void): () => void;
```

主进程 → 界面的通道名：`ixaeon:ask-delta`。

## 要做的

### S1 主进程

1. `AgentSession.run()`（`packages/core/src/runtime/session.ts`）入参加可选的 `onDelta?: (text: string) => void`。Hermes 路径上，把事件里 `kind === 'text'` 且 `payload.delta` 为字符串的分段交给它（在现有 `wireEventLedger` 的事件回调里转，不要另开一条监听）。
2. **只转回答正文。** `reasoning.delta`、`thinking.delta`（模型的「思考」）在 tuiGateway 里是 unhandled，**不许**当成回答显示。
3. `AppRuntime.ask()`（`apps/desktop/src/main/appRuntime.ts`）传入 `onDelta`：
   - 追加到占位消息：`this.conversations.appendContent(assistantMessage.id, …)`（它本来就只在 `status='streaming'` 时生效）；
   - **数据库写入要合并**：每秒不超过 5 次，结束时把剩余的写掉；
   - 发给界面：`AppRuntime` 新增 `setAskDeltaSink(fn)`，在 `apps/desktop/src/main/index.ts` 建窗口后设置为 `mainWindow.webContents.send('ixaeon:ask-delta', e)`。
4. 回答结束时 `finishMessage` 写入的是 Hermes `message.complete` 的整段文字——**最终内容必须等于这段文字**，不能是「分段累积 + 整段」拼起来的重复内容。
5. Core 兜底路径没有分段，保持原样（一次性出现）。

### S2 界面（`apps/desktop/src/renderer/src/pages/Ask.tsx`）

1. 发送时如果还没有选中对话，**先调 `createConversation` 拿到 id 再发**，这样分段到来时知道属于哪个对话。
2. 订阅 `onAskDelta`：分段属于当前正在等待的那一轮，就追加进正在转圈的气泡；属于别的对话就忽略（切回去时从数据库重新加载即可看到已累积的部分）。
3. 用户取消（`cancelAsk`）之后，该消息的后续分段一律忽略。
4. 收到 `askQuestion` 的最终返回后，以返回/重新加载的消息为准，替换掉气泡里的临时文字。
5. 组件卸载时取消订阅。

## 验收条件（写死；执行方不改）

1. **core 集成测试**：用协议替身（照 `packages/core/test/integration/chat-model-selection.test.ts` 的 `spawnRecorder` 写法）让 Hermes 依次发 3 段 `message.delta`、1 段 `reasoning.delta`、再发 `message.complete`；断言 `onDelta` 按顺序收到恰好那 3 段，思考内容一段都没有。
2. **desktop 集成测试**（照 `apps/desktop/test/integration/ask-semantic-gate.test.ts` 的搭法，适配器用替身）：
   - 生成过程中查数据库，消息 `status='streaming'`，`content` 是已到达分段的累积；
   - 结束后 `content` **严格等于** complete 的整段文字（无重复）；
   - 发出的每个事件 `conversationId`/`messageId` 都对；
   - **两个对话同时在答**：各自的分段只进各自的消息，互不串；
   - 取消后不再追加、不再发事件。
3. **界面测试**（jsdom，照 `apps/desktop/test/unit/error-boundary.test.ts`）：mock `api`，发 A 对话的分段 → A 的气泡出现文字；发 B 对话的分段 → 当前 A 的界面不变。
4. 回归：`node scripts/verify.mjs` 全过；`apps/desktop/e2e/d6-chat-ui.spec.ts` 全过。
